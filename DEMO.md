# BeFoS — сценарий демонстрации (5–10 минут)

Документ рассчитан на защиту проекта и демонстрацию «вживую». Все шаги проверены
на реальном Android-устройстве (эмулятор `befos_avd`) против Docker-backend.

## Подготовка (делается ДО показа)

1. Backend запущен и здоров:
   ```bash
   docker compose up --build -d
   curl http://localhost:8000/api/v1/health   # → {"status":"ok"}
   ```
   При первом старте миграции и seed-данные (50 демо-пользователей с анкетами,
   тестами и интересами) применяются автоматически.

2. Android-приложение установлено на устройство/эмулятор:
   ```bash
   cd android && ./gradlew :app:assembleDebug
   adb install -r app/build/outputs/apk/debug/app-debug.apk
   ```
   Эмулятор видит host-backend по `http://10.0.2.2:8000` (configured в debug-сборке).

3. **Демо-партнёр.** Взаимный match требует второго живого аккаунта. Заранее
   создайте его через API (скрипт ниже использует только реальные эндпоинты:
   `/auth/register`, `/users/me/onboarding`, `/tests`, `/tests/answers`, `/tests/complete`):
   ```bash
   cd backend && ./.venv/Scripts/python.exe - <<'PY'
   import httpx, time
   B = "http://localhost:8000/api/v1"
   c = httpx.Client(base_url=B, timeout=30)
   email = f"demo.partner.{int(time.time())}@example.com"
   r = c.post("/auth/register", json={
       "email": email, "password": "DemoPass123!", "password_confirm": "DemoPass123!",
   }).json()
   token = r["tokens"]["access_token"]
   h = {"Authorization": f"Bearer {token}"}
   c.post("/users/me/onboarding", headers=h, json={
       "name": "Мария", "birth_date": "1994-02-10", "city": "Москва",
       "gender": "female", "gender_preference": ["male"],
       "dating_goal": "relationship",
       "about": "Люблю бег, велосипед и кофе по выходным.",
       "interests": ["running", "cycling", "hiking", "road_trips", "coffee", "cinema"],
   })
   qs = c.get("/tests", headers=h).json()["questions"]
   c.post("/tests/answers", headers=h, json={"answers": [
       {"question_id": q["id"], "option_id": q["options"][0]["id"]} for q in qs]})
   c.post("/tests/complete", headers=h)
   open("partner_token.txt", "w").write(token)   # токен вне git; удалить после демо
   print("PARTNER READY:", email)
   PY
   ```
   Партнёр затем лайкает main-демонстратора (uid возьмите из `GET /users/me` под его токеном):
   ```bash
   curl -X POST http://localhost:8000/api/v1/users/<main_uid>/like \
     -H "Authorization: Bearer $(cat partner_token.txt)"
   ```
   Аккаунт main-демонстратора (`demo@befos.app` / `Demo12345`, если включён seed-демо-вход)
   тоже подходит, но новая регистрация на устройстве зрелищнее.

4. Держите под рукой второй терминал с `adb` — для кадров/резерва.

---

## Шаг 0 → 1. Запуск

- **Что нажать:** запустить BeFoS на устройстве.
- **Что должно произойти:** splash → маршрутизация по реальному состоянию сессии:
  новый девайс → экран входа/регистрации; загруженный профиль → сразу подбор.
- **Что показать зрителю:** приложение не «притворяется» — роутинг определяется
  состоянием сервера и заполненностью профиля (`RootViewModel`).
- **Особенность BeFoS:** честная цепочка данных без заглушек; demo-пользователи реальные, из PostgreSQL.

## Шаг 2. Регистрация

- **Что нажать:** «Создать аккаунт» → e-mail вида `demo.YYYYMMDD@example.com`, пароль `TestPass123!` (×2) → «Зарегистрироваться».
- **Что должно произойти:** аккаунт создан, токен сохранён в DataStore, открыт онбординг.
- **Что показать:** пароль передаётся только по HTTPS (в демо — локальный трафик до Docker-контейнера) и нигде не сохраняется в открытом виде: backend хэширует его bcrypt (cost 12) в `core/security.py`, в БД лежит только хэш.
- **Особенность:** регистрация — часть скользящего rate limiting; лимиты реально работают (можно показать 429 частыми попытками, если спросят).

## Шаг 3–4. Онбординг: профиль и интересы

- **Что нажать:** 3 шага — имя/дата рождения (формат `ГГГГ-ММ-ДД`, напр. `1996-07-05`), пол/предпочтения, город; затем выбор интересов из каталога (обязательно пересекитесь с партнёром: **Бег, Велосипед, Кофе**) → «Сохранить».
- **Что должно произойти:** профиль сохранён через `POST /users/me/onboarding`; interests — это ссылки на каталог `interests`, а не свободный текст.
- **Что показать:** interests и город позже вернутся в карточке подбора как обоснование «почему показан».
- **Особенность:** данные структурированы (словари интересов, каталог активностей) — алгоритм работает на множествах, а не на текстах.

## Шаг 5. Тестирование (21 вопрос)

- **Что нажать:** «Пройти тест» → отвечать по одному варианту, «Далее» до конца (21 вопрос).
- **Что должно произойти:** `POST /tests/answers` (затем `/tests/complete`); backend собирает **профиль совместимости** по 7 категориям; появляется предпросмотр категорий.
- **Что показать:** вопросы покрыты всеми категориями движка (ценности, характер, интересы, коммуникация, образ жизни, досуг, цели).
- **Особенность:** без теста подбор и проценты недоступны — BeFoS не показывает «пустые» карточки.

## Шаг 6. Профиль совместимости

- **Что нажать:** подтверждение на экране результата теста.
- **Что должно произойти:** разбивка по 7 категориям, версия движка (`engine_version`) в ответе.
- **Что показать:** «это инженерная эвристика на основе анкеты и теста, не психологическая диагностика» — формулировка есть в README и в приложении.
- **Особенность:** детерминизм: тот же вход → тот же результат (можно повторить ответы и сравнить).

## Шаг 7. Подбор (discovery)

- **Что нажать:** «Начать подбор» / перейти в табу подбора.
- **Что должно произойти:** карточка кандидата с изображением, городом, интересами; очередь строит `discovery_service` из реальных профилей.
- **Что показать:** кандидатов ≥50 (seed) + созданный демо-партнёр; у каждого — настоящий профиль в БД. Изображения в seed — детерминированные duotone-аватары с монограммой имени (`seed_data/placeholder_images.py`), реальных людей они не изображают.
- **Особенность:** никакого «рандома» — кандидаты отбираются по совместимости и видимости (настройки видимости, блок).

## Шаг 8. Объяснение «Почему этот человек мне показан»

- **Что нажать:** открыть карточку кандидата (например, Марию с общими «Бег, Велосипед»).
- **Что должно произойти:** в карточке отобразится highlight-строка, например
  **«Общие интересы: Бег, Велосипед»** (при одном совпадении — **«Общий интерес: Походы»**;
  далее — «Из вашего города» / «Высокое совпадение: …»).
- **Что показать:** эту строку и попросить зрителей проверить: интересы действительно общие.
- **Особенность:** highlight выводится из **данных пары** (backend `explain`/discovery), а не генерируется случайно — ключевое обещание объяснимости.

## Шаг 9. Like

- **Что нажать:** кнопку «Нравится» (сердце) на карточке.
- **Что должно произойти:** `POST /users/{id}/like` → `{liked: true, match: false, compatibility: NN}`.
- **Что показать:** ответ содержит числовую совместимость уже сейчас — алгоритм считает её при каждом лайке, не «после матча».
- **Особенность:** детерминированная формула `Score = Σ normalize(component_i) × weight_i`, веса категорий фиксированы и документированы.

## Шаг 10. Взаимный match

- **Что нажать:** найти main-демонстратора в подборе у партнёра **или** вызвать like со стороны партнёра из prepared-скрипта/второго терминала:
  ```bash
  curl -X POST http://localhost:8000/api/v1/users/<main_uid>/like \
    -H "Authorization: Bearer <partner_token>"
  ```
- **Что должно произойти:** диалог «ВЗАИМНЫЙ ЛАЙК» — сверху заголовок и фото партнёра, кольцевой индикатор совместимости проявляется на такт позже (например 75%), подпись «Ваша совместимость 75%».
- **Что показать:** сам момент (появление + хаптик), затем «Написать сообщение» — он открывает чат этой пары.
- **Особенность:** матч — пересечение двух реальных лайков; никаких «фейковых матчей» в демо.

## Шаг 11. Чат

- **Что нажать:** ввести сообщение (латиницей проще: `Hi Maria!`) → отправить.
- **Что должно произойти:** сообщение сохраняется через REST и появляется у партнёра; история подгружается по `GET /matches/{match_id}/messages`.
- **Что показать:** доставку без перезагрузки экрана.
- **Особенность:** надёжная доставка через REST + персистентность; WebSocket отвечает за realtime-события.

## Шаг 12. Realtime WebSocket

- **Что нажать:** попросить «партнёра» ответить (со второго терминала скриптом или держать второе устройство/окно):
  ```bash
  cd backend && ./.venv/Scripts/python.exe - <<'PY'
  import httpx
  B = "http://localhost:8000/api/v1"
  c = httpx.Client(base_url=B, timeout=30)
  token = open("partner_token.txt").read().strip()
  h = {"Authorization": f"Bearer {token}"}
  ms = c.get("/matches", headers=h).json()["matches"]
  match_id = ms[0]["match_id"]
  c.post(f"/matches/{match_id}/messages", headers=h, json={"body": "Привет! Это Мария."})
  print("sent")
  PY
  ```
  (или заранее сохраните этот скрипт как `partner_reply.py`).
- **Что должно произойти:** ответ **влетает в открытый чат без перезагрузки** (WebSocket `/ws/chat/{match_id}`); индикатор набора текста, отметка «прочитано».
- **Что показать:** входящее сообщение в момент отправки + затем отправить своё и показать у партнёра «прочитано».
- **Особенность:** JWT-авторизация сокета, проверка участия в матче, keepalive-пинги 10с и авто-переподключение: можно остановить backend (`docker compose stop`) → баннер «переподключаемся», запустить → чат восстанавливается сам (проверено на устройстве).

## Шаг 13. Детали совместимости

- **Что нажать:** в чате или матче открыть «Совместимость».
- **Что должно произойти:** общий процент + 7 категорий + «сильные стороны» / «отличия» / общие интересы, версия движка.
- **Что показать:** категории, где совпадение максимальное, и реальные пересечения интересов.
- **Особенность:** объяснимость «из конца в начало»: каждый пункт текста выводится из анкет и ответов, nothing invented.

## Шаг 14. Рекомендации активностей

- **Что нажать:** вкладка/кнопка «Рекомендации» для пары.
- **Что должно произойти:** список совместных активностей с `score`, позицией и **человекочитаемыми причинами** («Почему подойдёт: …»).
- **Что показать:** нажать «Предложить в чате» → в чат пары реально уходит сообщение «Идея для нас: …Что скажете?», кнопка переходит в состояние «Выбрано» (выбор сохраняется в БД).
- **Особенность:** каталог активностей с сигналами `energy / social / cost`; оценка пары учитывает интересы, досуг, образ жизни, город и цель знакомства обоих.

## Шаг 15. Настройки и logout

- **Что нажать:** «Настройки» → видимость профиля (переключатель) → «Выйти».
- **Что должно произойти:** скрытый профиль исчезает из подбора партнёра; logout убирает токены из DataStore; повторный вход → корректная маршрутизация (завершённый профиль сразу в подбор).
- **Что показать:** до/после переключателя — карточка пропадает из очереди (обновить подбор у партнёра).
- **Особенность:** приватность — часть продукта, а не «галочка»: `visibility` и `block` проверены тестами (IDOR/набор безопасности).

## Шаг 16. Устойчивость (если просят «а что если…»)

- **Ошибки на русском.** Неправильный пароль при входе → «Не совпали email или пароль. Попробуйте ещё раз.». Английский текст API-конверта на экран не попадает: единственная точка перевода — `core/network/BackendErrorText.kt` (55 известных сообщений + совпадение по префиксу + запас по machine-code).
- **Backend выключен.** `docker compose stop backend` → на подборе `ErrorState` «Не удалось загрузить анкеты» + кнопка «Повторить», в чате — баннер о потере соединения. `docker compose start backend` → «Повторить» реально возвращает данные, WebSocket переподключается сам.
- **Пар нет.** У нового аккаунта вкладка «Пары» → пустое состояние с объяснением механики и кнопкой «Смотреть анкеты».
- **Протухшая сессия.** Если у аккаунта отозвать/сменить JWT-секрет на сервере, следующее же действие в приложении очищает токены и возвращает пользователя на экран входа с предзаполненным email — а не оставляет его на «Повторить», которое не может сработать.
- **Фото недоступно.** Плейсхолдер-аватар (монограмма бренда) вместо битой картинки; серых квадратов и «?» нет.
- **Что показать:** все четыре проверки пройдены на устройстве в этом же билде, что и демо.
