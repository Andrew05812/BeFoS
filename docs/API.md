# API BeFoS

Базовый префикс: `/api/v1`. Формат тела — JSON (кроме загрузки фото — `multipart/form-data`).
Аутентификация — Bearer access-токен в заголовке `Authorization: Bearer <token>`.

**Конверт ошибки** (все не-2xx ответы):

```json
{ "error": { "code": "STRING_CODE", "message": "Текст", "detail": null } }
```

Число, которое не помещается в колонку, отсекается на входе и не доходит до запроса:
`question_id` и `option_id` в `POST /tests/answers`, `activity_id` в
`POST /matches/{match_id}/recommendations/{activity_id}/select` и номер в `cursor` подбора
ограничены вместимостью PostgreSQL `integer`. Адрес или тело с таким числом — ошибка
запроса (`validation_error` / 422), а не сбой сервера: без границы значение доходило до
SQL, где его отвергал драйвер, и рукописная опечатка выглядела как 500 `internal_error`
с трассировкой.

Тело `POST /tests/answers` принимается пачкой, и её размер ограничен тем же отказом на входе:
не больше 500 элементов. Ограничение определяет форму двух запросов, которые пачка порождает, —
списка параметров в `IN` при проверке каталога и числа строк одного `INSERT` при записи, — а у
протокола PostgreSQL потолок 65 535 параметров. Столько ответов не содержит ни один тест, поэтому
тело длиннее — ошибка запроса (`validation_error` / 422), а не попытка отдать драйверу список,
который он не вместит.

Тот же путь сверяет строку вопроса и с таксономией трейонов: если `test_questions` держит
`category` или `trait`, которых нет в `app/compatibility/traits.py`, пачка отвечает
`validation_error` / 422, называя вопрос и объявленные оси его категории — снятое сообщение
«Question 27 names trait 'gaming_taste', which category 'leisure' does not declare; its axes are
creative, intellectual, outdoor, relaxation, social_leisure.» Отказ приходит до первой записи,
поэтому уже данные ответы и сохранённый вектор после него не меняются. Без этой сверки такой
вопрос принимался (200), попадал в leisure-подсловарь шестым ключом при пяти объявленных и
двигал категорию пары с 0.860000 до 0.716667, а объяснение печатало сырое имя оси:
«Разное отношение: gaming_taste — gaming_taste vs gaming_taste».

**Перечисления**
- `gender`: `male | female | nonbinary | other`
- `dating_goal`: `relationship | marriage | friendship | casual | networking`

## Health

| Метод | Путь | Что утверждает | Когда базы нет |
|-------|------|----------------|---------------|
| GET | `/health` | процесс backend жив | всегда 200 |
| GET | `/health/db` | соединение берётся и `SELECT 1` выполняется | 503 `{"status":"degraded","database":"unavailable"}` |

Пробы отвечают вне конверта ошибки: их читают машины, и тело `/health/db` намеренно не
содержит текста ошибки драйвера (в нём есть host, user и пароль строки подключения, а
маршрут открыт без логина).

Ключ любого окна — адрес TCP-соединения, а не `X-Forwarded-For`: клиент, который придумывает себе
адрес в этом заголовке, не получает свежий бюджет. Развёртывание за прокси объявляет обратное
переключателем `TRUST_PROXY_HEADERS`, и там, где его забывают, все посетители сайта считаются
одним адресом — замер и настройка: `docs/OPERATIONS.md`, §11.

`/health` не лимитируется ничем: монитор, получивший 429, объявит сервис мёртвым в час пик,
которого не было. `/health/db` стоит 60 запросов в минуту на адрес — не потому, что он дорогой
для процессора, а потому, что каждый его запрос берёт соединение из пула, который делят настоящие
пользователи, и цикл по этому маршруту без ответа может оставить их без пула. 429 здесь приходит
в обычном конверте (`rate_limited`), поэтому алертер, который опрашивает оба маршрута чаще раза в
секунду, должен читать 429 как «я слишком часто спрашиваю», а не как «сервис падает».

Когда база недоступна, любой обычный эндпоинт отвечает тем же 503 и заголовком
`Retry-After: 5` в стандартном конверте:

```json
{ "error": { "code": "database_unavailable", "message": "BeFoS is sorting itself out for a moment. Try again in a few seconds." } }
```

Это не «ошибка запроса» и не повод выбрасывать сессию: 5xx означает «попробуй позже», и
клиент сохраняет токены и набранный текст. Детали — в [`OPERATIONS.md`](OPERATIONS.md).

## Auth

| Метод | Путь | Тело | Ответ |
|-------|------|------|-------|
| POST | `/auth/register` | `{email, password, password_confirm}` | `201` `AuthResponse` |
| POST | `/auth/login` | `{email, password}` | `AuthResponse` |
| POST | `/auth/refresh` | `{refresh_token}` | `TokenPair` (плоский, без `user`) |
| POST | `/auth/logout` | `{refresh_token}` | `204`, тело пустое |
| POST | `/auth/change-password` | `{old_password, new_password, password_confirm}` | `204`, тело пустое (нужен Bearer) |
| GET | `/auth/sessions` | — | `{sessions: [SessionCard], has_more: bool}` (нужен Bearer) |
| POST | `/auth/sessions/{session_id}/revoke` | — | `204`, тело пустое (нужен Bearer) |
| POST | `/auth/sessions/revoke-all` | — | `204`, тело пустое (нужен Bearer) |

`SessionCard`:

```json
{
  "id": "uuid", "device": "BeFoS/1.0.0 (Pixel 7, Android 14)",
  "signed_in_at": "ISO-8601", "expires_at": "ISO-8601", "current": true
}
```

`device` — строка `User-Agent`, с которой сессия пришла; она пишется в строку как пришла, без
перевода на слова, которых сервер не видел, и отсутствует (`null`) у входа, который пришёл без
этого заголовка.

`AuthResponse`:

```json
{
  "user": { "id": "uuid", "email": "user@mail.com", "is_active": true, "created_at": "ISO-8601" },
  "tokens": { "access_token": "…", "refresh_token": "…", "token_type": "bearer", "expires_in": 900 }
}
```

Ошибки: несовпадение `password_confirm` → `422`; занятый email → `409`; неверный пароль → `401`.
Отказ входа на адрес, которого нет, и отказ на существующем адресе с неверным паролем отвечают одним
и тем же `401` с одним телом, а с стадии 52 — и примерно одним временем; существование адреса по-
прежнему отдаёт только `409` регистрации.

**Где считается пароль.** bcrypt при `rounds=12` — это 451–468 мс чистого процессора на этой машине
(четыре повтора каждой из двух функций, `hash_password` и `verify_password`, снятые одним прогоном
внутри процесса), и с
стадии 51 он считается не на событийном цикле воркера, а в рабочем потоке (`asyncio.to_thread`):
приложение держит один процесс uvicorn, поэтому синхронный расчёт на этом цикле останавливал весь
трафик процесса. Для клиента не изменилось ни число обращений к базе (вход — те же два, см.
«Сколько стоят маршруты сессии» выше), ни длительность самого вызова: 492.5 мс медианой на цикле
против 505.1 мс на потоке, а изменилось то, кто ждёт — дешёвый посторонний запрос в окне одного
входа получает ответ 21–22 раза вместо двух, и четыре входа подряд, которые на цикле шли
последовательно 1896.7 мс, теперь укладываются в 532.0 мс. Замер пары, прибор и потолок по числу
процессоров — в разделе «Парные прогоны стадии 51» файла `docs/SCALE_PLAN.md`.

**Когда пароль не считался вовсе.** Стоимость одной проверки — это ещё не ответ на вопрос, считается
ли она вообще. До стадии 52 `AuthService.authenticate` проверял пароль только когда аккаунт найден:
условие `user is None or not await verify_password_async(…)` обрывается на первом истинном операнде.
Оба отказа оставались неразличимы по статусу и телу, поэтому единственной разницей между ними было
время: на сокетном стенде (один процесс uvicorn, пять повторов, прогрев отброшен) несуществующий
адрес отвечал за 24.69 мс, существующий с неверным паролем — за 476.08 мс; разрыв 451.39 мс при
нулевом контроле 14.9 мс. Это оракул перечисления адресов. Теперь маршрут платит ровно одну проверку
bcrypt на обеих ветках: неизвестный адрес сверяется с `TIMING_FILLER_HASH` (`app/core/security.py` —
тот же маркер алгоритма и та же стойка `rounds=12`, что у хешей в `users.password_hash`), а вопрос
«найден ли пользователь» возвращается после проверки, поэтому напечатанная рядом исходная строка
этого хеша не входит ни под каким адресом. Замер после правки: 486.37 мс против 486.99, разрыв 0.62
мс, нулевой контроль не сдвинулся (14.52 мс). Для клиента это значит, что опечатка в адресе на входе
стоит теперь столько же, сколько неверный пароль, — около 486 мс вместо 24.7; лимитер (`20`
обращений в минуту на адрес) отказывает до проверки пароля, и `429` стоит 2.5 мс. Прибор и разбор —
в разделе «Парные прогоны стадии 52» файла `docs/SCALE_PLAN.md`.

**Сколько стоят маршруты сессии.** Оба они заканчиваются одной и той же записью в
`refresh_tokens`, и до стадии 34 оба сначала читали эту запись, хотя решала её не прочитанная
строка, а сама запись: отзыв — это `UPDATE … WHERE revoked is false`, чей счётчик строк и отвечает,
жив токен или уже погашен. Чтение до записи ничего не решало и только держало окно, в котором два
запроса с одним токеном успевали увидеть его живым; это окно закрыл ещё `consume` (строка
«Гонка ротации refresh» в истории, 2026-10-07), а здесь оно закрыто совсем — чтения больше нет.
`POST /auth/refresh` стоит 3 обращения вместо 4: проверка пользователя, погашение старого токена,
вставка новой пары. `POST /auth/logout` — 1 вместо 2: оба условия, которые раньше применялись на
Python после чтения (хеш принадлежит этому же владельцу, и строка ещё жива), теперь сидят в `WHERE`
той же записи, поэтому строку никто не трогает дважды. Контроль `POST /auth/login` — 2 → 2, он не
менялся.

Отзыв уже мёртвого токена стоит 1 обращение на обеих ветках, и повторный выход отвечает `204`: не
найти ничего — не ошибка. Один переход подорожал, и это цена отсутствия чтения: подпись верна, а
строки в таблице нет — отказ занимает 2 обращения вместо 1, потому что о судьбе токена раньше
сообщало само чтение. Все эти числа сняты слушателем `before_cursor_execute`. На стенде с 50 001
анкетой маршруты не измерялись, и стадия 34 называла причину верно: в `refresh_tokens` стенда было 0
строк, а самих путей не было в списке наблюдаемых у `ops/scale_probe.py`, — поэтому она отдавала
только число обращений, как стадии 23 и 29. Стадия 77 сняла эту оговорку: оба пути наблюдаемы, а
сессии прибор выпускает до замеряемого окна, поэтому `docs/SCALE_PLAN.md` печатает им медианы на трёх
объёмах (1 000 / 10 000 / 50 000 анкет) — 20.6 / 20.7 / 19.7 мс у поворота и 13.1 / 12.1 / 11.1 мс у
выхода (прогон A, база `befos_s78a`, 2026-10-13 21:58:28…22:02:59 UTC; переснят прогоном B на
`befos_s78b` — 20.3 / 20.3 / 21.5 мс и 12.0 / 11.6 / 13.0 мс), — и после каждой из шести съёмок в
`refresh_tokens` стоит 23 строки, 17 живых и 6 отозванных, посчитанных запросом, а не оценкой
`n_live_tup`. Стадия 78 пересняла и число обращений: счётчик прибора видит теперь письма, и колонка
стенда даёт повороту 3, а выходу 1 — ровно те числа, которые снял слушатель, и это сверка двух
независимых приборов, а не пересчёт одного. Миллисекунды стенда при этом мерят вызов `AuthService`
целиком, вместе с декодом предъявленного токена и его хэшем, поэтому их нельзя сложить с 3 и 1 как с
ценами отдельных обращений. Убранное обращение посчитано отдельно — прямым прогоном обеих форм через asyncpg на
dev-базе, где 642 строки токенов: 60 чередующихся повторов, медиана 7.366 мс против 4.745 мс, то
есть +2.621 мс на вызов. `EXPLAIN (ANALYZE, BUFFERS)` показывает, что новый `UPDATE` с охраной в
`WHERE` идёт по тому же `ix_refresh_tokens_token_hash`, что и убранный `SELECT`, а не по полному
обходу таблицы: 0.348 мс против 0.402 мс у прежнего `UPDATE` по первичному ключу, — то есть
выигрыш даёт пропущенное обращение, а не план. Держат форму семь проверок
`tests/test_session_token_roundtrips.py`, а `tests/test_refresh_token_reuse_race.py` перенесён с
прочитанной строки на само погашение.

**Дверь для своего слова.** `POST /auth/change-password` — пятая дверь `/auth`, и единственная из
пяти, которая требует предъявить сессию: в её теле нет адреса аккаунта, единственный аккаунт, которого
она может коснуться, назван заголовком `Authorization`, и подменить чужое слово этим запросом нельзя ни
при каком теле — без заголовка дверь отвечает 401 и не меняет ничего. Тело — `old_password`,
`new_password`, `password_confirm`, и те же два формальных правила, что у регистрации, держат его в
двух местах сразу: схема `ChangePasswordRequest` (`app/schemas/schemas.py:54`) не пускает слово короче
восьми, а сервис (`app/services/auth_service.py:137`) переспрашивает совпало ли сказанное дважды —
оба правила отвечают `validation_error` / 422, и оба отвечают до сверки прежнего
слова, поэтому bcrypt на опечатку в подтверждении не тратится. Неверное прежнее слово — `unauthorized` /
401 с текстом «Current password is incorrect.»; оракула перечисления здесь быть не может в принципе:
аккаунт назван заголовком, а не телом, поэтому ветки «адреса нет» у двери нет вовсе, а сверка
bcrypt платится ровно одна — и на отказе, и на принятии.

Ответ при совпадении — `204` с пустым телом, и пуст он не из лени: запись о новом слове гасит
`refresh_tokens` этого аккаунта целиком (`revoke_all_for_user`, тот же механизм, что у выхода), а
значит пара токенов, на которой стоит запросивший, попадает в отозванные. Отдать её обратно было бы
обещанием, которое сервер уже нарушил. Клиент поэтому обязан сбросить сохранённую сессию сам — на
Android это делает слой репозитория, и только на принятом ответе: на 401 хранилище остаётся ровно
там, где было, потому что сервер не изменил ничего, и человек, ошибившийся в своём прежнем слове,
остаётся вошедшим на этом телефоне и на всех остальных.

Граница, которая остаётся открытой и названа как открытая: отозваны refresh-токены, а access-токен,
выпущенный до смены слова, отвечает до своего истечения — по умолчанию 30 минут
(`ACCESS_TOKEN_EXPIRE_MINUTES`). Живой путь это проверяет прямо: после принятой смены прежний
access-токен читает `GET /users/me` (200), а refresh того же набора — уже 401; то же окно закрывает и
то, что чужая сессия от чужого слова не падает — партнёр после смены читает свой профиль тем же
запросом. Дверь закрывается сверкой версии слова на каждом чтении access-токена (столбец вроде
`password_changed_at` и проверка его в `get_current_user`) — на этой стадии она не закрыта, и
число обращений, которое такая сверка стоит, не замерено.

Потолок у двери тот же, что у входа и обновления: `/auth` лимитируется скользящим окном в двадцать
обращений на минуту для адреса, и дверь смены слова тратит тот же бюджет, а не заводит свой. Проверено
 прогоном против живого сервера: попытки угадать прежнее слово получают `unauthorized` / 401, ничего не
записывая, пока окно не кончится (не позже двадцать первого обращения к дверям `register` / `login` /
`change-password` с этого адреса), следующее обращение получает `rate_limited` / 429 — и в тот же
момент отказывает уже `POST /auth/login`, тогда как `GET /users/me` продолжает отвечать 200: окно
держит двери входа, а не чтение профиля. Держат форму этой двери девять проверок
`tests/test_the_account_can_change_its_password.py` и пятнадцать сверок ряда клиента
(`PasswordRotationWritesTest.kt` про форму запроса, ответы сервиса и сброс хранилища,
`SettingsPasswordChangeTest.kt` — про экран настроек).

**Какие устройства держат его сессию.** Три двери того же ряда — `GET /auth/sessions`,
`POST /auth/sessions/{session_id}/revoke` и `POST /auth/sessions/revoke-all` — закрыли пробел, который
`docs/OPERATIONS.md` §14 описывал как работу оператора: `register`, `login` и `refresh` пишут строку в
`refresh_tokens` на каждом входе и хранят рядом `User-Agent`, с которым тот вход пришёл, но до этой
стадии ни один аккаунт не мог ни прочитать свои строки, ни закончить одну из них. Красный съём
(`stage110/s110_red_sessions.log`, прогон 09:29:18…09:29:23 UTC 2026-10-19 против живого контейнера, база
`befos`) отвечает на это семью `404`: проверены семь возможных адресов двери (`/auth/sessions`,
`/auth/devices`, `/auth/refresh-tokens`, `/me/sessions`, `/auth/sessions/{id}/revoke`,
`/auth/logout-everywhere`, `/auth/sessions/revoke-all`), и живых строк у пробного аккаунта к тому моменту
две — то есть у человека, который хочет убрать одну из них, оставалось одно средство: сменить своё слово,
что гасит их все, включая ту, с которой он читает ответ. Тот же съём называет вторую половину пробела: на
всем стенде 1223 строки токенов (203 живых), и 111 из них пришли под `ktor-client` — так движок Ktor
подписывал себя по умолчанию, поэтому три телефона одного человека выглядели в его списке тремя
одинаковыми словами, а различить их было нечем.

`GET /auth/sessions` (обработчик `api/v1/auth.py:88`, сервис `AuthService.own_sessions`,
`services/auth_service.py:156`) отвечает `{sessions: [SessionCard], has_more: bool}` и держит правило
двух отсева: строка, уже отозванная, и строка, у которой `expires_at` позади, не показываются, потому что
ни та, ни другая не может быть тем, на чём человек стоит, а на экране это выглядело бы как предупреждение
об устройстве, которого нет. Порядок — `created_at DESC, id DESC`, а не по одному времени: два входа попадают в
одну микросекунду, и список, у которого хвост переставляется между двумя страницами, показал бы одно
устройство дважды. Потолок — `AuthService.SESSIONS_SHOWN = 50` строк (`services/auth_service.py:154`), а
за ним стоит `has_more`, поэтому обрезанный список говорит, что он обрезан; доводить его до конца
страницами продукт не умеет, и это названо открытым: жест «завершить все» дотягивает до строк, которые на
экран не вместились, а тап по названному id — нет. Ответ не несёт ничего, чем можно открыть сессию: ни
refresh-токена, ни хеша, который хранится вместо него, — только id устройства, его слово о себе и два
момента.

`current` ставит ровно одна строка, и ставит её не сервер, а предъявленный токен: `AuthService.issue_tokens`
(`services/auth_service.py:85`) кладёт в access-токен требование `sid` — id строки, которую эта пара
только что открыла, — и чтение (`app/auth/deps.py:56`) достаёт его из того же набора требований, который
уже проверил
`get_current_user`, поэтому ни одного обращения к базе метка не стоит. Токен, подписанный до того, как
требование появилось, не помечает ничего — угадать «самую свежую строку» значит поставить враньё на экран,
который по этому слову предлагает человеку не трогать именно её.

`POST /auth/sessions/{session_id}/revoke` (`api/v1/auth.py:127`) заканчивает одну строку — той же формой,
что `consume`, `revoke_all_for_user` и `revoke_one_live_for_owner` в `repositories/token_repo.py`
(`:33`, `:68`, `:100`): один `UPDATE`, чей предикат держит и id, и
владельца, и `revoked is false`, и живую дату, поэтому решение о гонке принимает сама запись, а список
возможных жертв ровно тот, что показывает чтение. Чужой id, уже отозванный id, истёкший id и id, которого
никогда не было, отвечают одним и тем же `404 not_found` с текстом «No live session with this id for this
account.» — это не место, где узнают, какие сессии у чужого аккаунта были. `POST /auth/sessions/revoke-all`
(`api/v1/auth.py:110`) гасит все живые строки аккаунта, включая ту, на которой стоит запрос, и потому, как и
смена слова, отвечает пустым `204` без пары токенов: отдать пару значило бы отозвать собственную запись
тут же. Граница та же, что у двери слова, и названа она тем же словом: отозван refresh, а выданный раньше
access живёт до своего `ACCESS_TOKEN_EXPIRE_MINUTES` (30), и мгновенного отзыва доступного токена в продукте
не умеет ни одна дверь, которая гасит сессии, — ни смена слова, ни эти три.

Все три двери стоят в том же окне `_auth_limiter`, что вход, регистрация, обновление и смена слова
(20 обращений на адрес за 60 с), и тратят тот же бюджет — список, который человек перечитывает после
каждой записи, не стал вторым ничем не ограниченным маршрутом. Держат форму этого ряда четырнадцать
проверок `tests/test_the_account_reads_which_devices_hold_its_session.py` (список читается только своим;
устройство, пришедшее без имени, показано как без имени; самый свежий отвечает первым и каждая строка
один раз; ровно одна строка называет устройство, на котором стоит читающий; токен без `sid` не помечает
ничего; в списке нет материала, которым открывается сессия; отсечённое устройство не трогает другое;
мёртвая строка отвечает как отсутствующая; чужой аккаунт не заканчивает чужую сессию; истёкшая строка ни
показывается, ни отсекается; «завершить все» гасит собственную строку спрашивающего; дверь, которая
заканчивает сессию, по-прежнему держит слово аккаунта в неприкосновенности; и список останавливается на своём потолке
и говорит об этом), двадцать девятью сверками клиента (`data/repository/OwnSessionsReadWritesTest.kt` — 10,
`presentation/settings/SettingsOwnDevicesTest.kt` — 19) и двадцатью одним шагом живого пути, где аккаунт
входит с двух устройств, читает свой список, режет названный id, натыкается на отказ чужим токеном,
собирает всё одним жестом и остаётся с одним живым входом (`stage110/s110_journey_final.log`, 213/213,
прогон 11:52:11…11:57:42 UTC 2026-10-19 против контейнера, собранного из дерева `a8ace25`).

`is_moderator` стоит или снимает дверь в очередь модерации на странице «Настройки» (раздел
«Модерация» ниже), и отвечают его только хозяйские маршруты `/users/me…`; публичный
`GET /users/{user_id}` его не отдаёт, а ни один маршрут не принимает его на запись.

`city_preference` — город поиска, фильтр, который человек называет своей колоде. С правки
стадии 104 его принимает `PATCH /users/me`, экран «Профиль» пишет его полем «Город поиска»,
и чтение кандидатов слушает его (`_preference_conditions`): названный город сужает колоду до
профилей этого города (сверка без учёта регистра), пустая строка после снятия пробелов
снимает фильтр, и в колонке остаётся NULL. Поле, которого в запросе нет, не тронуто; потолок
120 символов, больше — `422 validation_error`. Отвечают его только хозяйские маршруты
`/users/me…`: чужой профиль не знает, где его хозяйка ищет, и `GET /users/{user_id}` поля
не несёт.

`GET /users/me/export` отвечает не страницей, а документом: `Content-Disposition: attachment` с
именем `befos-account-<id>.json`, внутри — `format` (`befos.account-export/1`), `generated_at` и
разделы `account`, `profile`, `photos`, `questionnaire`, `taps`, `deck`, `pairs`, `chats`, `plans`,
`blocks`, `complaints`, `sessions`, счётчик `counts` и потолок `limits`. Разделы читаются теми же
сервисами, что отвечают экранам (`MatchesService.list_matches`, `SafetyService.list_blocked`,
`AuthService.own_sessions`, `PlanService.list_for_viewer` и `detail`, `TestService.stored_profile`),
и второй раз ничего не пересчитывается: процент экрана совместимости остаётся округлением на экране,
а в файле лежит число, из которого его округлили, и версия модели, которая его посчитала. Дверь
только читает: строки переписки выбираются прямыми операторами, а не через `ChatService.history`,
который по пути отмечает нить прочитанной, — и это снято проверкой, сверяющей число операторов и
счётчики непрочитанного до вызова и после него. Потолок — 500 строк на раздел; порезанный раздел
назван в `limits.truncated`, а `counts` продолжает отвечать числом строк, которые стоят в базе, —
вырезка не выдаётся за полный список. Секретов документ не несёт: ни хеша слова, ни материала
токенов, ни частной заметки партнёра по плану, ни руки модератора и его слова за решением жалобы, —
при этом переписка обеих половин в нём лежит, потому что её писали и читали вдвоём, и отозванная
строка остаётся в файле с отметкой `recalled`. Имя аккаунта в пути не нужно: токен доступа уже
сказал, чьи строки собирать, и `DELETE /users/me` закрывает эту дверь вместе с аккаунтом — тот же
токен после стирания получает `401`, и это снято живым шагом пути. Дверь стоит перед опасной зоной
экрана «Настройки» (38-й сценарий `docs/USER_FLOWS.md`), а её цена на стенде не снималась: у неё нет
пути в `ops/scale_probe.py`, и это названо открытым концом в `docs/RELEASE.md` §8.

`OnboardingProfile` (POST `/users/me/onboarding`):

```json
{
  "name": "Алекс", "birth_date": "1996-05-10", "city": "Москва",
  "gender": "male", "about": "…", "dating_goal": "relationship",
  "interests": ["hiking", "cinema", "coffee"], "lifestyle": {},
  "age_min": 18, "age_max": 60, "gender_preference": ["female"]
}
```

`birth_date` — строка `YYYY-MM-DD`; возраст должен быть 18..120.

Возраст считается по UTC-календарю — по той же дате, что ставит метки времени всем строкам.
Гейт 18+ при регистрации, число `age` в ответе и границы колоды спрашивают «сегодня» у одной
функции (`app.models.base.utc_today`), поэтому не могут разойтись: раньше гейт и колода жили
на календаре сервера, а карточка — на UTC, и в часы, когда эти даты различаются (в UTC+3 это
полночь — три утра), продукт пропускал человека как взрослого и показывал его на год моложе.
Часовой пояс устройства сервер не знает и в расчёт не берёт.

**Фото.** `photos` отдаётся в одном порядке на всех эндпоинтах: выбранный владельцем (`is_primary`)
первым, далее `position`, `created_at`, `id` — два последних как детерминированный разрыв ничьих,
которого после записи ряда вообще быть не может: `position` пишет один проход `_write_photo_order`
(`app/services/profile_service.py`), и у снимков одного владельца он различается всегда. Экраны
берут `photos[0]` как аватар, поэтому это контракт, а не деталь реализации. Рядом с загрузкой стоят
три маршрута того же владельца: `DELETE /users/me/photo/{photo_id}` снимает строку и переписывает ряд
без неё, `POST /users/me/photo/{photo_id}/primary` ставит названный снимок головой,
`PATCH /users/me/photo/order` принимает весь порядок (`photo_ids`, от одного идентификатора) и
отвергает его на 422, если список называет один снимок дважды или забывает хоть один из
имеющихся —
полуперестановка и есть тот способ, которым ряд разъезжается со своей головой. Все три читают
только свои строки: чужой `photo_id` отвечает 404 той же строкой, что и отсутствующий, поэтому
проверить чужой ряд этим путём нельзя. Файл на диске стирается после коммита удаления, поэтому
отказ удаления не трогает снимок, который всё ещё в чьём-то списке. `POST /users/me/photo`
принимает JPEG/PNG/WEBP; тело читается с пределом `MAX_UPLOAD_SIZE_MB` (дефолт 5) и отказывается на
422 `validation_error`, не дочитывая остаток; слишком большой объявленный холст — тоже 422, а не
500. Потолка числу снимков в анкете маршруты не ставят — кадр принимается, пока человек его присылает.
Перенкодирование (разбор, `draft`, `thumbnail` до 1600 px, запись JPEG и файл в `UPLOAD_DIR`) с
стадии 51 считается в рабочем потоке, а не на событийном цикле воркера: на холсте 3024×4032 это
427–549 мс процессора, и, пока они шли на цикле, их платил весь трафик процесса. Файл на диске от
этого не меняется — обе формы прогоняют один и тот же конвейер, и на каждый размер приходит один
md5. `DELETE /users/me` удаляет и строки `photos`, и файлы: `/uploads` — публичная статика без
авторизации, поэтому скрытие анкеты не означает, что снимков больше нет.

**Запись профиля.** `interests` — slug'и из `GET /users/interests`: ответ принимает до тридцати
названий, повторяющиеся считаются одним, а того, чего в каталоге нет, просто не будет в записанном
наборе (отдельного отказа на неизвестный slug нет — см. «Что остаётся открытым» в `CHANGELOG.md`).
Порядок `interests` в ответе записи закреплён: ответ догружается выборкой, упорядоченной по
`user_interests.interest_id`, а запрос, который сам меняет набор, раскладывает строки, прочитанные
в каталоге, по тому же признаку. Прежний порядок ничем не был закреплён — набор догрушался связью
без `ORDER BY`, — и на стенде три формы этого чтения (догрузка связью, выборка сохранённого
набора, выборка по slug'ам) и собранный ответ принесли шесть интересов одним и тем же порядком,
то есть правка закрепила то, что и так совпадало, а не переставила ответ.
Запись набора — одно обращение к базе, сколько бы интересов в нём ни было. Ответ собирается из
строки, которую запись держит, а не из второго чтения той же строки: сессия после `commit` не
сбрасывает значения (`expire_on_commit=False`, `app/core/database.py:43`), а в ответе нет поля,
которое сервер досчитывает сам, — `age` является свойством над `birth_date`. Список интересов
поднимается из таблицы ровно один раз и только тогда, когда запрос его не менял: запись, которая
его заменяет, уже держит те же строки — она читала их из каталога, чтобы записать. На замере
свежего аккаунта (слушатель `before_cursor_execute`, видит каждый оператор) это 10 обращений на
`POST /users/me/onboarding` — одинаково при одном интересе и
при тридцати, — 5 на `PATCH /users/me` с одним полем, 3 на `POST /users/me/visibility` и 20 на
`DELETE /users/me`. `GET /users/me` стоит 4: этот экран набор показывает, поэтому он единственный,
кому это чтение нужно, и выполняет он его один раз. Кто зовёт это чтение на запуске приложения: с
стадии 40 — ровно один корневой вентиль; раньше заставка строила второй `RootViewModel` в
хранилище своей навигационной записи, и те же четыре обращения платились дважды на каждый запуск
(замер 02:00:58 — пара `GET /users/me` в одну секунду, порты 38308 и 38324).
Изменение полей предпочтений (`age_min`, `age_max`, `gender_preference`, `interests`,
`dating_goal`, `city_preference`) сбрасывает колоду этого человека, а изменение `interests`, `city` или `dating_goal` —
страницу активностей его пар и проценты на сохранённых матчах: это те входы, из которых они
считаются. Поэтому запрос на изменение профиля дороже, чем кажется из его тела, и цена зависит от
того, какие поля в нём оказались и есть ли у человека пары: на аккаунте с одной живой парой правка
одного города стоит 6 обращений, правка набора интересов — 13, а набора вместе с городом — 14
(прежние деревья того же прогона: 7, 15 и 16; город ещё до этого сняла стадия 35 — 11 → 7). Разницу
делает веер инвалидации — сброс страницы активностей, чтение пары и три пакетных чтения двоих
(анкеты, интересы, векторы ответов).

Ответ на запись набора интересов изменила стадия 65: маршрут, который молча сохранял только то, что
нашёл в каталоге, теперь отказывает. `PATCH /users/me` и `POST /users/me/onboarding` дают
`422 validation_error` в трёх случаях: назван пустой интерес (`An interest name cannot be empty.`),
после снятия пробелов и повторов названо больше тридцати (`A profile can hold at most 30 interests;
this answer names N.`) или назван slug, которого в `interests` нет (`Interests the catalogue does not
know: a, b.`). Отказ приходит до `DELETE` старого набора, поэтому ни сохранённый набор, ни остальные
поля того же тела не меняются: тело `{"interests": ["ghost"]}` больше не стирает тридцать интересов
одним ответом `200`, как стирало до стадии — на live-контейнере тридцать хранящихся строк стали
одной записанной, и ответ не сказал ни о двух вымышленных именах, ни о снятых двадцати девяти.
Проверка не читает ничего сверх того же обращения к каталогу, которым запись и так превращает slug'и
в строки, а потолок стоит перед ним: тело из двухсот вымышленных slug'ов получает короткое сообщение
про потолок, а не двести имён обратно (эхо имён ограничено ровно тем же числом). Пустой список
остаётся ответом, а не ошибкой — это то, чем экран снимает все чипы. Оба отказа, число которых
считает сервер, клиент печатает русскими строками по постоянному префиксу
(`android/.../core/network/BackendErrorText.kt`): «Интересов можно выбрать не больше 30.» и «Таких
интересов в списке нет. Обновите экран и выберите заново.»

Тем же порядком стадия 66 закрыла `gender_preference` на тех же двух маршрутах. Пока список
прочёсывался по `VALID_GENDERS`, значение вне него молча выпадало, а регистр, которого набор не
держит, молча превращался в пустой список; пустой список — это не «никто не выбран», а снятый
фильтр: `social_repo._preference_conditions` навешивает `Profile.gender.in_(...)` только на
непустое предпочтение. Замер на рабочем контейнере (четыре отдельных зрителя, снимок
`s66_probe_deck.txt`, 15:09:06 UTC): зритель с `["male"]` получал колоду из 47 карточек, зритель с
`["Male"]` — из 94, и его анкета после этого не отвечала ничего о том, что он просил. Теперь
`422 validation_error` в трёх случаях: названо пустое значение (`A gender preference cannot be
empty.`), после снятия пробелов и повторов названо больше четырёх (`A profile can prefer at most 4
genders; this answer names N.`) или названо значение, которого в `VALID_GENDERS` нет (`Genders the
server does not know: a, b.`). Отказ приходит до записи строки, поэтому ни сохранённое
предпочтение, ни остальные поля того же тела не меняются; `["  Male  ", "female", "female"]` —
по-прежнему `200` и `["male", "female"]`, а пустой список — по-прежнему штатный способ снять
выбор. Проверка ничего не читает: `VALID_GENDERS` живёт в модуле, а потолок выведен из его длины,
поэтому он не может разойтись с множеством, которым проверяется. Клиент печатает оба counted-отказа
русскими строками по префиксу — «Предпочтений по полу можно выбрать не больше четырёх.» и «Таких
вариантов пола в списке нет. Обновите экран и выберите заново.»

Стадия 70 свела словарь целей знакомства к одному источнику и заставила матрицу проверять себя.
Значения `dating_goal` лежали в шести местах: строки и столбцы `_GOAL_COMPAT` (25 клеток над
пятью целями), `profile_service.VALID_GOALS`, `seed.GOALS`, `models.enums.DatingGoal` и клиентский
`DatingGoalLabels`. Замер до правки (`probe_goal_vocabulary.txt`, 22:58 UTC) — один набор на шесть
копий, диагональ 1.0, 0 асимметричных клеток, то есть само число менять не пришлось и не было
ничего, что заметило бы их расхождение. `VALID_GOALS` теперь читает `traits.GOAL_KEYS`, собранный
из строк матрицы: цель, которую принимает запись, но не знает движок, перестаёт быть правкой,
которую можно сделать незаметно. Обещание симметрии из комментария к таблице проверяет
`validate_goal_matrix()`, вызванный при импорте, — полная таблица над 0..1 с диагональю 1.0, и на
смоделированной правке (клетка `marriage` против `friendship` становится 0.60, а обратная ей
остаётся 0.45) импорт падает, называя оба числа. До стадии такой импорт проходил, и двое читали бы разные
проценты одних и тех же ответов, потому что движку пара передаётся «зритель первым». Отказ записи
стал называть причину: было `Invalid dating goal.`, стало `Invalid dating goal 'situational'. The
app scores: casual, friendship, marriage, networking, relationship.` Клиент печатает по постоянному
началу свою строку «Выберите цель знакомства.» — ту же, что и до правки.

Молчание о цели перестало читаться расхождением и в движке рекомендаций: пустое значение
`_goal_match` отдаёт 0.5 — половину веса `goal` (0.10), — тогда как `goal_compatibility` отвечал
`0.0`, и карточка теряла всю полосу. Замер на движке: до правки — `probe_goal_vocabulary.txt`
(22:58 UTC), после — `s70_probe_goal.txt` (23:23 UTC); 82 % у пары с двумя названными целями,
72 % до правки и 78 % после, если одна сторона не назвала ничего. Это та же поправка, что стадия 60 сделала interests-компоненте движка пары, и она
согласует два движка: там пустой ответ читается как `NEUTRAL_SCORE` при `has_data=False`. На трёх
живых базах ветка пока никому не доступна — 0 пар, у половины которых нет строки профиля, 0 половин
пары с пустой целью и 0 профилей с таким значением без строки пользователя (`befos`, `befos_scale`,
`befos_test`, снимок `s70_final_erased.txt`, окно 00:51:59…00:52:00 UTC), а 236 строк с `erased` —
значение, которое пишет удаление аккаунта, — держат `is_deleted = true` у каждой и в пару не
читаются. Поэтому правка меняет не текущий процент, а правило, по которому он считается.

`PublicProfile` (GET `/users/{id}`):

```json
{
  "user_id": "uuid", "name": "…", "age": 27, "city": "…", "about": "…",
  "dating_goal": "…", "gender": "…",
  "interests": ["Походы", "Кино"],
  "photos": ["/uploads/a.png"],
  "compatibility": 82,
  "categories": [{ "category": "values", "label": "Ценности", "score": 88, "weight": 0.25,
                   "has_data": true }],
  "shared_interests": ["hiking", "cinema"]
}
```

**Кого этот маршрут показывает.** Чужой профиль отдаётся тому же правилу, которым колода решает,
кого показывать: аккаунт жив, активен, не спрятан и прошёл анкету. Поэтому профиль, который
человек спрятал, аккаунт, который отключили, и недоделанная регистрация отвечают `404 not_found` —
как и `POST /users/{id}/like` с `/pass`, — а не `403` и не анкетой без фото. Владелец читает свой
профиль в любом из этих состояний: прятаться — не значит отключаться, и недоделанную анкету надо
чем-то доделывать. Удалённый аккаунт не читает ничего — его токен отвергается на 401, ещё до
маршрута. Блокировка отвечает 404 в обе стороны, чтобы маршрут не подтверждал существование того,
кого уже не видно.

## Tests (профиль совместимости)

| Метод | Путь | Тело | Ответ |
|-------|------|------|-------|
| GET | `/tests` | — | `{questions: [...], total, answered, categories: [{key, label, total, answered}]}` |
| GET | `/tests/progress` | — | `{answered, total, percent, remaining, completed, categories: [{key, label, total, answered}]}` |
| POST | `/tests/answers` | `{answers: [{question_id, option_id}]}` | прогресс |
| POST | `/tests/complete` | — (без тела) | `{categories: [...], axes: [{category, trait, label, value, side}], completed_at}` |
| GET | `/tests/profile` | — | `{categories: [...], axes: [{category, trait, label, value, side}], updated_at}` |

Тело `POST /tests/answers` — карта ответов: приложение отдаёт её целиком, когда закрыт последний
вопрос, а до того одним элементом на каждое касание, чтобы тест, брошенный на середине, не
пришлось проходить заново. Пачка проверяется по каталогу одним чтением и пишется одним оператором,
поэтому запрос стоит одинаково — несёт он пять ответов или двадцать один. Пока хоть один элемент
недействителен, не записан ни один: ответ — 422, а сохранённые ответы остаются прежними. Вопрос,
названный в теле дважды, считается повтором касания и сохраняет последний вариант. В той же сверке
каталога строка вопроса проверяется и на оси: `category` или `trait`, которых таксономия трейонов
не объявляет, отказывают этой же пачкой до первой записи — текст отказа и снятые им числа приведены
в начале этого документа.

`POST /tests/complete` отвечает теми же числами, которые он только что записал: пересчёт профиля
делает один проход по сохранённым ответам, и ответ берётся из его результата, а не из второго
чтения тех же строк. Ворота «тест закрыт» — те же два счёта, что считает `/tests/progress`, и отказ
случается до любых писем: в отказанном запросе не появляется ни строка `compatibility_profiles`, ни
строка `test_results`. `GET /tests` считает поле `total` по тому каталогу, который отдаёт, —
отдельного запроса-счётчика у него нет. У `/tests/progress` его тоже нет: маршрут поднимает
активные вопросы двумя колонками (`id`, `category`) и ответы этого человека двумя колонками — тот
же состав строк, что читает `GET /tests`, но без текстов вопросов и вариантов, — поэтому `total`,
`answered` и `categories[]` этого ответа выводятся из одних и тех же двух чтений и не могут
разойтись с `GET /tests`.

`axes[]` в ответе `/tests/complete` — те же значения вектора, из которых посчитаны `categories[]`:
`category` и `trait` — ключи таксономии, `label` — русское имя оси, `value` — 0..1, `side` — слово,
которым `describe_side` читает это значение (тот же единственный вывод, что даёт карте пары
`GET /matches/{id}/universe`). Обход — `TRAIT_CATEGORIES`, поэтому оси одной полосы идут рядом и
клиент собирает их под свою полосу по `category`; сами `categories[]` при этом отсортированы по
ключу, так что порядок двух списков совпадает по группам, а не по строкам. Ось, по которой у
человека нет активного ответа, в `axes[]` не появляется:
полоса без данных остаётся и без позиций, а не с нулём. Что `categories[].score` — среднее осей,
лежащих под ним, держит проверка `test_a_band_percent_is_the_average_of_the_axes_listed_under_it`.

`GET /tests/profile` — то же чтение спустя недели. У зачёта тело ответа нельзя попросить обратно:
`POST /tests/complete` пишет (пересобирает вектор, пересортировывает колоду, обновляет проценты пар,
печатает `TEST_COMPLETED`) и отказывает, пока анкета не закрыта. Маршрут читает посчитанное:
полосы из `test_results`, оси из `compatibility_profiles.vector`, и собирает оба списка той же
`_bands_and_axes`, которой собран ответ зачёта, — экран, открывший профиль через месяц, не может
показать процент, которого экран завершения не показывал. Идентификатора человека в пути нет:
`current_user` берётся из токена, поэтому чужой профиль не открывается ни одним параметром.
`updated_at` — момент последней пересборки вектора из ответов этого человека; у профиля, который
никогда не считали, маршрут отвечает `categories: []`, `axes: []`, `updated_at: null` — пустой
профиль, а не нулевой. Сколько разделов анкеты для него не заполнено, маршрут не пересказывает:
это уже отдаёт `GET /tests/progress`, и экран, которому нужны пропуски, спрашивает их там.
Проверки — `tests/test_a_finished_profile_can_be_read_back_after_the_evening_it_was_made.py`.

`categories[]` в `/tests/progress` — те же полосы, что называет `GET /tests` (`key`, русское
`label`, `total`, `answered`), и служит он экрану пары: полоса совместимости без данных спрашивает,
какой раздел анкеты её наполняет и сколько в нём уже отвечено, — отвечать это по всему каталогу с
текстами вопросов значило бы платить экрану пары чтением чужого маршрута. Экран пары спрашивает
этот маршрут только когда пустая полоса на экране есть.

Вопрос:

```json
{
  "id": 1, "category": "values", "trait": "…", "text": "…", "position": 0, "kind": "scale",
  "options": [{ "id": 11, "text": "…", "position": 0 }],
  "selected_option_id": 11
}
```

`kind` — как вопрос задан: `choice` — стопка карточек, одно касание на ответ; `scale` — те же
самые упорядоченные варианты, только выставленные бегунком. Поле про один лишь показ: ответ
остаётся строкой `test_options`, так что `option_id` в теле, счёт `answered` и вектор
совместимости не сдвигаются ни на полбалла там, где вопрос задан шкалой. Клиент, который поля не
знает, рисует карточки и шлёт ровно тот же ответ. Шкалой заданы шесть осей каталога
(`values/family`, `values/growth`, `personality/openness`, `communication/frequency`,
`lifestyle/activity_level`, `leisure/intellectual`), остальные пятнадцать — карточками; шкалой
выбраны только те наборы вариантов, что перечисляют градацию силы, потому что над четырьмя
разными местами или четырьмя разными планами бегунок сказал бы, что человек стоит на шкале,
которой там нет.

`selected_option_id` — вариант, на котором стоит сохранённый ответ этого вопроса, `null` там, где
его нет. Каталогу это поле нужно, чтобы отметить карточку, а не спрашивать человека, что он уже
отвечал: экран открывает первую неотмеченную строку, и тест, брошенный на середине, продолжается с
неё, а не с первого вопроса. Поле ничего не дописывает: `GET /tests` читает те же строки
`test_answers`, что читал до него, — один двухстолбцовый выбор вместо `COUNT`, из тех же строк
считаются и `answered`, и отметки, и `categories[]`. Поэтому `answered` этого ответа и `answered`
`/tests/progress` — один и тот же набор строк, а `categories[]` называет каждую полосу каталога,
в том числе ту, под которую нет ни одного ответа: `{"key": "values", "label": "Ценности", "total":
5, "answered": 2}`.

`categories[]` после завершения — `CategoryScore`: `{category, label, score (0..100), weight,
has_data}`. У личной анкеты `has_data` всегда `true`: категория, под которую нет ни одного
ответа, в этот список не попадает (`build_vector` пишет полосу только при непустом наборе
трейтов, `test_service.py:120`), а на экране пары те же семь полос могут стоять на нейтральных
50 без данных — различает их флаг ниже.

## Discovery (подбор)

| Метод | Путь | Query | Ответ |
|-------|------|-------|-------|
| GET | `/discover` | `limit` (1..50, по умолчанию 20), `cursor` | `Paged<DiscoveryCard>` |
| GET | `/discover/liked-me` | — | `{likes: [IncomingLikeCard], has_more}` |
| GET | `/discover/liked` | — | `{likes: [IncomingLikeCard], has_more}` — свои касания, зеркало входящих |
| GET | `/discover/passed` | — | `{passed: [PassedUserSummary], has_more}` |
| POST | `/users/{user_id}/like` | — (без тела) | `{liked, match, match_id, compatibility}` |
| POST | `/users/{user_id}/pass` | — (без тела) | `{passed}` |
| DELETE | `/users/{user_id}/like` | — | `{likes: [IncomingLikeCard], has_more}`; `404` — аккаунт этого касания не писал, и чужое он тоже не называет; `422` — тап по самому себе |
| DELETE | `/users/{user_id}/pass` | — | `{passed: [PassedUserSummary], has_more}`; `404` — аккаунт этого пропуска не писал, и чужой он тоже не называет; `422` — пропуск самого себя |

`Paged`: `{items: [...], next_cursor, has_more}`.

`cursor` — непрозрачная метка последнего просмотренного места в колоде, её выдаёт сам
сервер и меняет только он. Позиции (`offset`) нет: свайп убирает кандидата из выборки,
и номер следующей карты тут же начинает указывать на другого человека. Колода
ранжируется один раз и хранится в таблице `discovery_queue`, поэтому страницы не
повторяются и не пропускают кандидатов, даже если между запросами кто-то скрылся или
был заблокирован.

Метка проверяется на входе, а не доверяется как число: `cursor`, который нельзя
расшифровать, и номер за пределами колонки `rank` дают `validation_error` / 422 — общее
правило для таких чисел записано в начале этого документа.

`DiscoveryCard`:

```json
{
  "user_id": "uuid", "name": "…", "age": 27, "city": "…", "about": "…",
  "dating_goal": "…", "photo_url": "/uploads/x.png",
  "interests": ["Походы"], "compatibility": 82, "shared_interests_count": 3,
  "highlight": "Общие интересы: Походы, Каякинг"
}
```

`highlight` — короткая «расшифровка» подбора на экране карточки («почему этот человек мне показан»), всегда производная от реальных данных: имена общих интересов, совпадение города, либо сильнейшая категория совместимости ≥ 70%. Поля нет, если ни одно правило не сработало.

Подбор исключает самого пользователя, заблокированных и уже «пропущенных»/лайкнутых. Взаимный лайк создаёт `match` и возвращает `match: true` с `match_id`.

**Сколько стоит лайк.** Собеседника этот путь читает дважды и намеренно: до замка пары — только
чтобы ответить «можно ли вообще», после замка — строку, из которой считается процент (порядок
держат тесты гонок стадий 12 и 15). Остальное было повтором. До стадии 26 вектор ответов каждого
из двоих приходил своим обращением, а перед вставкой программа ещё и спрашивала, есть ли уже строка
в `likes`; слушатель `before_cursor_execute` на свежем аккаунте дал первому лайку 15 обращений,
теперь 13. Второму тапу по той же карточке — 13 стало 12: пред-чтение ушло, `INSERT` остался и при
конфликте по `uq_like_pair` ничего не пишет, потому что именно он теперь и отвечает на вопрос «был
ли этот лайк». На объёме те же два снятых чтения — 12 → 10 на стенде вечера стадии 26, медиана
83.9 / 74.5 / 70.0 мс
стала 77.9 / 65.1 / 66.1 мс при 1 000 / 10 000 / 50 000 анкет; выигрыш по времени утверждается на
двух больших масштабах, а на 1 000 контроль сдвинулся сильнее пути — пара прогонов в
[`docs/SCALE_PLAN.md`](SCALE_PLAN.md), §«Парные прогоны стадии 26». Третью колонку нынешней таблицы
эта строка печатает числом 12, и это не возврат к прежнему: стадия 78 пересняла счётчик правилом,
которое видит письма, и 12 раскладываются на те же 10 чтений плюс `insert likes` и `delete passes`
(проба составов в §«Задержки горячих путей» той же таблицы).

**Сколько стоит страница, на которой не осталось карточек.** Правило подбора — самое широкое
чтение продукта: семь коррелированных `NOT EXISTS` по `likes`, `passes`, `blocks`, `matches` и самой
очереди. До стадии 27 страница, которой нечего отдать, спрашивала его за один запрос трижды: два
идентичных `select profiles.user_id from profiles join users …` (оба `new_candidate_ids` — вторая
попытка дозаполнения шла потому, что булев ответ первой не умел отличить «никого не нашли» от
«не искали») и `select 1 from (select profiles.user_id …)` (`has_unqueued_candidate`, тот же
предикат с теми же предпочтениями). Слушатель `before_cursor_execute` на свежем аккаунте дал этой
странице 10 обращений, теперь 8: пустой ответ скана живёт в запросе до его конца, поэтому
`has_more` больше не переспрашивает. Запоминается только строгое направление: пустой скан при тех
же предпочтениях гарантирует пустой и `has_unqueued_candidate`, а ненайденное — нет, и случай
«скан принёс анкеты, но движок не оценил ни одной» по-прежнему уходит в отдельный вопрос базе.
Следствие видно на третьем тесте этого набора: анкета, завершившая онбординг после пустой
страницы, попадает в следующую — память запроса не переедает её. Разбор пары прогонов —
[`docs/SCALE_PLAN.md`](SCALE_PLAN.md), §«Парные прогоны стадии 27».

**Сколько стоит страница, которая дозаполняет колоду.** У этого пути одни и те же люди читались
дважды за один запрос: `_ranked_scores` поднимала анкеты, списки интересов и векторы ответов, чтобы
упорядочить новую пачку колоды, а `_build_cards` поднимала их же — теми же id, в той же сессии, —
чтобы собрать карточки из строк, только что выбранных из этой пачки. Слушатель
`before_cursor_execute` на свежем аккаунте (шесть анкет в дозаполнении, три карточки на странице)
дал такому запросу 19 обращений, теперь 16: пакетных чтений кандидатов стало три (по одному на
заботу) вместо шести (по два). Ранжирование отдаёт разобранных кандидатов наружу, и карточки
дочитывают только тех, кого этот запрос не ранжировал, — строки, которые колода получила из прежнего
запроса. Фотография при этом читается как читалась: ранжирование её не смотрит. Правило пригодности
тоже остаётся перед сборщиком карточек — решает `deck_fresh_ids`, а не память запроса, иначе анкета,
скрывшаяся после ранжирования, уехала бы в ответ из того, что этот запрос уже держал. Второе
следствие одной пары чтений: процент на карточке теперь ровно тот, что лежит в строке очереди,
упорядочившей эту карточку. Разбор пары прогонов — [`docs/SCALE_PLAN.md`](SCALE_PLAN.md),
§«Парные прогоны стадии 28».

### Кто лайкнул (`GET /discover/liked-me`)

`IncomingLikeCard`:

```json
{
  "user_id": "uuid", "name": "…", "age": 31, "city": "…", "photo_url": "/uploads/x.png",
  "compatibility": 88, "liked_at": "2026-10-19T06:00:00+00:00"
}
```

До стадии 112 таблица `likes` читалась в одну сторону: `has_liked_back` спрашивает, лайкнул ли
один конкретный человек, анти-джойн колоды — лайкнул ли зритель его. Кто лайкнул зрителя, не
спрашивал никто, поэтому строку, которую написала чужая карточка, мог прочесть только тот, кто её
написал. Маршрут меняет направление чтения, а не запись: он ничего не пишет и ни одного столбца
не трогает.

Три правила решают, кто попадает в список, и ни одно не придумано для этого маршрута. Человек
должен быть показуем вообще (`_candidate_conditions`: не удалён, не деактивирован, анкета не
скрыта, онбординг заверш), двое не должны уже быть парой, и блокировки не должно быть ни в одну
сторону (`_relationship_conditions`). Скрывшаяся анкета, которая лайкнула до того как скрыться,
остаётся снаружи: список не имеет права называть человека, попросившего его не называть.

Жесты зрителя из правила колоды сюда сознательно не скопированы. `pass` отвечает на вопрос
«показывать ли этого снова», а стоящий за ним чужой лайк — ответ другого человека про зрителя, и
он принадлежит обоим. Убрать его здесь значило бы сделать свайп тайным отказом назад: никто бы не
узнал, что тот, кого он отверг, сказал «да».

Процент на строке — тот, с которым касание было сделано. `likes.compatibility_score` пишет сам тап
(стадия 26), а перечисление его только читает: пересчёт ответил бы читателю числом, которое не
было ничьей причиной. Строка без числа остаётся без числа — `null`, не `0`: поле разрешает пустоту
с самого начала, а одеть непрочитанное в измеренное — тот же дефект 72-1, названный для полос
совместимости.

Порядок — от нового к старому, и при равных микросекундах его держит `id`: порядок, который база
договаривает сама, делает список подбрасыванием монеты (та же правка, что у курсора истории,
стадия 54). Курсора у маршрута нет намеренно: страница отдаёт 50 строк и честно говорит
`has_more`, когда за ними ещё кто-то есть, — тот же договор, что у списка устройств
(`auth_service.SESSIONS_SHOWN`). Колоде курсор нужен, чтобы не повторять карты между запросами, а
этот список перечитывается целиком и живёт один вход.

Цена обращения известна из кода и из прибора: одно чтение `likes` и два пакетных дочитывания
страницы (анкеты и ведущие фотографии, `get_profile_cards` / `get_primary_photos`); в цикле база
не спрашивается ни разу, а пустой входящий список платит одним обращением — обе пакетные функции
уходят в пустоту до всякого `SELECT`. Ряд `liked_me` снят стадией 113, переснят стадией 117, снова
переснят стадией 118, ещё раз — стадией 119 и ещё раз — стадией 120, тем же прогоном, что и вся
таблица: 31.2 / 49.3 /
64.1 мс медианой
при трёх обращениях за вызов на 1 000 / 10 000 / 50 000 анкет (`docs/SCALE_PLAN.md`,
§«Задержки горячих путей», артефакт `s120_scale_a.json`). Зеркало своих касаний
(`GET /discover/liked`) читает ровно столько же и стоит в той же таблице рядом — двадцатый ряд
снят тем же прогоном.

### Кого вы лайкнули (`GET /discover/liked`)

Страница отдаёт те же строки `IncomingLikeCard`, что и входящий список, и держит тот же договор
без курсора: `LIKED_SHOWN` карт (пятьдесят, `discovery_service.py:41`) и честный `has_more`,
когда за ними есть ещё. Отличие от входящей двери ровно одно — направление обращения к таблице:
входящие читают `to_user_id == viewer`, эта читает `from_user_id == viewer`, то есть половину
таблицы, которую карточка зрителя написала сама. До стадии 116 спросить «кого я лайкнул» было
негде: человек видел, кто тронул его, но не своих собственных касаний.

Два правила попадания скопированы у входящего списка целиком, не переизобретены: человек должен
оставаться показуемым (`_candidate_conditions`) и двое не должны быть парой или держать
блокировку (`_relationship_conditions`). Правило пары носит здесь основание, которого у входящих
нет: отвеченный касанием человек уже живёт в списке совпадений, и вторично называть его «вашим
касанием» рядом с дверью «вы пара» — тот же шум, который стадия 112 выгнала с той стороны.
Собственный `pass` зрителя фильтром не стал и по обратным причинам: `like` при записи удаляет
строку пропуска (стадия 26), поэтому касание и пропуск одной пары не стоят одновременно.

Число на строке — тот процент, с которым этот аккаунт видел карточку в момент жеста; он прочитан
из собственной строки `likes.compatibility_score`, а не пересчитан, — та же позиция против
дефекта 72-1, что у входящего списка. Порядок — от нового к старому, при равных микросекундах
его держит `id` (стадия 54). Цена чтения снята стадией 117, переснята стадией 118, ещё раз —
стадией 119 и ещё раз — стадией 120, тем же
прогоном, что и цена входящего списка: 30.7 / 55.1 / 62.6 мс медианой при трёх обращениях за вызов
на 1 000 / 10 000 / 50 000 анкет, корень плана — `Limit` с 51 строкой на всех масштабах
(`docs/SCALE_PLAN.md`, §«Задержки горячих путей», артефакты `s120_scale_a.json` и
`s120_scale_b.json`). Под этим рядом лежит тот же список, что и под
рядом отзыва: 88 / 894 / 4 494 касания (отбор `s120_row_counts.json`), — до стадии 118 ряд отзыва
стоял на вдвое большем.

### Забрать касание назад (`DELETE /users/{user_id}/like`)

Маршрут без тела снимает собственное исходящее касание и отвечает оставшимся списком той же
формы, что и `GET /discover/liked`, — не булевой истиной, а страницей: экран, задавший вопрос,
рисует то, что держит сервер, тот же договор, что у `unpass` и `unblock` (стадия 111, 115).

Три ответа различимы друг от друга намеренно. Свой аккаунт получает `422`
(`ValidationError("You cannot act on your own profile.")`) — строка, которая не могла
существовать, это не потерянная строка, и `404` отправил бы зовущего искать ответ, которого он не
давал. Чужая или уже снятая пара касаний получает `404`
(`NotFoundError("You have not liked this user.")`), и он неотличим: маршрут не объявляет,
существовало ли касание у другого человека. Гонка повторного DELETE решается тем же `lock_pair`,
что берут `like`, `pass` и блок: кто держит строку — тот её снимает, второй отвечает ту же `404`,
двух снятий никто не рапортует.

Снято только направление спрашивающего (`delete_like`): касание ничего не говорит о касании
другого человека, а состоявшаяся пара остаётся стоять — нераспаривание это дверь стадии 105 со
своим каскадом по чату и встречам, и растворять разговор кнопкой «забрать касание» тяжелее, чем
она обещает. Колоду маршрут тоже не трогает: like никогда не писал строку памяти колоды
(стадия 26 писала только `likes` и удаляла `passes`), поэтому анти-джойн, прятавший человека,
поднимается сам в момент удаления строки — и он возвращается той же дверью, что прятала.

### Кого пропустил (`GET /discover/passed`)

`PassedUserSummary`:

```json
{
  "user_id": "uuid", "name": "…", "age": 27, "city": "…", "photo_url": "/uploads/x.png",
  "passed_at": "2026-10-20T09:12:03+00:00"
}
```

До стадии 114 таблица `passes` читалась только как отсутствие: анти-джойн `_acted_conditions`
(`backend/app/repositories/social_repo.py:433`) спрашивает колоду, не отвечал ли зритель «нет»
этому человеку, — и на этом чтение кончалось. Своей двери у строки не было, поэтому свайп за
экраном подбора оставался невидимым для того, кто его сделал, и необратимым.

У списка одно направление, и оно то же, что у списка заблокированных: читатель — `from_user_id`.
Ряд, где читатель стоит на месте пропущенного, принадлежит другому человеку, и принести его сюда
значило бы рассказать одному, что другой о нём решил.

Правило показа взято из колоды не целиком, и обе снятые половины сняты сознательно.
`_candidate_conditions` (`backend/app/repositories/social_repo.py:390`) остаются: удалённый,
деактивированный, скрывший анкету и не завершивший онбординг в список не попадает. Фильтры подбора
(`_preference_conditions`, `:442`) — возраст, пол, город — это вопрос «кого показать дальше», а
здесь запись уже данных ответов: сдвинуть планку возраста и потерять половину списка, который ещё
и отменяется, было бы нечестно. Анти-джойны блокировки и пары (`_relationship_conditions`, `:406`)
сторожат приглашение на встречу, которым эта страница не является, и маршрут возврата применит их
обратно, когда человек вернётся в подбор.

Процента у строки нет намеренно: пропуск ничего не оценивает, и число о нём было бы числом ни о
чём. Порядок — от нового к старому, а при равных микросекундах его держит `id`
(`backend/app/repositories/social_repo.py:816`) — то же правило, которое стадия 54 записала для
курсора истории: порядок, который база договаривает сама, превращает список в подбрасывание
монеты. Курсора нет: страница отдаёт 50 строк (`PASSED_SHOWN`,
`backend/app/services/discovery_service.py:37`) и честно говорит `has_more`, когда за ними ещё
кто-то есть, — тот же договор, что у входящих касаний и у списка устройств.

Чтение стоит одного обращения к `passes` и двух пакетных дочитываний страницы — анкеты и ведущие
снимки; в цикле база не спрашивается ни разу. Ряд `passed` снят стадией 115, переснят стадией 117,
снова переснят стадией 118, ещё раз — стадией 119 и ещё раз — стадией 120: 25.9 / 52.9 / 82.6 мс
медианой при трёх
обращениях за вызов на
1 000 / 10 000 / 50 000 анкет (`docs/SCALE_PLAN.md`, артефакт `s120_scale_a.json`). У этого ряда
есть оговорка, которую называет
тот же раздел: посев собственных касаний снимает строки пропусков тронутых людей, и вечерний прогон
стадии 115 стоял на 400 / 4 000 / 20 000 проходов, а этот — на 315 / 3 109 / 15 509: снято ровно по
одной строке на касание зрителя (88 / 894 / 4 494, отбор `s120_row_counts.json`), поэтому ряды
двух таблиц не сравниваются как подешевение.

Ряд держат двадцать три проверки нового
`backend/tests/test_the_account_takes_back_a_person_it_passed.py` и девятнадцать андроидных
сверок экрана пропущенных — шесть в `PassedUsersReadTest.kt` и тринадцать в
`PassedViewModelTest.kt`.

### Забрать пропуск обратно (`DELETE /users/{user_id}/pass`)

Ответ человека колоде — не одна строка, а две: ряд в `passes`, который читает правило подбора, и
ряд в `discovery_queue`, который помнит, что карточку уже показывали. Снять только первый означало
бы оставить второй замок: `_never_queued` (`backend/app/repositories/social_repo.py:474`) не
пускает в добор того, кого колода уже держала, поэтому человек не вернулся бы ни в колоду, ни в
какой другой список. Маршрут снимает оба — `delete_pass`
(`backend/app/repositories/social_repo.py:117`) по `DELETE … RETURNING`, и `deck_release` (`:692`)
ровно одним рядом пары, а не очередью целиком: очистка очереди за спиной вернула бы карточки,
которые уже показаны, и пересчитала колоду, которая работала.

Замок здесь тот же, что у лайка, блокировки и вычистки аккаунта (`lock_pair`,
`backend/app/repositories/social_repo.py:43`), поэтому повтор запроса на гонке не даёт двух
освобождений: убирает ряд тот, кто держал его в свой черёд, а второй отвечает тем же `404`, каким
ответил бы чужой паре. Отличить «такого пропуска нет» от «такой пары нет» снаружи нельзя — иначе
дверь становится вопросом, есть ли у двух других людей записанный ответ.

Пропуск самого себя отвечает `422`, а не `404`: строки, которой не могло быть, не хватает так же,
как не хватает чужой, и `404` отправил бы клиента искать ответ, которого он никогда не давал. Слово
то же, что `MatchService._reject_unavailable` даёт для тапа по своей анкете, — один и тот же вход с
двух сторон не должен называться по-разному, иначе два экрана начнут спорить об одном факте.

Обратно человек приходит в хвост колоды, а не в её начало: новый ряд получает ранг по
`deck_next_rank` (`backend/app/repositories/social_repo.py:572`), то есть за теми карточками,
которые ещё ждут своей очереди. Отвечает маршрут не `true`, а страницей — тем списком, который
сервер держит после ухода строки, по тому же договору, что разблокировка
(`SafetyService.unblock`): экран красит то, что перечислено, а не то, что вычтено из памяти.

Стоимость этого хода названа стадией 117 и переснимается каждым прогоном таблицы, который переснимает
её зеркало: `unlike`
стоит 46.7 / 86.0 /
81.8 мс медианой при пяти обращениях за вызов на 1 000 / 10 000 / 50 000 анкет — замок пары, один
`delete from likes …
returning likes.id` и те же три чтения выжившего списка (`docs/SCALE_PLAN.md`, §«Задержки горячих
путей», артефакты `s120_scale_a.json`, `s120_scale_b.json` и
`s117_compose.json`). Состав окна правка не меняла — меняется только список, который остаётся
после удаления: под этим рядом те же 88 / 894 / 4 494 касания, что и под рядом чтения.

`DELETE /matches/{match_id}` — дверь, которую пара держит без блокировки (стадия 105). Она
снимает строку матча, а с ней по `ON DELETE CASCADE` всё, что под неё цепляется: переписку,
квитанции о прочтении, общие планы и их участников, предпочтения активностей и рекомендации;
строки журнала плана лежат в той же переписке, поэтому отдельного каскада им не нужно.
С нею уходят оба лайка — с одной стороны стены, так что вторым тапом в тот же номер пару не
воскресить: начать заново можно, но только вдвоём, и новая пара при этом рождается под новым
`match_id`. Блок-строки маршрута не появляется, оба профиля остаются видимыми друг другу, а
жалобы, поданные до расторжения, живут дальше: они стоят на номерах людей, а не на строке пары.
Открытые сокеты пары маршрут закрывает тем же `close_room`, что и блок с удалением аккаунта.

`GET /matches/{match_id}` смотрит на собеседника глазами участника пары, а не колоды.
«Скрыть из подбора» снимает анкету из выдачи, с публичной карточки `GET /users/{id}` и с
путей `like`/`pass`, но не стирает матч, который оба уже подтвердили: список пар, история
сообщений и `/compatibility` продолжают его отдавать, поэтому и заголовок пары обязан
отвечать 200, а не «Match not found» под открытым чатом. Из правила колоды здесь исключено
только `is_hidden` — удалённый, деактивированный или не прошедший анкету аккаунт остаётся
недоступен и для того, кто с ним матчился.

`score` совместимости и рекомендаций — процент `0..100`; границы объявлены в выходных
Pydantic-схемах (`CategoryScoreOut.score`, `CompatibilityOut.overall`, `DiscoveryCard.
compatibility`, `LikeResponse.compatibility`, `MatchSummary.compatibility`, `RecommendationOut.score`),
поэтому оценка вне диапазона не уходит на экран, а валится на сериализации ответа.

Процент в списке пар (`/matches`) и в заголовке пары (`/matches/{match_id}`) — тот же, что
считает `/matches/{match_id}/compatibility`. Он хранится на строке матча, но перезаписывается
когда меняется любой из входов движка: после пересдачи теста и после правки
`interests`/`dating_goal` в профиле. До этой правки на одной паре было замерено расхождение
`list=100 single=100 live=46`.

**Сколько стоит список пар.** Карточка пары несёт из переписки две вещи: последнюю строку и
счётчик непрочитанного. До стадии 33 за них отвечали два запроса к одной таблице — `distinct on
(match_id)` приносил самое свежее сообщение каждой пары, а `count(messages.id) … group by match_id`
считал ожидающие, — и оба обходили одни и те же строки по одному и тому же списку id. Теперь это
один `SELECT`: счётчик стал оконным `count(*) filter (…) over (partition by match_id)`, а
PostgreSQL вычисляет оконные функции раньше `DISTINCT ON`, поэтому строку, которую `DISTINCT ON` и
так оставил самой свежей, он приносит вместе с числом ожидающих сообщений. Квитанции присоединяются
по читателю (`message_reads.reader_id`): каждое отправленное сообщение несёт квитанцию своего
автора, и джойн без этого условия снял бы такое сообщение из счётчика собеседника, а развернуться
строке не даёт `uq_message_read (message_id, reader_id)`. Предикаты прежние — `sender_id !=
читатель` и `is_deleted is false`, — поэтому ответ не меняется: пара без сообщений остаётся с
`last_message = null` и `unread = 0`, а удалённое сообщение не становится ни строкой карточки, ни
ожидающим. Слушателем на читателе с тремя парами — 6 обращений стало 5, и чтений `messages` среди
них одно вместо двух; на объёме проба считает 4 наблюдаемых оператора вместо 5, и медиана
29.8 / 37.2 / 34.3 мс против 31.0 / 45.4 / 40.9 мс при 1 000 / 10 000 / 50 000 анкет. Выигрыш по времени утверждается
только на 50 000: на двух меньших масштабах ход нетронутых контролей (−12.2 % у `chat_history` и
−21.8 % у `recommendations`) больше сдвига пути, — пара прогонов одной командой в
`docs/SCALE_PLAN.md`, §«Парные прогоны стадии 33». Держат форму четыре проверки
`tests/test_matches_list_messages_read.py`.

**Как категория отвечает на отсутствие ответа.** Правило одно на все семь категорий и записано оно
в самом движке (`NEUTRAL_SCORE = 0.5`): там, где сравнивать нечего, категория читается нейтрально и
не наградить, не наказать. Интересы держались его до стадии 60 не во всех случаях — пустой набор
интересов у одного из двоих отдавал `0.0` с признаком «данные есть», то есть пропуск шага стоил
ответившему половину веса категории (7…8 пунктов процента), а экран пары называл это расхождение
фразой «Мало общих интересов». Теперь пустой набор у любой из сторон — те же нейтральные 50 без
данных, а два названных непересекающихся набора остаются расхождением и стоят, как стоили. Для
клиента важно другое: с стадии 72 `categories[]` несёт и `has_data`, поэтому `score: 50` больше не
означает одновременно «сравнивать нечего» и «ровно половина совпадения» — экран пары по этому
признаку печатает «нет данных» и не заливает полосу (проверка `CategoryReadoutTest`). Тот же флаг
выходит и на полосах чужой карточки (`GET /users/{id}`), потому что их считает тот же движок и
рисует тот же ряд полос. Прежний снимок: флага в ответе не было, `score: 50` различался только
соседним `shared_interests: []`, и полоса категории, где никто ничего не отвечал, выглядела
измеренной на середине. `engine_version` держит форму результата, а не каждое правило: правка
стадии 60 изменила одно правило и не подняла номер, потому что тот же номер штамповывает
формат сохранённого вектора ответов (`compatibility_profiles.version`), а сохранённый процент пары
(`Match.compatibility_score`) версии не держит — он пересчитывается, когда кто-то из двоих правит
интересы, цель знакомства или пересдаёт тест.

`UniverseOut` — карта пары «два мира»: те же семь полос, но разложенные на узлы с двумя сторонами.
Процент, вес и `has_data` полосы скопированы из `CompatibilityResult` того же движка — маршрут
ничего не оценивает заново, поэтому карта и экран пары не могут рассказать паре два разных числа.
Узел несёт `a_value`/`b_value` (0..1 или `null`, если половина пары этот вопрос не трогала),
`connection` из четырёх слов — `harmony`, `complementarity`, `discussion`, `unknown` — и `evidence`:
строку, которая называет значения именно этого узла, а не соседний текст. Четвёртое слово несущее:
`unknown` означает отсутствие сравнения, и карта не выдаёт его за совпадение. `coverage` полосы —
доля узлов, где сравнение состоялось, — стоит рядом с процентом и не двигает его. Порядок `a`/`b`
взят из самой строки матча (`user_a`/`user_b`), а не от зрителя, поэтому двое открывают одну карту.
Клиент читает этот документ как есть: `presentation/universe/` рисует Canvas по `layers`, подписывает
миры по `a_user_id`/`b_user_id`, а четыре раздела экрана — это четыре слова `connection`, и узел под
тапом раскрывает свою `evidence`. Отдельного числа экран не вычисляет: единственное преобразование —
`(0..1) × 100` над `a_value`/`b_value` того же узла, поэтому у карты и у экрана совместимости под ней
один источник. `evidence` называет те же числа в той же единице: процент, округлённый от половины
в большую сторону — как `roundToInt()` на клиенте, а не как округление Python (0.125 даёт 13, а не 12).
До стадии 75 строка печатала шкалу движка (`0.90 против 0.70`), и пара видела одно и то же значение
в двух единицах внутри одного жеста.

Узел отвечает и на три вопроса, которые тап оставлял открытыми: насколько этому верить, что с этим
делать и чем это измерено. `confidence` — расстояние сходства до границы той полосы, которая его
распустила, нормированное на ширину этой полосы: 0 значит «ещё шаг, и узел читается другой связью»,
100 — «иначе этот ответ не читается». Полосы меряются каждая по своей ширине, поэтому 100 в harmony,
в complementarity и в discussion означает одно и то же; `unknown` сравнивать нечего, и он не имеет
права быть уверенным — 0. `confidence` полосы — среднее по узлам, где сравнение состоялось, и полоса
без таких узлов читает 0, а не выдуманный оптимизм. `suggestion` собрана из низких и высоких меток
самой таксономии для этих двух ответов (`traits.describe_side` — одна функция на карту и на экран
совместимости, чтобы один ответ не назывался двумя словами) и не печатает ни одного числа: числа
остаются за метками. Это продуктовое предложение («обсудите», «пусть каждый приносит свою сторону»),
не утверждение о том, как устроены отношения. `questions` — пункты анкеты, чьи варианты и дали ответ
на этой оси; каталог импортируется, а не читается из базы, поэтому пять обращений за вызов остаются
пятью. Интерес и цель — выбор из онбординга, а не измеренная ось, поэтому у них нет вопроса: поле
пустое, а не выдуманное.

`story` — тот же документ, рассказанный словами, которые пара может отправить наружу. Строки
собирает движок из одних агрегатов: итог пары, процент полосы (только когда `has_data`), её вес и
сколько пунктов полосы действительно сравнили, разложенные по трём словам связи — `unknown` в этом
счёте отсутствует, потому что там сравнения и не было. Ни одного названия оси и ни одного
`a_value`/`b_value` здесь нет: метка узла — это и есть чей-то ответ, а этот текст уходит за пределы
приложения, куда дефект 72-1 доехал бы быстрее всего. Полоса без сравнения поэтому называется словами,
но остаётся без процента. Порядок строк — по весу полосы, а не
по тому, кто открыл карту: документ парный, и история, которая начинается по-разному для двоих, была
бы вторым зеркалом. Клиент к этим строкам не добавляет ни числа, ни имени: перед `ACTION_SEND` экран
кладёт рядом с ними только заголовок и оговорку, а имена миров в текст шаринга не попадают.

`reasons` — это и есть обещание экрана «почему именно этой паре», и держит оно слово, а не шаблон.
Полоса печатает строку только там, где данные пары сами её говорят: ось досуга или образа жизни
называется, когда обе половины и сигнал самой идеи отвечают на ней одной стороной (сторону называет
`describe_side` — тот же, что у карты пары и разбора совместимости); interests-полоса различает
тег, выбранный двоими, и тег, выбранный одним из них, потому что второй двигает 0.4-е слагаемое этой
полосы и без строки карточка теряла бы объяснение очков, которые уже взяла; город отвечает «в вашем»,
«в ваших» или «в городе одного из вас» по фактическому числу совпадений; цель знакомства различает
одну названную цель и две не расходящиеся. Молчание остаётся молчанием: половина, не назвавшая цель,
не получает за это ни пунктов, ни строки, и карточка, которой нечего сказать про эту пару, приходит с
пустым `reasons` — это отсутствие факта, а не отсутствие места. Одна полоса даёт не больше одной
строки, и строка эта выбрана детерминированно (ось, на которой идея отвечает резче всех, при равенстве
— по ключу), потому что страница хранится и читается дважды. Связь этого образца с движком держит
`tests/test_an_explanation_has_to_name_the_pair_not_the_threshold.py`: она собирает карточку по тем же
тегам, городам и ответам и требует, чтобы `score` и все четыре строки были ровно напечатаны.

Когда же ни одна ось не собрана в согласие, полоса молчала не потому, что факта нет, а потому, что
факт был другой: две половины отвечали на оси, которую идея сама называет (`energy` — это
`outdoor` и `relaxation`, `social` — `social_leisure`), с противоположных названных сторон, а
процент карточки есть среднее двух совпадений, то есть число, которое одна из половин принесла идее,
а вторая — нет. С стадии 85 такая карточка печатает разногласие и своё место на нём: «Социальный
досуг: вы на разных сторонах — «в больших компаниях» против «один/вдвоём», идея ближе к «в больших
компаниях»», при равном удалении — «идея посередине между вами». Сторону по-прежнему называет
`describe_side`, сторона названа, а человек — нет: страница одна для двоих, и из неё нельзя понять,
кто из пары ответил 0.95, а кто 0.05. Ответ «умеренно» не противоположен ничему, поэтому карточка
с одной неназванной стороной остаётся без строки, как и до правки, а согласие пары про ту же идею
по-прежнему важнее разногласия: на карточке печатается одна строка, и выбранная согласием полоса не
уступает разногласию. Съём на стенде (те же две пары, что мерили стадию 81, 16 карточек, движок до
правки и после, — `s85_real_pairs_before.log` и `s85_real_pairs_after.log`): строку разногласия
получили 4 карточки из 16, карточек без строки по досугу стало 5 вместо 9, а все 16 процентов совпали
с точностью до цифры. Держат это семью проверками
`tests/test_an_idea_built_on_a_pair_that_disagrees_says_which_end_it_sits_on.py`; две из них
держат число, снятое с прежнего движка, — текст двинулся, счёт карточки нет.

`selected` отвечает на вопрос зрителя, а не пары: «я уже предлагал(а) этой паре эту идею или нет».
Оба читают один и тот же сохранённый набор карточек, но отметка принадлежит тому, кто нажал,
поэтому у собеседника та же карточка остаётся `false`. До стадии 63 поля не было: нажатие
записывалось в `activity_preferences` и никем не читалось, так что экран не помнил выбор между
двумя открытиями вкладки.

`partner_selected` отвечает на второй вопрос той же таблицы — «а эту идею уже предложил(а)
собеседник». До него страница читала строки пары фильтром по зрителю и второй половины касалась
молча: совпадение выборов выглядело на обоих экранах как предложение одного и молчание другого.
Скрытого тут ничего не вскрывается: строка `activity_preferences` — это то же, что читается
карточкой плана в чате этой пары, а читают её только те двое, кого `_require_match` пускает в
`match_id`. Обе отметки приходят из одного `SELECT activity_preferences` (стадия 63 измеряла им
страницу в пять обращений на тёплом пути), поэтому поле не стоит маршруту ни одного лишнего
round-trip. Клиент на `partner_selected` меняет только подпись действия: кнопка становится
«Поддержать в чате», а тап за ней — тот же один `select`, который вынес идею паре в первый раз.
С стадии 95 экран не дописывает в чат никакого предложения: идею приносит в переписку сам план,
журнал которого тот же `select` и пишет — в своей транзакции (`plan_proposed`, а когда за идею
держатся обе половины — `plan_accepted`).

`declined` — третий ответ того же зрителя: «я отклонил(а) эту идею». До него строка
`activity_preferences` умела означать только согласие, и «не подходит» было некуда записать:
карточка возвращалась на страницу при каждой новой сборке, а человек, который уже решил, что идея
ему не подходит, читал её снова. Ответ живёт в той же строке отдельным флагом, а не вместо
`proposed`: идея, ушедшая в чат и потом отклонённая, остаётся и тем и другим — свёртка в один флаг
вернула бы дефект стадии 63, где карточка предлагалась повторно. Отклонённая карточка не
выбрасывается из ответа: она остаётся в `recommendations` со своим `score` и `reasons`, чтобы
отказ было кем отменить.

Отвечается он только для зрителя, как `selected`, и поле для собеседника заведено не было. Разница
между двумя отметками — в том, что они уносят из этого экрана: предложение уже лежит в чате пары,
поэтому назвать его — не открыть ничего нового; отказ никуда не уходит и остаётся правкой личного
списка. `POST` и `DELETE /matches/{match_id}/recommendations/{activity_id}/decline` — две записи
одного решения, а не флаг на маршруте `select`: нажатия означают для пары противоположное, и
обслуживающий код читает их двумя разными запросами. Оба пишут по той же парной блокировке, что и
`select` (стадия 14), поэтому распад пары за спиной запроса отвечает `404`, а не `500`.

Записи держат флаги раздельно: `set_declined` на конфликте обновляет только `declined`, поэтому
отказ не стирает то, что идея уже уходила в чат, а новый ряд отказа не предлагает идею сам
(`proposed=false`). Карточка, у которой оба флага истинны, — это не противоречие, а два факта об
одном решении: идея в переписке осталась, а человек её больше не хочет. Обратное направление —
`set_preference` — с стадии 107 снимает `declined`: тап «поддержать» на карточке, которую человек
уже отклонял, есть смена собственного ответа, а отказ, оставшийся под свежим подтверждением, читался
бы парой как «вы отклонили» про человека, который только что нажал «подтвердить». Держит это
`test_the_half_that_confirmed_can_still_say_no` рядом проверок о том, кто что читает, и
`test_an_idea_already_proposed_keeps_its_proposal_after_being_pushed_away`, где два тапа теперь
идут в том порядке, в котором человек передумывает.

Четыре поля времени — последний глагол §81: у пары есть идея, есть переписка, и до этой правки не
было момента, когда под этой идеей встретиться. Хранятся они в той же строке
`activity_preferences` двумя `timestamptz`, и каждая принадлежит своему человеку: `meeting_time` —
когда встретиться готов автор строки, `accepted_time` — на что он согласился, а это всегда имя
собеседника. Поэтому и в ответе четыре поля читаются со стороны зрителя, как `selected`: у одной
половины карточка показывает `my_meeting_time`, у другой то же самое имя лежит в
`partner_meeting_time`.

Договорённость — не третье состояние, а сверка двух строк: она есть, когда `accepted_time` одного
совпадает с `meeting_time` другого, и тогда `agreed_time` заполнен у обоих одним и тем же
мгновением. Отсюда два следствия, которые держат тесты. Если пара обменялась предложениями — один
назвал 19:00, его приняли, потом второй назвал 20:00 и согласился уже на него, — строки поддерживают два
непротиворечивых прочтения, и `agreed_time` остаётся пустым у обоих: распечатать более раннее
означало бы выдать обещание, которого ни у кого из двоих нет. И если автор имени двигает час,
согласившаяся сторона видит свой `i_accepted_time` на месте, а `agreed_time` гаснет: строка честно
помнит, на что человек соглашался, а пары у этого часа больше нет.

`when` в теле обязателен с offset (`AwareDatetime`), и равны сравниваются мгновения, а не строки:
Казань и Новосибирск договариваются об одном моменте, и тот же момент, записанный как `+03:00`,
принимается вместо `+00:00` без `409`. В ответе тот же миг отдаётся в UTC. Вперёд пускают на 400
дней, назад — на 15 минут; последние — допуск на часы телефона, а не правило продукта.

Согласие не является предложением. Строка, которую пишет `accept`, ставит `proposed=false`, иначе
второй половины досталась бы отметка «выбрали эту идею» за касание, которое ничего в чат не носило, —
дефект, закрытый стадией 63. Обратное верно для отказа: назвать час или согласиться на него значит
заняться идеей, поэтому оба маршрута снимают `declined` с той стороны, чья это строка.

Маршрут имени — `PUT`, а не `POST`: на человека и карточку в паре приходится одна строка, поэтому
второе касание заменяет названный час, а не даёт собеседнику два, между которыми приходится
выбирать. Оба пути берут парную блокировку (`lock_pair`) и перепроверяют, что матч жив, — та же
защита, что у `select`, `decline` и чата: строка предпочтения ребёнок матча, и касание, пришедшее
после распада, отвечало бы `500` вместо `404`.

Стоимости для экрана новые поля не добавили: оба часа читаются тем же единственным
`SELECT activity_preferences`, который приносит `selected`, `partner_selected` и `declined`,
поэтому тёплая страница остаётся в пяти обращениях, и это проверяется инвариантом round-trip'ов.

Доступ к матчу имеют только его участники; иначе `404` с `error.code = "not_found"` — ровно так
же, как отвечает маршрут о несуществующей паре. `403` здесь означал бы «такая пара есть, но не
твоя», то есть был бы оракулом для перебора id, поэтому ни один маршрут с идентификатором пары
его не возвращает.

**Сколько стоит экран совместимости.** Пара — это два человека, а забот, из которых складывается
процент, три: анкета, список интересов и вектор ответов. До стадии 25 каждый из двоих читался по
своему обращению на заботу, то есть шесть чтений на двоих там, где хватает трёх пачек по два id;
свежая пара давала `GET /matches/{match_id}/compatibility` в девять обращений, теперь шесть. Тем же
почерком написана инвалидация процента (`refresh_pair_scores`): `PATCH /users/me` с городом на
аккаунте с одной парой — 15 обращений стало 12 на стадии 25, 11 стало 7 на стадии 35 (стадия 29
сняла между ними ещё одно чтение, 12 → 11), 7 стало 6 на стадии 36 — там снято второе чтение
строки анкеты; `POST /tests/complete` на том же аккаунте — 18 стало 15 (число стадий 22 и 25, этой
стадией не переснималось и не сдвинулось бы: анкету он не пишет), а правка одного поля `name`,
которое веер не запускает, — 6 стало 5 (стадия 36).
Город из триггеров пересчёта вынесен вовсе: процент движок строит из вектора ответов, набора
интересов и цели (`app/compatibility/engine.py:19`), и правка одного города больше не является
поводом перечитывать пары (стадия 35, `CHANGELOG.md`). Пачка, в отличие
от прежнего одиночного чтения, берёт только живые аккаунты, и отсутствие одной из половин движок
читает как `not_found`, а не как процент по пустой анкете; на ходу это не встречается — строка матча
уходит при чистке удалённого аккаунта, и маршрут не доходит до движка. На объёме те же три чтения
против шести и медиана 21.5 / 21.5 / 21.1 мс против 31.9 / 32.9 / 32.1 мс при 1 000 / 10 000 / 50 000
анкет — пара прогонов одной командой в `docs/SCALE_PLAN.md`, §«Парные прогоны стадии 25».

**Сколько стоит заголовок пары.** `GET /matches/{match_id}` показывает того же собеседника и тот
же процент, поэтому и строит входы движка так же — по анкете, списку интересов и вектору ответов
каждого из двоих. До стадии 30 он поднимал их поодиночке: анкета собеседника шла по правилу
участника пары, анкета зрителя — из построения его входа, интересы каждого вторым чтением, и оба
вектора — двумя запросами по одному id. Слушатель `before_cursor_execute` на свежей паре дал такому
запросу 10 обращений, теперь 7: анкеты обоих читаются одним `SELECT` с условием
`user_id = <зритель> or (user_id = <собеседник> и правило участника пары)`, интересы обоих — одним
запросом по двум анкетам, векторы — одним `compatibility_profiles.user_id in (…)` на двоих. Правило видимости осталось у своей
половины: «Скрыть из подбора» по-прежнему не стирает пару, которая уже сказала «да», — это
охраняет отдельная проверка набора. Контроли того же прогона не сдвинулись: карточка по правилу колоды (`GET /users/{id}`)
осталась на 9 обращениях, экран совместимости той же пары — на 6, список пар — на 6, собственная
карточка — на 6. На объёме те же пять чтений против восьми и медиана 47.1 / 38.0 / 44.5 мс против
53.8 / 52.8 / 53.4 мс при 1 000 / 10 000 / 50 000 анкет — пара прогонов одной командой в
`docs/SCALE_PLAN.md`, §«Парные прогоны стадии 30»; выигрыша по времени этот прогон не утверждает,
и почему — записано там же. Те 9 обращений карточки, оставленные этим прогоном, сняла стадия 31 —
абзац ниже.

**Сколько стоит карточка по правилу колоды.** `GET /users/{id}` — та же ветка того же сервиса, что
и заголовок пары, только зрителю показывают незнакомца из колоды, а не собеседника из `matches`.
Правило здесь другое: `is_hidden`, живой аккаунт и пройденный онбординг, собранные в
`_showable_conditions`, — профиль, спрятавший анкету, отключённый и не дошедший до конца
регистрации дают незнакомцу тот же 404, что и маршруту лайка. До стадии 31 анкета собеседника
приносилась этим правилом по одному id, а анкета зрителя — вторым обращением к `profiles` из
построения его входа совместимости, списки интересов обоих шли вместе с каждой строкой отдельно, и
оба вектора ответов — двумя запросами по одному id. Слушатель `before_cursor_execute` на паре
незнакомцев дал такому запросу 9 обращений, теперь 6: анкеты обоих читаются одним `SELECT` с
условием `user_id = <зритель> or (user_id = <собеседник> и правило колоды)`, интересы обоих — одним
`profiles_1.id in (…)` от того же загрузчика, векторы — одним `compatibility_profiles.user_id in (…)`
на двоих. Скобок вокруг `or` в условии нет, и `and` связывает сильнее, поэтому фильтр колоды
относится только к половине собеседника: половина зрителя читается безусловно — ровно как до правки,
где его анкету поднимал тот же безусловный `get_profile`, так что проверка видимости не
ослаблена. Правило пары в карточку не перенесено намеренно, а правило колоды — в страницу пары:
«Скрыть из подбора» снимает незнакомцев из колоды, а не пару, которая уже сказала «да», — каждое из
этого держит отдельная проверка. Дороже стал отказ: карточка спрятанного профиля до правки стоила
два обращения, теперь три — загрузчик приносит список интересов зрителя вместе с его строкой до
того, как ветка узнает, что собеседника нет. Принятие стоит шесть, и снять из них больше нельзя:
чтение аккаунта из проверки токена, проверка блокировки между этими двоими, фотография собеседника
и три пачки по два id. На объёме те же пять чтений против восьми и медиана 39.5 / 34.6 / 36.1 мс
против 51.3 / 55.3 / 58.3 мс при 1 000 / 10 000 / 50 000 анкет — пара прогонов одной командой в
`docs/SCALE_PLAN.md`, §«Парные прогоны стадии 31»; в отличие от трёх предыдущих стадий этот прогон
утверждает и задержку, потому что контроль `chat_history` за тот же вечер сдвинулся на +6.6 / −0.5 /
−12.4 % — меньше по модулю, чем сдвиг пути, а на 1 000 ещё и в противоположную сторону.

**Из чего складывается `score` карточки.** Пять компонент с весами 0.40 (интересы), 0.20 (досуг),
0.15 (образ жизни), 0.15 (город) и 0.10 (цель знакомства), сумма — 100, и interests-компонента
делит покрытие карточки на длину её собственного списка тегов. Отсюда граница ответа, о которой
клиенту стоит знать: тег, которого нет в каталоге интересов, не может оказаться в числителе, и
карточка с ним держится ниже своего потолка для всех пар сразу — на 20 пунктов из 100 там, где из
двух тегов живым был один (`volunteering`), на 13 там, где один из трёх, на 10 там, где один из
четырёх. Именно эта карточка на запросе, где двое назвали всё, что она перечисляет, возвращалась
с 71 из 100. Стадия 61 сняла семь таких тегов из каталога (`nature`, `food`, `art` — названия групп
интересов, записанные там, где ожидался slug), и тот же запрос теперь отдаёт 91; держалась эта
разница не на ответах пользователя, а на строке каталога. Форма ответа от этого не изменилась ни на одном поле: `interests` карточки ни
один маршрут не отдаёт, `ActivityDto` на Android его не читает. Клиенту правка видна только числом и
порядком: мёртвый тег никогда не попадал в `shared_both`, из которого движок собирает `reasons`,
поэтому текст «Общий интерес — …» он не менял — меняются `score` и, сверху восьми карточек,
состав и порядок страницы.

**Сумма весов теперь проверена, и вот что она держит.** `score_activity` складывает пять
взвешенных компонент и отдаёт сумму в `_clamp01`, поэтому верх страницы — это ровно сумма весов,
0.40 + 0.20 + 0.15 + 0.15 + 0.10 = 1.0. Для рекомендаций это нигде не проверялось, хотя у
соседнего движка проверка есть: `app/compatibility/weights.py` вызывает `WeightConfig.validate()`
при импорте и отвергает набор, где семь весов расходятся с 1.0 больше чем на 1e-6. Молчание
работало в обе стороны и по-разному. Убрать вес — опустить потолок: замерено на прежнем движке
`leisure` 0.20 → 0.05 даёт паре, совпавшей со всеми пятью компонентами, 0.85, то есть 85 из 100, а
`goal` 0.10 → 0.00 — 0.90 и 90. Поднять вес — перестать поломку видеть: `interest` 0.40 → 0.50
(сумма 1.10) на том же прежнем движке отдаёт те же 1.0 и 100, потому что `_clamp01` насыщает сумму,
и по числам страницы расхождение незаметно вовсе. С этой стадии пять весов лежат в одном словаре
`WEIGHTS`, `validate_weights()` вызывается при импорте, и движок с неверной суммой не поднимается;
выбор весов в одном месте — не косметика, а та же причина: у правки, которую проверка уже прочла,
не должно оставаться дороги в число. Форму и числа страницы правка не изменила: те же четыре файла
проверок (`test_recommendations.py`, `test_engine_determinism.py`, регрессии стадий 61 и 68) дают
27 passed в 38.72 с (прогон 18:55:50…18:56:34 UTC, артефакт `s68_group_final.txt`), включая потолок
100 для полностью совпавшей пары и ровно 40 пунктов разницы между парой, назвавшей все теги
карточки, и парой, не назвавшей ни одного.

**Порядок пересборки страницы.** `?force=true` пересчитывает и перезаписывает страницу, а без него
ответ читается из `recommendations` — то есть карточка, сохранённая до правки каталога, держит своё
прежнее число, пока её не пересобрать. Миграция `7c4f2a91be36` меняет строки `activities` и не
трогает сохранённые страницы: на рабочей базе после апгрейда 25 пар, 16 сохранённых карточек на двух
из них, и 4 из этих 16 — перетегибанные этой стадией активности. Их interests-компонента в
сохранённом `score` осталась 0.4667 там, где движок теперь считает 0.7000 (`hiking_trip`), 0.2000
против 0.4000 (`volunteering`), 0.3333 против 0.5000 (`cooking_class`) и 0.2000 против 0.2667
(`picnic`), то есть 0.0267…0.0933 от общего числа; по самому ответу нельзя сказать, с какой стороны
ревизии оно посчитано.

**Сколько стоит страница.** Без `force` ответ лежит в `recommendations`: карточки читаются одним
обращением к этой таблице и одним — к каталогу `activities`, и вместе с чтением аккаунта и пары
это пять обращений: пятым стадия 63 добавила одно чтение `activity_preferences`, которое и отвечает,
какие из этих карточек зритель уже предлагал. `?force=true` пересобирает страницу: анкета и вектор
ответов каждого из двоих берутся одной пачкой на двоих, восемь карточек пишутся одним `INSERT`, а
ответ собирается из записанных значений и того же прочитанного каталога — обратно страницу никто не
читает. Замер слушателем `before_cursor_execute` на свежей паре: 16 обращений стало 11 на стадии 24,
стадия 63 добавила к этой сборке то же одно чтение отметок — 12; из них ровно одно читает
`recommendations` (проба кэша), одно — `activities` и одно — `activity_preferences`, а не по чтению
отметок на карточку. На объёме те же восемь чтений против тринадцати и медиана 58.0 мс против
82.8 / 80.6 / 81.9 мс при 1 000 / 10 000 / 50 000 анкет — пара
прогонов одной командой в `docs/SCALE_PLAN.md`, §«Парные прогоны стадии 24». Эти три числа сняты тем
деревом и не пересняты: стенд не засевает `activity_preferences` вовсе (`select count(*) from
activity_preferences` на `befos_scale` даёт 0 при 50 001 анкете, а `_seed_activity` прогона пишет
только `matches`, `messages` и `passes`), так что добавленным чтением на объёме было бы измерение
пустой таблицы по индексу.

## Chat

| Метод | Путь | Query / Тело | Ответ |
|-------|------|--------------|-------|
| GET | `/matches/{match_id}/messages` | `limit` (1..100), `before_id` | `{messages: [MessageOut], has_more}` |
| POST | `/matches/{match_id}/messages` | `{body, client_msg_id?}` (body 1..4000, id ≤ 64) | `201` `MessageOut`; повтор с тем же `client_msg_id` → `200` тот же объект |
| POST | `/matches/{match_id}/read` | — | `{marked_read: N}` |
| DELETE | `/matches/{match_id}/messages/{message_id}` | — | `204` пустое тело; `404` `Message not found.`, если строка не этого аккаунта, уже отозвана или набрана не человеком |

Сообщения, отправленные через REST, отметки о прочтении и отзывы строк дополнительно транслируются
в WebSocket матча (`type: message` / `type: read` / `type: message_recalled`), поэтому подключённый
второй клиент получает их без повторного запроса истории.

`client_msg_id` — имя, которое отправитель даёт своей отправке. POST, ответ на который не дошёл,
неотличим от POST, который отказали, поэтому повтор без имени записывает вторую копию того же
предложения. С именем на `(match_id, sender_id, client_msg_id)` в БД стоит частичный уникальный
индекс: повтор возвращает уже сохранённое сообщение, а analytics-событие и трансляция в комнату
идут только на первую запись. Имя необязательно: отправку без имени нельзя отличить от
намеренного повтора текста, и она пишется как обычное сообщение. `client_msg_id` длиннее 64
символов — `422` на REST и `type: error` в сокете (сокет остаётся жив).

**Своя строка отзываема.** `DELETE /matches/{match_id}/messages/{message_id}` заканчивает одно
набранное человеком предложение: строка помечается `is_deleted`, её текст стирается в `""`, а
`client_msg_id` с неё снимается — `find_by_client_id` не фильтрует отозванные строки, и ключ,
оставленный на мёртвой, вернул бы более позднему повтору её же как ответ. Условие одного `UPDATE`
(`id` + `match_id` + `sender_id` + `kind = 'text'` + `is_deleted IS FALSE`) и есть всё разрешение:
второй тап по уже отозванной, чужая строка, страница журнала плана и отсутствующий id отвечают
одним и тем же `404` и ничем не различимы, чтобы отказ не стал оракулом над строками, которых
этому аккаунту не видно. Маршрут стоит за тем же допуском, что и отправка
(`_require_membership_for_write`), поэтому чужая пара не получает ни отзыва, ни кадра. Пустой `204`
ничего не называет, а трансляция комнаты `{ "type": "message_recalled", … }` убирает строку с обоих
открытых экранов — и с того, где по ней ударили, и со второго устройства этого же аккаунта. Держат
поведение двенадцать проверок
`backend/tests/test_a_person_takes_back_a_line_they_typed.py` (съём `s111_backend_newfile.log`,
`12 passed in 70.61s`, прогон 17:28:09…17:29:28 UTC 2026-10-19, база `befos_s111nf`, дерево
`cb08643`); красной эта дверь стояла до своего маршрута — `s111_red_message_delete.log` (прогон
15:08:10…15:08:21 UTC 2026-10-19, стенд `befos`, дерево `e45811a`) отвечала `404` на все восемь
подозреваемых дверей отзыва, когда своя строка уже лежала в паре, а история после пробы осталась
прежней.

`MessageOut`:

```json
{
  "id": "uuid", "match_id": "uuid", "sender_id": "uuid", "body": "…",
  "created_at": "ISO-8601", "is_read": false, "is_own": true, "client_msg_id": "local-uuid",
  "kind": "text", "plan": null

```

**Договорённость пары — строка в той же переписке.** `kind` принимает `text` (предложение, которое
кто-то набрал) и девять строк журнала плана: `plan_proposed` (идею вынесли паре), `plan_accepted`
(оба за неё), `plan_declined` (её оттолкнули), `plan_agreed`, `plan_rescheduled`, `plan_changed`,
`plan_cancelled`, `plan_completed` и `plan_voided` (согласованный час снят, и пара стоит без
договорённости). У строк журнала заполнен `plan`:

```json
{
  "kind": "plan_agreed",
  "plan": {
    "plan_id": "uuid", "activity_id": 7, "activity_title": "Поход в кино",
    "when": "2026-10-17T16:00:00Z", "is_latest": true
  }
}
```

`plan_id` — та же сущность, что отвечает в списке планов (§«Планы пары»), поэтому карточка в чате
доводит человека до плана, а не до его пересказа. `activity_id` — FK на каталог с
`ON DELETE SET NULL`, поэтому идея, которую каталог потерял,
отвечает `null` здесь и в `activity_title`, а `body` остаётся читаемой фразой; `when` — тот же
миг, что лежит в парной строке предпочтения, отдан в UTC. `is_latest` считается не по строке, а по
всей переписке: `false` у обеих сторон означает, что более поздний журнал эту договорённость уже
снял, поэтому старая страница истории не выдаёт за живую обещание, которого пара больше не держит.
Места в модели активности нет ни в базе, ни в ответе, ни на карточке — с стадии 95 адрес есть у
плана пары (`place` в §«Планы пары»), и пока никто из двоих его не назвал, он `null`.

Оба поля добавлены с дефолтами (`kind = "text"`, `plan = null`), и сборка клиента, которая журнала
ещё не знает, читает такие ответы как обычные сообщения. Кадр `type: message` в сокете несёт ровно
те же ключи — за это отвечает общий `message_frame`, поэтому история и живое сообщение расходятся
только если разойдётся код, а не контракт.

Журнал пишется в той же транзакции, что и час, под уже взятой `lock_pair`, и это разница состояний,
а не счётчик нажатий: `_journal` сверяет `_Hour` (согласованный и спрашиваемый момент) строки плана
до правки и после неё, а `_newest_last` помечает `is_latest: true` только у последней строки одного
тапа. Отсюда четыре следствия, которые держат
`backend/tests/test_the_hour_a_pair_agreed_on_is_said_in_their_chat.py`. Повтор запроса после
потерянного ответа ничего не меняет и не оставляет второй строки. Согласие на час, который пара уже
переторговала, плана не создаёт и в чат ничего не пишет, — иначе переписка сообщила бы о
договорённости, которой ни у кого из двоих нет. Ход, который переносит уже согласованный момент,
даёт две строки по порядку: `plan_voided` прежнего часа, потом `plan_rescheduled` нового — вопрос,
на который вторая половина ещё не ответила. Тап, который выносит идею паре, даёт `plan_proposed`, и
он не называет договорённости: до ответа второй половины часа, о котором пара стоит, не существует.

Час, который уже прошёл, журнал не трогает. `agreed_instant` сверяет только сами мгновения и в
часы не смотрит, поэтому `plan_agreed` с `is_latest: true` и `agreed_time` на карточке переживают
этот час ровно в той же форме: сервер не вправе объявить обещание кончившим, потому что такое
событие не подтвердил никто из двоих. То, что договорённости пора уступить место новой, читает
клиент по своим часам — а молчание сервера держит
`test_an_agreement_whose_hour_has_passed_is_still_the_agreement`, которая называет час двумя
сутками раньше через подменённые часы сервиса, а потом читает и переписку, и страницу идей уже на
живых часах. Прошедший момент по-прежнему отвергается на записи (`validate_meeting_time` из
`app/services/plan_time.py`, тот же `MIN_LEAD`), поэтому карточка, у которой час позади, не
предлагает его повторно, а ведёт к новому.

Страница истории дорожает ровно на тех страницах, где журнал есть. `ChatService.history` поднимает
актуальность одним `DISTINCT ON` (`latest_plan_events`) и читает каталог пачкой по id из строк
журнала — два обращения, и оба только когда на странице нашлась хоть одна строка плана: страница из
сообщений, которые пара набрала, идёт прежним кругом.

Все двери часа (`PUT …/recommendations/{activity_id}/time`, `POST …/time/accept` и
`POST /plans/{plan_id}/hour`, `POST /plans/{plan_id}/hour/confirm`) остаются `204`: кадр в комнату
идёт после коммита из общего `message_frame`, поэтому второй половине не приходится перечитывать
историю, чтобы увидеть договорённость. С стадии 95 так же отвечают и двери самого плана —
`select`, `decline` и снятие отказа на странице идей, а на детали плана приём, отказ, перенос,
отмена и завершение (`app/api/v1/plans.py`, общий `_broadcast` после коммита). Двери разные, а
правило одно — строку плана пишет `PlanService`, и с любого экрана это один и тот же `plan_id`.

**Сколько стоит отметка о прочтении.** Открытие переписки — с очередью и без неё — стоит
слушателю `before_cursor_execute` шесть обращений; восемь были до стадии 32, семь — между
стадиями 32 и 50. Прежний `mark_read` приносил список
непрочитанных id в Python и отправлял те же id обратно в `INSERT` — по четыре параметра на сообщение,
два круга к базе. Теперь это один `INSERT … SELECT`: `id` считает `gen_random_uuid()`,
`ON CONFLICT DO NOTHING` опирается на `uq_message_read`, а `RETURNING id` отдаёт число строк,
записанных именно этим вызовом — по нему идёт `marked_read` и рассылка «прочитано» в сокет.
Прямое сравнение двух форм против той же базы на 10 000 анкет (60 чередующихся повторов): 4 ожидающих
сообщения — 7.885 → 5.546 мс, 12 — 11.674 → 8.929 мс, 120 — 33.090 → 29.079 мс, и круг с двух стал
один; когда отмечать нечего, прежний код выходил до вставки, поэтому там правка не убрала
обращение, а заменила читающий оператор пишущим — плюс 0.056…0.085 мс. Число обращений при этом
не изменилось: открытие прочитанного чата — 7 и 7 (с стадии 50 это уже шесть, см. ниже), `POST /read`
на пустой очереди — 5 и 5. Парный прогон стенда выигрыша по времени не утверждает (медиана пути
31.7 / 30.9 / 30.8 → 34.2 / 37.1 / 39.1 мс при
нетронутых контролях того же порядка); числа двух половин, таблицы слушателя и оговорка про счётчик
пробы — в `docs/SCALE_PLAN.md`, §«Парные прогоны стадии 32». Держат форму четыре проверки
`tests/test_chat_receipt_roundtrips.py`, а гонку с распавшейся парой —
`tests/test_read_receipt_into_dissolved_match.py`.

**Чем история пары платит за отметку «прочитано».** Седьмое обращение из абзаца выше держалось не за
`mark_read`, а за чтением страницы: `ChatRepository.list_messages` поднимал коллекцию `Message.reads`
вторым запросом (`selectinload`), а `ChatService._to_dto` сокращал её до одного булева на строку. На
стенде стадии 50 (переписка в 500 строк, страница в 50, 40 500 отметок в таблице) этот запрос нёс 51
параметр и привозил 76 строк, чтобы ответить пятьюдесятью булевыми значениями. Теперь флаг —
коррелированный `EXISTS (SELECT message_reads.id … AND message_reads.reader_id <> messages.sender_id)`
в тексте того же чтения, которое выбирает страницу, и отдельного запроса к `message_reads` на
открытии нет (слушатель: 7 → 6 обращений на обеих формах открытия; `POST /read` правка не касается,
она в чтении). Парный прогон трёх форм на том же стенде (10 000 анкет, девять повторов, первый
отброшен, сессия на каждый вызов): открытие прочитанной переписки — медиана 42.5 → 32.2 мс при ходе
нулевого контроля 0.2 мс и разнице слотов 32.2 против 32.0 мс, открытие с очередью — 91.6 → 83.8 мс,
где контроль ушёл дальше пути (−9.4 % против −8.5 %) и потому о времени ничего не говорит; отличий
ответа — ноль в обоих сценариях. Сервер при этом не разгружается: сумма планов двух прежних чтений
страницы — 1.22 мс, нового одного — 1.19 мс, и снимается именно разговор с базой вместе со сборкой 76
объектов ORM (время вызова вне засечённых обращений: 24.04 → 17.09 мс). Условие
`reader_id <> sender_id` здесь не косметика: каждое отправленное сообщение несёт квитанцию
своего автора
(`_note_read_by_sender`), и наивный `EXISTS` показал бы человеку «прочитано» на его же строке до того,
как переписку открыл собеседник. Отвечает страница состоянию до той отметки прочтения, которую это же
чтение ставит (стадия 37), — семантика после правки не двинулась. Держат её пять проверок
`tests/test_chat_page_receipt_flag.py`, а опущенный этой стадией потолок открытия с очередью —
`tests/test_chat_receipt_roundtrips.py`; красное состояние на прежнем дереве — `3 failed, 6 passed`.
Числа пары, план и оговорки — в `docs/SCALE_PLAN.md`, §«Парные прогоны стадии 50».

**Что страница обязана держать свою верхнюю строку.** У курсора есть контракт, и с этой стадии он
держится кодом: `GET /matches/{match_id}/messages?limit=N&before_id=…` отвечает `N` самых свежих
строк окна по возрастанию, а `before_id` следующего обращения — id самой старой строки этой
страницы. До стадии 53 `ChatService.history` оставлял `lines[:limit]`, тогда как `list_messages`
возвращает окно развёрнутым — по возрастанию (`rows.reverse()`,
`backend/app/repositories/chat_repo.py:152`), — и срез по началу списка отрезал не «лишнюю» строку,
а верхнюю: прочитанное окно в `limit + 1` строк отвечалось `limit` самыми старыми, а следующая
страница начинается строго ниже самой старой показанной (`WHERE created_at < anchor.created_at`),
поэтому отрезанная строка не попадала ни на одну. Замер на сокетном стенде (отдельная база `befos_s53`,
200 анкет, пара, созданная через `POST /users/{id}/like`, переписка в 70 строк, `s53_page_pre.json`):
обход курсора при `limit=5` — 59 строк из 70, ни одной повторной, 11 строк не показались никогда, а
самой свежей строки не было на первой странице; при `limit=50` экран отдаёт 50 строк и заканчивает
`sequential-8`, тогда как последняя строка таблицы и подпись карточки в `GET /matches` —
`sequential-9`. После правки (`lines[-limit:]`, `backend/app/services/chat_service.py:79`) тот же
обход даёт 70 строк из 70, ноль потерянных, самая свежая строка на первой странице, а карточка и
экран называют одну и ту же строку (`s53_page_fixed.json`). Правка — срез на стороне Python: текст
чтения страницы, число обращений к базе и его план не изменены, и контроль слушателем
`before_cursor_execute` зелёный на обоих деревьях (не больше шести обращений на открытие прочитанной
переписки, отдельного чтения `message_reads` нет). Полный обход той же переписки стоит 15 обращений
вместо 13 — именно потому, что 11 строк, которых раньше не было ни на одной странице, теперь на них
лежат. Гипотеза, из-за которой эту правку чуть не искали не там: ничьи по `created_at` на стенде не
возникли (все 70 отметок различны, наименьший промежуток между двумя записями — 22.35 мс, хотя часы
этой машины идут с шагом около 1 мс), поэтому `ORDER BY created_at DESC, id DESC` против строгого
`<` в условии курсора на той стадии оставалось заметкой, а не найденным дефектом — см.
`docs/SCALE_PLAN.md`, §«Курсор страницы истории». Держат
контракт пять проверок `tests/test_chat_page_keeps_its_newest_line.py` (красное состояние на прежнем
дереве — `4 failed, 1 passed`, где зелёной остаётся проверка стоимости открытия).

**Курсор режет по тому же порядку, что и страница.** Стадия 54 вернулась к заметке стадии 53 и
построила то, чего на её стенде не было: переписку, где по 20 строк делят одну `created_at`
(отдельная база `befos_s54`, 20 000 строк на 1 000 отметок). У порядка страницы второй ключ есть, а у
среза следующей страницы его не было, и этого хватило: обход документированного курсора при
`limit=50` вернул 335 обращений, 16 670 строк из 20 000, ни одной повторно — и 3 330 строк, которых не
было ни на одной странице; при `limit=5` 1 001-е обращение вернуло пустую страницу с `has_more=false`,
хотя в таблице оставалось 15 000 непоказанных строк. На тех же данных экран называл своей самой
свежей строкой `line-19998`, а `GET /matches` ставил на карточку `line-19999` — обе строки делят
`2026-10-10T03:41:45.602977+00:00`. Правка в одном правиле для обоих чтений: срез страницы стал
row-value сравнением `(created_at, id) < (anchor.created_at, anchor.id)`
(`backend/app/repositories/chat_repo.py:149`), а `DISTINCT ON` карточки получил тот же второй ключ
(`backend/app/repositories/chat_repo.py:242`). После правки тот же обход отдаёт 20 000 строк из 20 000
при обоих размерах страницы, 0 потерянных, 0 повторных, и карточка с экраном называют одну строку
(`s54_cursor_post.json`). Новый индекс для этого не понадобился: `EXPLAIN (ANALYZE, BUFFERS)` на якоре
внутри ничейной группы даёт ту же форму плана (`Limit → Result → Incremental Sort → Index Scan
ix_message_match_created → Index Only Scan uq_message_read`, 61 строка против 60 по индексу), а
`Incremental Sort` доупорядочивает только ничью, а не всю переписку; цифры планов и оговорки — в
`docs/SCALE_PLAN.md`, §«Курсор истории на ничьей». Держат контракт четыре проверки
`tests/test_chat_cursor_carries_every_line_of_a_tie.py` (красное состояние на прежнем дереве — `3
failed, 1 passed`, где зелёной остаётся проверка стоимости: страница, взятая по курсору, стоит те же
семь обращений к базе). Ничьих в живой переписке этого стенда измерено не было: в базе разработчика на
51 строке 0 групп ничьей, а штатная запись одного сообщения их не создаёт — правка держит контракт
там, где равные отметки существуют (загрузка истории, backfill, строки с явной `created_at`).

**Кто зовёт `POST /read`.** С стадии 37 — не открытие переписки. Клиент Android звал этот маршрут
вторым запросом сразу после загрузки истории (`ChatViewModel.kt`, `loadHistory`), тогда как само
чтение уже поставило квитанции (`ChatService.history` зовёт `repo.mark_read`,
`backend/app/services/chat_service.py:80`): второй запрос приносил пять обращений при
`marked_read = 0` — и те же пять на переписке, где отмечать нечего (снято слушателем на двух
независимых парах). Стоял он после `when`, а не внутри ветки успеха, поэтому отметка уходила и когда
история не загрузилась: человек видел экран ошибки, а собеседник — «прочитано». Вызов из `loadHistory`
убран, и остались два места, где отметка по-прежнему нужна. Первое — сообщение, пришедшее по сокету:
за ним нет никакого чтения, поэтому `POST /read` здесь и есть путь отметки (`upsert`, строка 157).
Второе — не клиентское, а серверное: кадр `read` самого сокета
(`backend/app/websocket/chat_ws.py:192-204`) идёт через тот же `ChatService.mark_read`. Держат
клиентское поведение три проверки
`android/app/src/test/java/app/befos/presentation/chat/ChatViewModelTest.kt`.

**Сколько раз открытие читает страницу.** С стадии 38 — один. До неё лог живого стенда давал на
открытие переписки два `GET /matches/{id}/messages?limit=50` (72.0 и 39.2 мс в окне 23:43:48 —
23:43:49), и временные пробы в клиенте назвали второго автора: `fillGap`, запущенный в ту же
миллисекунду, что и первый настоящий кадр `Connected` (23:43:48.396). Механизм в том, что состояние
сокета живёт в `MutableStateFlow(false)` (`ChatRepositoryImpl.kt:64`), а `StateFlow` воспроизводит
текущее значение каждому новому слушателю (`ChatRepositoryImpl.kt:75-87`): экран подписывается до
конца дозвола, поэтому его первый кадр — `Disconnected`, хотя сокет ещё ни разу не был поднят, а
обработчик считал любой такой кадр обрывом и обещал дочитать при возврате. `Disconnected` теперь
поднимает флаг только если экран это соединение уже имел. На сервере здесь ничего не меняется:
одно чтение страницы по-прежнему стоит слушателю столько же обращений, сколько и до правки (семь на
том дереве, шесть с стадии 50 — см. два абзаца выше), экономия лежит в круге клиента. Держат
поведение две те же проверки `ChatViewModelTest.kt` — одна на открытие, вторая на
настоящий обрыв и возврат, которые дочитывать должны.

### WebSocket `/ws/chat/{match_id}?token=<access>`

Авторизация по JWT на рукопожатии, но токен — не пропуск: перед тем как принять сокет, сервер
проверяет строки пользователя и матча. Close `1008` (на клиенте проявляется как `403` при
handshake) бывает когда токен нечитаем, когда аккаунт удалён или отключён, и когда пары больше
нет; то же проверяется перед каждым кадром `message`, `read` и `typing`, потому что и токен, и
открытое соединение живут дольше, чем решение о блокировке, удалении или отключении. Кадр
«печатает» здесь не исключение: он доходит до экрана другого человека, значит спрашивает строки
не дешевле сообщения.

У соединения два окна, и ни одно из них не видят лимитеры REST. До расшифровки токена: 30
рукопожатий в минуту на адрес — каждое стоит разбор JWT и два чтения строк. Внутри соединения:
120 кадров в минуту на аккаунт, считаются и исправные, и испорченные; ответ — кадр
`{"type":"error","message":"Too many messages, slow down."}`, а не разрыв, потому что слишком
быстрый клиент не нарушил политику, он просто опередил окно.

**Сколько клиент шлёт перед дозвоном.** С стадии 39 — ноль аутентифицированных чтений, пока токен жив.
Клиент Android перед каждым дозвоном слал `GET /users/me` ради одного: сокет носит токен в
query-параметре, поэтому HTTP-стек не может обновить его на 401, как обновляет обычный вызов. На замере
это обращение ничего и не покупало: четыре открытия переписки дали четыре `GET /users/me`, сервер
ответил на них `200` (12.1 / 14.3 / 14.5 / 13.7 мс), а `POST /auth/refresh` в том же окне не было ни
одного — токен не был просрочен. Один такой запрос стоит серверу четыре обращения (см. счётчик выше),
поэтому с каждого открытия переписки снято одно обращение клиента и четыре обращения к базе. Теперь
решение читает `exp` из тела токена, которое клиент уже держит
(`android/app/src/main/java/app/befos/data/repository/ChatRepositoryImpl.kt:275-288`): предзапрос
идёт, если до истечения осталось меньше минуты (`ChatRepositoryImpl.kt:287`) или если `exp` не
читается (`ChatRepositoryImpl.kt:286`). Это не слабит допуск — он серверный: `decode_token`
отбрасывает просроченное и неподписанное, а `_refusal_reason` перед рукопожатием переспрашивает
строки пользователя и пары (строки 46-62 того же файла), и живой локально `exp` не открывает ни одной
чужой пары. Держат поведение шесть проверок
`android/app/src/test/java/app/befos/data/repository/ChatSocketPreflightTest.kt`.

**Клиент → сервер:**

```json
{ "type": "message", "body": "текст", "client_msg_id": "local-uuid" }
{ "type": "typing", "typing": true }
{ "type": "read" }
```

**Сервер → клиент:**

```json
{ "type": "message", "id": "…", "client_msg_id": "…", "match_id": "…", "sender_id": "…", "body": "…", "created_at": "…", "is_read": false }
{ "type": "typing", "user_id": "…", "typing": true }
{ "type": "read", "user_id": "…" }
{ "type": "message_recalled", "match_id": "…", "message_id": "…" }
{ "type": "presence", "user_id": "…", "online": true }
{ "type": "error", "message": "…" }
```

Отправитель получает кадр `message` всегда: при первой записи — от комнаты, при повторе — только
ему, с тем же `id`. Вторая попытка не добавляет в комнату второе сообщение, а клиент, у которого
такой id уже есть в списке, кадр пропускает. Кадр `message_recalled` комната рассылает обоим
половинам пары после `DELETE` своей строки: он называет только `match_id` и `message_id`, поэтому
экран убирает строку, не узнавая от сервера её текста, и получает его и на втором устройстве того же
аккаунта. Отозванная строка перестаёт быть самой свежей историей пары и перестаёт числиться
непрочитанной — это проверяют те же двенадцать бэкенд-сверок, что и сам маршрут.

## Планы пары

| Метод | Путь | Query / Тело | Ответ |
|-------|------|--------------|-------|
| GET | `/plans` | — | `{plans: [PlanOut]}` — все планы человека по всем его парям |
| GET | `/matches/{match_id}/plans` | — | `{plans: [PlanOut]}` — планы одной пары |
| GET | `/plans/{plan_id}` | — | `{plan: PlanOut, my_note, events: [MessageOut]}` |
| PATCH | `/plans/{plan_id}` | `{place? (≤200), note? (≤500), my_note? (≤500), clear_place?, clear_note?}` | `PlanOut` |
| POST | `/plans/{plan_id}/accept` | — | `204`; `409`, если план отменён или состоялась |
| POST / DELETE | `/plans/{plan_id}/decline` | — | `204`; `POST` — и на закрытом плане тоже: свой отказ забирают обратно |
| POST | `/plans/{plan_id}/hour` | `{when}` (aware, `MIN_LEAD`…`MAX_LEAD`) | `204`; `409`, если план отменён или состоялся |
| POST | `/plans/{plan_id}/hour/confirm` | `{when}` | `204`; `409`, если час уже уехал, а с правки стадии 108 — и если план отменён или состоялся |
| POST / DELETE | `/plans/{plan_id}/cancel` | — | `204` |
| POST / DELETE | `/plans/{plan_id}/complete` | — | `204` |
| PUT | `/plans/{plan_id}/note` | `{note}` (≤500, null очищает) | `204` |

**Отсутствующее поле — это не пустое поле.** `PATCH` читает четыре слова раздельно: `place` и `note`,
которых в теле нет, остаются такими, как их держит строка, а снять уже написанное можно только флагом
`clear_place` / `clear_note` — пустая строка маршруту не указ, он её отвергает (`422`) и не меняет
ничего. Поэтому карточка, у которой два поля на экране, шлёт изменённое слово и флаг на то, которое
человек стёр, а не оба поля всегда: правка заметки не обязана возвращать место тем, что было в поле при
загрузке. У этих двух слов нет авторства: любая из половин пары пишет их и снимает, и ограничение
одно — состоять в этой паре, иначе чужой план отвечает `404` и для спрашивающего его не существует.
Держат это `test_a_pairs_plan_is_one_thing_that_every_screen_moves.py`
(13 проверок на этом дереве) и новый `test_the_plan_card_sends_the_words_the_plan_route_reads.py`
(5 проверок: тело клиента совпадает с полями маршрута, два флага названы отдельным обращением, тап
доходит до маршрута, дверь сохранения стоит только там, где она может сработать, и каждый отказ
переведён), а живой путь добавляет к ним одиннадцать шагов на настоящем сервере.

**Один план, а не его копия на каждом экране.** `PlanOut.id` — `shared_plans.id`, и это тот же id,
который несёт `plan.plan_id` в строке журнала (§«Chat») и на который указывает `messages.plan_id`.
Карточка в переписке, список планов человека (`GET /plans`), деталь плана (`GET /plans/{id}`) и
страница идей говорят об одной строке, а не пересказывают договорённость заново: та же идея,
предложенная второй раз, падает в
`uq_shared_plan_pair_activity`, поэтому план не удваивается.

**Чем стоит этот экран.** Стадия 119 поставила обе двери чтения плана в прибор цены, стадия 120
поставила рядом две двери письма, и ряд `plans` — самое дорогое чтение таблицы после входа:
475.2 / 1489.4 / 1167.5 мс медианой при 85 / 245 / 245 обращениях за вызов на
1 000 / 10 000 / 50 000 анкет, первый вызов — 615.9 / 1455.6 / 1321.0 мс
(`docs/SCALE_PLAN.md`, §«Стадия 120: чем платят две пишущие двери, когда журнал наполняется»,
артефакты `s120_scale_a.json` и `s120_scale_b.json`). Цена принадлежит не строкам и не
планировщику — сумма уникальных чтений ряда равна 2.61 / 9.61 / 2.91 мс, — а числу обращений:
`PlanService.list_for_viewer` идёт по парам аккаунта и каждой паре нужен свой проход проекции,
поэтому ряд укладывается в 1 + 4·пары + 4 запроса. На 10 000 и на 50 000 он плоский именно потому,
что ось у него — пары (20 / 60 / 60), а не толпа; одна пара стоит на этом вечере 25.4 мс — это
разность медиан 10 000 и 1 000, делённая на сорок добавленных пар, и считается она по арифметике
над двумя печатными числами, а не по отдельному замеру. Дверь карточки
(`GET /plans/{plan_id}`) читает
тринадцать запросов и стоит 83.1 / 83.6 / 59.5 мс; тринадцатый вместо прежних двенадцати она платит
за журнал, который наполнен её же планом — строки `events` рядом с этой карточкой перестали быть
пустыми именно с вечера стадии 120.
Двери часа стоят в той же таблице рядом и читаются иначе: перенос вечера
(`POST /plans/{plan_id}/hour`) — 25 обращений, 125.4 / 157.3 / 122.3 мс медианой; ответ на вечер,
названный половиной (`POST /plans/{plan_id}/hour/confirm`) — 22 обращения,
115.8 / 137.4 / 94.1 мс. Число обращений не зависит от масштаба: дверь измеряется одним тапом, а не
длиной списка пар. Запись здесь не побочная: тап, который уводит пару с согласованного вечера, пишет
в её переписку две строки — `plan_voided` и `plan_rescheduled`, — а тап, который соглашается, пишет
одну, `plan_agreed`; повтор того же часа ничего не пишет вовсе. Отсюда и то, чего эти два ряда не
ценят: `chat_history` и карта пары стоят в реестре до них и сняты над тем же набором строк, что и
прежде (`s120_row_counts.json`).

**История плана — это его строки журнала, а не вторая таблица.** `GET /plans/{plan_id}` отдаёт в `events`
те же строки `messages`, что рисует переписка пары, — прочитанные по `plan_id`, от старшей к младшей,
не дальше тридцати (`PlanRepository.events`), с `plan.is_latest` у последней из них. Отдельной таблицы
истории под это не заводили, и проверка необходимости осталась в документах, а не в схеме: второй
журнал означал бы два рассказа об одном тапе, а расхождение между ними пару прочитала бы как чужое
решение. Поэтому строка, которая появляется здесь, обязана быть тем, что пишет чат, — и живым путём
сверяются именно id: список `events` деталями плана совпадает с нитью переписки построчно.
С правки стадии 108 строка изменения двух слов плана называет оба края движения: `plan_changed` несёт в
`body` не только факт правки, но и `место: не было → «…»`, `заметка: «…» → снято` — первое для поля,
которое написали впервые, второе для снятого флагом. Историю пары спрашивают не о том, *было ли*
изменение, а о том, каким значение поля было до него, и оба края живут только в этой строке: ряд плана
держит лишь то, что план держит сейчас. `my_note` в журнал не попадает никогда — личное
слово о своей встрече не является утверждением о паре.

**Статус читается, а не записывается вперёд.** `_status` — одно упорядоченное правило, и порядок в
нём и есть ответ пары: `cancelled` (план отменён) → `completed` (обе половины сказали, что встреча
состоялась) → `declined` (одна из половин от неё отказалась) → `planned` (пара стоит на часе) →
`rescheduled` (час стоит, а новый уже назван) → `accepted` (оба за неё, часа ещё нет) →
`proposed`. Отмена старше часа, потому что «вы договорились» не может стоять рядом с
«отменено»; отказ создателя — не ответ паре, а правка своей страницы, поэтому она оставляет план
`proposed`.

**Отказ читается раньше часа, и это то, что делает подтверждение обратимым.** До стадии 107 в этом
порядке часа `declined` не было вовсе: `_decision` отвечал `joined` всякому, чья строка несла метку
предложения, поэтому «не приду», сказанное после «в семь», до состояния пары не доходило — строка
`activity_preferences` держит оба флага (`proposed` и `declined`) одновременно, и флаг предложения
снять нельзя, иначе карточка в чате получила бы вторую копию уже отправленного предложения (это
закрыла стадия 63). План, отвечающий по первому флагу, читал отказ, который был записан, подтверждён
базой и забыт всеми экранами. Теперь `_decision` смотрит на
отказ первым, а `declined` встаёт в `_status` перед `starts_at`: «Не приду», сказанное после названного
часа, — состояние пары, каким бы часом строка ни продолжала стоять. Взятый обратно отказ оставляет под собой предложение, из которого он вырос,
поэтому выход из отказа — тот же тап, что его сделал, и договорённость не приходится торговать заново.
Держат это `test_the_half_that_confirmed_can_still_say_no.py` (13 проверок) и
`test_a_refusal_outranks_the_hour_it_came_after` внутри него.

**Чей ответ спросить — у того и спрашиваем.** `PlanOut` отдаёт три слова об ответах, и каждое из них
смотрит на одного человека: `my_decision` (`pending` | `joined` | `declined`) — собственное слово
смотрящего, `partner_decision` — те же три слова, снятые со строки второй половины (или `pending`,
пока она молчит), `needs_my_answer` — план ждёт именно этого человека. Третье поле раньше читалось
как «партнёр не ответил», поэтому карточка того, чьего слова план и ждал, говорила, что ждут не её:
половина, подтвердившая первая, видела `partner_decision: pending` прямо у себя, а вторая половина —
то же самое слово о себе, и паре оставалось выяснять, кто молчит, сверяя две карточки. Теперь
`needs_my_answer` — пропущенное собственное слово либо час, который назвал другой (за него отвечает
`hour_for_me_to_confirm`), а чужой долг по-прежнему виден только в `partner_decision`. Тап одной
половины не двигает строку другой — это проверяют и `_both_read` в новом ряде, и живой путь, где оба
ответа снимаются с карточек двух настоящих клиентов.

Часы план не переводит ни в какое состояние сам: `completed` появляется только из двух
`attended_at`-ответов, поэтому наступивший час не кладёт в журнал утверждение о встрече, которой
никто не подтверждал — это держит `test_an_hour_that_passed_completes_nothing_by_itself`.

`POST …/cancel` доступен любой половине, `DELETE …/cancel` — только той, что отменила (вторая
получает `409`: чужую отмену отменяет тот, кто её сделал). Возврат плана возвращает и его вечер:
`cancelled_at` снимается, `starts_at` остаётся тем часом, на котором пара стояла до отмены, а карточки
обоих читают `can_cancel` снова. После отмены оба часа-маршрута отвечают `409` (`_refuse_closed`),
пока план не взят обратно, — и с правки стадии 108 тот же отказ приходит и от состоявшейся встречи:
`This meeting is over, so there is no hour left to arrange.` До замера эта дверь была открыта: тап
«перенести встречу» на плане, который обе половины отметили состоявшимся, отвечал `204` и портил
закрытую строку — `starts_at` уезжал в `null`, `pending_hour` и `pending_by` брали новый миг, а
`hour_passed` становился ложным под статусом, который всё ещё читался `completed`. Это две разные
правды об одной строке: список говорит, что встреча состоялась, а карточка — что вопрос ждёт ответа.
Состоявшийся вечер передвигают не дверью часа, а той же дорогой, что и двери ответа: сначала снять своё
слово о том, что встреча была (`DELETE …/complete`, и оно остаётся словом автора), потом назвать час,
который ещё впереди.

**Час двигает любая из половин, и перенос — это тот же вопрос, что первое название.** До стадии 108
за названным вечером стояла одна половина: `PUT …/time` и `POST …/hour` принадлежат тому, кто назвал
`meeting_time`, а второй оставалось согласиться. Тап согласившегося не был запретом — маршрут принимал
его и писал новую строку, — но дальше ничего не менялось: ряд держил и новый `meeting_time`, и
прежний `accepted_time` рядом с ним, `agreed_instant` продолжал узнавать в двух старых значениях
стоящее обещание, план отвечал прежним часом, а чат молчал. С правки стадии 108 название *другого*
мига снимает собственное согласие там, где оно записано (`set_preference` в
`backend/app/repositories/activity_repo.py:48`, `accepted_time` через `case()`), и это делает перенос
замечаемым: `accepted_time`, равный новому часу, остаётся нетронутым, поэтому тап, который ничего не
двинул, по-прежнему остаётся тапом без строки журнала. Второй половинке этот тап приносит обычный
вопрос — `rescheduled` в статусе, `pending_hour` на карточке и `needs_my_answer: true` у того, кто
соглашался, — а согласить можно и со своей карточки, и со страницы идей: один и тот же глагол.
Держат это `test_either_half_moves_the_hour_the_pair_stands_on.py` и шаг живого пути, где вечер
двигает ровно та половина, которая его не называла.

**О том, какой час спрашивается, план знает сам — и только про это.** `starts_at` и ответы половин
остаются проекцией двух строк `activity_preferences`; исключением стал один факт, которого в рядах нет:
*о каком именно часе* пара сейчас спрашивается. Два ряда, называющие два разных мига, — это и пара,
которая ещё не сошлась на вечере, и пара, которая на вечере стояла и только что его передвинула;
различить их по рядам нельзя, а ответ второй половине нужен в обоих случаях, иначе тап упирается в
молчание. Поэтому `offer_hour` записывает свой вопрос на сам план (`_record_ask`,
`pending_hour`/`pending_by`), а `sync_pair` держит эту запись ровно столько, сколько строка спросившего
по-прежнему называет тот же миг (`_ask_of`), — ушедший вопрос не оставляет карточку спрашивать о том,
о чём никто не спрашивал. Паре, которая никогда не стояла на часе, вопрос по-прежнему читают ряды
(`unmatched_offer`). Отсюда честная формулировка: час — проекция двух строк плюс одна запись плана о
том, какой из названных вечеров сейчас на очереди. Миграции для этого не понадобилось: `pending_hour`
и `pending_by` лежат в `shared_plans` со стадии 95, и правка изменила только то, кто и надолго ли их
заполняет.

**Закрытый план не принимает ответа — кроме отказа, который ещё не взят обратно.** У дверей ответа
(`POST …/accept`, `POST …/decline`, `DELETE …/decline`, а на странице идей — `select` и снятие
отклонения с карточки) до стадии 107 охраны не было вовсе: `accept` отвечал `204` поверх отменённого
плана и двигал строку человека под договорённостью, которую пара уже сняла, а возврат плана ставил её
на подтверждение, данное тогда, когда его никто не ждал. `_refuse_answer_closed` отсекает
`cancelled` и `completed` с `409` и текстом `This plan is closed, so there is nothing left to answer.`
— на двух дверях сразу, потому что и карточка идей, и экран плана говорят об одной строке. `declined`
в этом списке отсутствует намеренно: отказ — тоже ответ, и его автор вправе забрать его обратно у
любого плана, иначе за закрытой дверью пара оставалась бы с договорённостью, которую не может
починить никто. На карточке идей это две разные проверки: `test_a_closed_plan_takes_no_new_answer_and_keeps_the_one_it_holds`
и `test_pushing_a_closed_idea_away_stays_this_persons_own_door`.

**Повтор того же ответа — один ответ.** Три тапа семейства (`accept`, `decline`, снятие отказа)
идемпотентны по состоянию, а не по счётчику: `_journal` сверяет факты строки до правки и после неё,
и тап, оставивший их на месте, не пишет ни строки переписки и не рассылает ни одного кадра. Проверено живым путём: второй `decline` оставляет на странице плана ровно
те же id строк, что первый, а сокет второй половины на него молчит (`the same refusal sent twice is one
answer and one line`). У двери, отсекаемой `409`, повтор тоже ничего не пишет — список планов до и
после сверяется по id.

`404`, а не `403`: план, к которому у человека нет доступа, для него не существует — ответ
«не твой» подтвердил бы незнакомцу, что договорённость реальна и какая пара её держит. Проверено
маршрутами по настоящему id чужого плана — деталь (`GET`), отмена (`POST …/cancel`),
правка (`PATCH`), своя заметка (`PUT …/note`) и три двери ответа (`POST …/accept`,
`POST …/decline`, `DELETE …/decline` — стадия 107) — и пустым `GET /plans` у того же незнакомца
(`test_a_stranger_naming_a_real_plan_has_no_plan_to_act_on`, `test_a_stranger_has_no_answer_to_give`);
чужой `plan_id` не оставляет строк в
чужой переписке, не меняет чужую заметку и не двигает чужой ответ — свой ответ человека читается из
его строки, поэтому тап незнакомца, дошедший до плана, был бы тапом по чужой половине пары.

Час остаётся проекцией двух строк `activity_preferences` — за исключением ровно одного факта, названного
выше: маршрут часа просит записать эти строки, а не держит третье изложение согласия где-то ещё,
поэтому план не может расходиться с тем, что пара действительно назвала. `PATCH` час не трогает
намеренно: час — это ответ второй половины, и он двигается только через двери часа, где этого ответа
ждут снова.

`my_note` живёт на строке участника и возвращается только тому, кто её написал: `PlanOut` её не несёт,
в общий `note`/`place` она не попадает и в чат ничего не пишет — заметка о своей встрече не является
утверждением о паре.

## Safety

| Метод | Путь | Тело | Ответ |
|-------|------|------|-------|
| POST | `/users/{user_id}/block` | — (без тела) | `200` (`{blocked: true, user_id}`) |
| DELETE | `/users/{user_id}/block` | — (без тела) | `200` (`{blocked: […]}` — список, который остался после снятия) |
| GET | `/users/me/blocks` | — | `200` (`{blocked: […]}`) |
| POST | `/users/{user_id}/report` | `{reason (2..40), details? (≤1000)}` | `200` (`{reported: true, reason}`) |
| POST | `/users/me/visibility` | `{hidden: bool}` | `200` |
| DELETE | `/users/me` | — | `200` (удаляет аккаунт, доступ отзывается) |

Блокировка скрывает пользователя из подбора обеих сторон.

**Список и его снятие отвечают одним и тем же телом.** И `GET /users/me/blocks`, и
`DELETE /users/{user_id}/block` отдают строку `{blocked: […]}` — карточки тех, кого аккаунт
заблокировал, новые первыми. Снятие отвечает не `true`, а оставшийся список, потому что экран,
который спросил, обязан нарисовать то, что сервер действительно держит, а не то, что предполагал
тап, — по тому же правилу, которым ряд снимков рисуется из ответа маршрута. Порядок держится по
`created_at.desc(), id.desc()`: два тапа в одну секунду дают две строки с одним временем, и по
одному только времени список переставлялся бы при каждом перечитывании. Карточка несёт ровно то,
по чему человека узнают, — имя, возраст, город, главный снимок и момент блокировки; интересы,
анкета и ответы теста в неё не читаются.

**Снятие возвращает в подбор, но не возвращает пару.** Строка `blocks` уходит — и anti-join
подбора перестаёт исключать человека, то есть его анкета снова приходит в ленту. Пара и её
переписка при этом не оживают: блокировка удалила их на записи, и маршрут, который молча
пересоздал бы `match`, записывал бы отношение, которого никто не согласовывал. Жалобы на
разблокированного остаются. Блокировка, её снятие и `like` берут один и тот же advisory-замок
пары, поэтому три порядка, которые человек может устроить своими тапами, сериализуются, а не
оставляют пару заблокированной и сматченной одновременно.

**Чужой номер не отличается от несуществующего.** `DELETE /users/{user_id}/block` на id, который
этот аккаунт не блокировал, и на id, которого нет в базе, отвечают одинаково — `404 not_found`, —
чтобы список нельзя было пустить на вопрос «заблокирована ли вот эта пара у кого-то». На
собственный id обе половины отвечают `422 validation_error` («You cannot block yourself.» /
«You cannot unblock yourself.»).

**Жалоба — это строка очереди, а не действие над парой.** `POST /users/{user_id}/report` пишет
`reports` и больше ничего не трогает: профиль не скрывается, пара не распускается, переписка не
закрывается, блокировка не ставится. Отправка жалобы не бывает скрытой блокировкой, а снятие
блокировки, удаление переписки и удаление аккаунта не стирают уже записанную жалобу — модератору
она видна и после того, как человека в подборе нет. Категорий восемь slug'ов
(`VALID_REASONS`, `backend/app/services/safety_service.py:34`): `spam`, `harassment`,
`inappropriate`, `fake`, `minor`, `impersonation`, `threats`, `other`; `reason` — обычная колонка,
поэтому строки, записанные прежними сборками, читаются как лежали, а список решает лишь тому, что
записывается теперь. Поле — `String(80)` и enum не есть. Клиент показывает из них семь
(`ReportReasonLabels`, `android/app/src/main/java/app/befos/presentation/common/Labels.kt`) — те,
которые человек выбирает словами из брифа, плюс `other`; `minor` остаётся принятый сервером, но на
экране его нет, потому что возрастной порог продукта проверяется анкетой, а не доверием к чужому
тапу.
`details` необязательна и ограничена тысячей символов с обеих сторон — и в `ReportIn`
(`backend/app/api/v1/safety.py:22`), и в `MaxReportDetails` клиента, — чтобы длинный рассказ о
вечере не возвращался ошибкой валидации, которую человек нечем исправить.

**Три отказа, которые жалоба умеет отвечать сама.** На собственный id — `422 validation_error`
(«You cannot report yourself.»); на id, которого нет или который удалён, — `404 not_found`; на
второй тап той же категории про того же человека — `409 conflict` («You have already reported this
user for the same reason.»). Четвёрка (жалобщик, обвиняемый, категория) охраняется ключом
`uq_report`, и решает он на записи: два тапа приходят раньше, чем первый успел закоммититься,
поэтому чтение «есть ли уже» не может быть пуском. Бюджет считается по аккаунту, а не по адресу:
`_report_limiter` (`backend/app/core/rate_limit.py:75`) даёт двадцать попыток в час на
`report:{user_id}` и отвечает `429 rate_limited` («Too many complaints for now. Try again later.») —
считается попытка, а не исход, потому что отказ, который ничего не стоит, можно повторять тысячу
раз в час. Адрес для этого бюджета не годится: один дом за одним NAT потратил бы чужой бюджет, а
тот, кто меняет адрес, менял бы вместе с ним бюджет жалоб.

**Того, кто пожаловался, обвиняемый не узнаёт.** Ответ маршрута — ровно `{reported: true, reason}`,
и ни один путь продукта не отвечает на вопрос «кто пожаловался на меня»: ни `GET /users/{id}`, ни
настройки, ни список блокировок не называют автора строки. Модератору жалобщик виден (`reporter` в
карточке очереди), потому что решение о человеке принимается по тому, что рассказал другой человек,
и анонимное утверждение проверять нечем.

## Модерация

| Метод | Путь | Кто пускается | Ответ |
|-------|------|--------------|-------|
| GET | `/reports?status=&after_id=&limit=` | модератор | `200` (`{reports: […], next_cursor, has_more}`) |
| GET | `/reports/{report_id}` | модератор | `200` (карточка + `reviews: […]` + `allowed_next_statuses: […]`) |
| POST | `/reports/{report_id}/review` | модератор | `200` (`{id, status, updated_at}`) |

Дверь у всех трёх одна — `get_moderator` (`backend/app/auth/deps.py:56`), и она читает флаг из
строки аккаунта на каждый запрос, а не из токена: access-токен роли не несёт, поэтому отнятое
право останавливает человека следующим запросом, а не через час, который остался украденному
ключу. Подписанный, но немодераторский аккаунт получает `403 forbidden` («Moderator role is
required.»), а не `401 unauthorized`: сессия цела, права нет, и клиент, который путает эти два,
начинает обновлять токен перед дверью, которую никакой refresh не открывает. Три маршрута лежат в
схеме отдельным тегом `moderation` (`backend/app/api/v1/moderation.py:25`) и в `router.py`
подписаны тем же префиксом, что и файл: `/docs` показывает их вместе, чтобы поверхность разбора
можно было перечитать как одно целое, а не искать по одному маршруту в каждом месте.

**Очередь — страница, а не дерево.** `status` принимает одно из четырёх значений
(`open`, `reviewed`, `resolved`, `dismissed`) и на другое слово отвечает `422` до обращения к
таблице; `limit` ограничен `MAX_PAGE = 100` и просит больше — тоже `422`, а не «меньше, чем вы
просили, молча»; курсор `after_id` — это id строки, от которой продолжается отсчёт, и курсор на
уже удалённую жалобу даёт `404` («Report cursor not found.»), а не первую страницу заново, потому
что самая старая жалоба, показанная дважды, выглядит как новая. Порядок — `created_at, id` от
старшего к младшему, то есть очередь идёт от того, кто ждёт дольше всех, и две жалобы, записанные
в одну секунду, не меняются местами между двумя чтениями одного состояния.

**Карточка жалобы несёт ровно то, чем решают.** Обвиняемый: `user_id`, имя, возраст, город и три
флага (`is_deleted`, `is_hidden`, `is_moderator`); жалобщик: `user_id` и имя. Анкеты, ответов
теста, снимков, почты и дат рождения нет: рассматривающий закрывает строку о поведении, а не
пересобирает профиль. Возраст не печатается у стёртого аккаунта — удаление пишет в `birth_date`
значение, которого никто не проживал, и возраст, прочитанный с него, был бы числом, которым никто
не был.

**Решение — это переход и строка истории в одном коммите.** Тело `POST …/review` — `{status,
comment?}`, и модератора в нём нет: чью руку запишет строка, решает аутентифицированный запрос,
поэтому тело, называющее другой id, не меняет ничего, кроме текста ошибки. Таблица переходов
живёт в одном месте (`ALLOWED_TRANSITIONS`, `backend/app/services/moderation_service.py:20`): из
`open` можно в `reviewed`, `resolved`, `dismissed`; из `reviewed` — в `resolved` и `dismissed`;
оба закрытых — тупики. Тупик здесь не лень, а правило: `resolved` и `dismissed` — то, что
модератор сказал очереди, и маршрут, который их отпирает, молча переписал бы решение, которое
история уже записала. Неправильный отказ отвечает следующий жалобой на того же человека — она
приходит своей строкой и решается заново, а не вторым приговором первой. Ровно тот же статус,
который строка держит, — `409` («This complaint already carries that status.»); статус, которого
нет в списке, — `422`; несуществующая жалоба — `404`. Закрытие без комментария — `422` («A
complaint that is being closed needs a comment saying why.»), комментарий длиннее `MAX_COMMENT =
1000` — тоже `422`. Строка читается `FOR UPDATE`, поэтому вторая рука, пришедшая к той же жалобе,
ждёт и читает статус, который первая уже оставила: два тапа двух модераторов дают одно решение и
один отказ, а не две строки истории, которые противоречат друг другу.

**История переживает того, кто её написал.** `report_reviews` хранит пару статусов (`from_status`,
`to_status`), а не только новый: очередь, читаемую post factum, просят отличить жалобу, закрытую
сразу, от жалобы, к которой возвращались дважды, и одна колонка оба ответа не держит.
`moderator_id` — `ON DELETE RESTRICT`, и это не перестраховка: accounts в этом продукте не
удаляются жёстко, а запись о том, что было решено о человеке, не должна становиться досягаемой
вопросом о том, работает ли решавший ещё здесь. `GET /reports/{report_id}` отдаёт её целиком, от
первого движения к последнему, и вместе с ней — `allowed_next_statuses`
(`backend/app/schemas/schemas.py:768`):
статусы, в которые эта жалоба ещё может уйти, снятые с той же таблицы `ALLOWED_TRANSITIONS`, против которой
проверяет запрос и маршрут записи (`backend/app/services/moderation_service.py:92`, сверка при записи — `:131`), поэтому экран решения
рисует только те переходы, которые сервер ещё не отверг; у закрытой жалобы список пуст, а не прежний путь.

**Своё решение модератор не пишет.** `reported_id == moderator_id` — `403` («A moderator cannot
decide a complaint about their own account.»): роль говорит, кто вправе решать, а не о ком именно.
Без этого правила поверхность модерации была бы способом изнутри закрыть жалобу на себя, и ни
один другой аккаунт не увидел бы, что это произошло.

**Первого модератора делает оператор, и это один осознанный шаг.** Публичной регистрации
модераторов и пригласительных ссылок в продукте нет: `is_moderator` — колонку, которую не записывает
ни один маршрут и ни одна форма клиента (массовое назначение проверено рядом
`test_an_ordinary_account_cannot_reach_the_moderation_surface.py`). С правки стадии 103 аккаунт и
читает её — `ProfileOut.is_moderator` (`backend/app/schemas/schemas.py:138`) отвечают лишь хозяйские
маршруты `/users/me…`, и клиент ставит по этому слову дверь в очередь на странице «Настройки», а
публичный `GET /users/{user_id}` (`backend/app/api/v1/users.py:200`) поля не знает: чужой профиль не
сообщает, кто здесь модератор. Чтение — единственное, что даёт это поле; запись роли оно не открывает,
и экран очереди стоит за той же дверью, что и маршруты: немодераторский аккаунт, добравшийся до него,
получает свой `403`. Единственный
путь — `UPDATE users SET is_moderator = true WHERE id = '…'`, и он описан в `docs/OPERATIONS.md`
§14 как шаг оператора, а не как обход: пока его не сделал никто, очередь пуста не потому, что
жалоб нет, а потому, что читать их некому — теперь уже и на экране.
