# Архитектура BeFoS

## Общая схема

```
┌─────────────────────────┐        REST (JSON) / WebSocket        ┌──────────────────────────┐
│  Android (Jetpack        │ ───────────────────────────────────▶ │  FastAPI (async)          │
│  Compose, Material 3)    │ ◀─────────────────────────────────── │                           │
└─────────────────────────┘                                       │  API (v1) → Service →     │
         │                                                         │  Repository → PostgreSQL  │
         │ data / domain / presentation                           │                           │
         ▼                                                         │  Compatibility Engine     │
   Ktor HttpClient + WebSocket                                     │  Recommendation Engine    │
   DataStore (токены)                                              │  WS Chat Gateway          │
                                                                   └──────────────────────────┘
```

Принцип: **тонкие контроллеры, логика в сервисах, доступ к данным в репозиториях**. Ни один слой не «перепрыгивает» через соседний.

## Backend

### Слои

- **`app/api/v1/`** — HTTP-маршруты. Контроллеры валидируют вход (Pydantic), вызывают сервис и формируют ответ. Маршруты сгруппированы по тегам: `auth`, `users`, `tests`, `discovery`, `matches`, `chat`, `plans`, `safety`, `moderation`, `health` (список снят со строк `APIRouter(tags=…)` этих десяти файлов, а не из названия папки: у `discover.py` тег `discovery`). Все подключаются под префиксом `settings.api_v1_prefix` (`/api/v1`). Ряд `moderation` стоит отдельно от `safety` не из-за похожести слов: жалобу пишет обычный аккаунт, а читает её модератор, и у этих двух половин разные двери (`app/auth/deps.py:56`), поэтому `api/v1/moderation.py` — свой роутер с префиксом `/reports`, а не новые строки на `/users/{user_id}/report`.
- **`app/services/`** — бизнес-логика: `auth_service`, `profile_service`, `test_service`, `compatibility_service`, `discovery_service`, `match_service`, `matches_service`, `chat_service`, `recommendation_service`, `plan_service` (+ `plan_time` — единственное место, где живут правила часа пары), `photo_service`, `safety_service`, `moderation_service`. Сервисы не знают про HTTP.
- **`app/repositories/`** — доступ к данным через SQLAlchemy 2.0 (async). Инкапсулируют запросы, возвращают модели/примитивы. Где экрану хватает нескольких колонок, метод возвращает проекцию (`select(Profile.user_id, Profile.name, …)`), а не сущность: список пар читал 38 колонок сущностей на карточку, чтобы ответить одиннадцатью полями (стадия 49).
- **`app/models/`** — декларативные SQLAlchemy-модели (25 таблиц; в базе их 26, потому что к ним
  добавляется `alembic_version` — съём 17:40:32…17:40:34 UTC 2026-10-17 на HEAD `d8a0957`:
  `len(Base.metadata.tables)` из того же `app.models`, что грузит приложение, плюс
  `select count(*) from pg_tables where schemaname = 'public'` на рабочей базе, артефакт
  `s102_model_counts.log`; тот же запрос даёт 74 индекса — столько же, сколько насчитывает
  поднятая с нуля база в [`DATABASE.md`](DATABASE.md), то есть стенд и пустая схема сходятся.
  Прежний съём этого ряда называл 22 модели и 23 таблицы — он отстал на две стадии: `shared_plans`
  и `shared_plan_members` добавила стадия 95, `report_reviews` — стадия 102).
- **`app/schemas/`** — Pydantic-схемы запросов/ответов (DTO-граница).
- **`app/core/`** — `config` (pydantic-settings, `.env`), `database` (async engine, `get_session`), `security` (bcrypt, JWT), `rate_limit` (скользящее окно), `exceptions` (единый конверт ошибок).

### Движок совместимости (`app/compatibility/`)

- `traits.py` — таксономия: пять категорий (`values`, `personality`, `communication`, `lifestyle`,
  `leisure`) и 21 ось, у всех осей `polarity = "similar"`. Их состав — инженерная эвристика, а не
  выведенное правило; охраняется не он, а согласие каталога вопросов с ним:
  `TestService._require_declared_axes` отказывает пачке ответов, если строка `test_questions`
  называет категорию или ось, которых здесь нет (стадия 69).
- `weights.py` — `DEFAULT_WEIGHTS` (сумма = 1.0), `ENGINE_VERSION`, валидация конфигурации весов.
- Матрица целей знакомства (`_GOAL_COMPAT`) — 25 клеток над пятью целями, симметричная, диагональ
  1.0. Обещание симметрии из комментария к таблице долго никто не читал; теперь его проверяет
  `validate_goal_matrix()`, вызванный при импорте, и называет оба числа у клетки, которая ему не
  соответствует. Это важно именно потому, что движок кормится парой «зритель первым»: уклонившаяся
  клетка дала бы двоим разные проценты одних и тех же ответов. Строки матрицы — теперь единственный
  словарь целей: `profile_service.VALID_GOALS` читает собранный из них `traits.GOAL_KEYS`
  (стадия 70; замер до правки — шесть копий словаря, один набор, 0 асимметричных клеток).
- Формула: `Score = Σ normalize(component_i) × weight_i`. Полностью детерминированно: одинаковый вход → одинаковый выход, никаких случайных величин. Детерминированность распространяется и на порядок слагаемых: среднее по категориям считается по **отсортированным** общим признакам, а ответы читаются с `ORDER BY question_id`. Без этого сумма float-ов зависит от порядка итерирования множества (то есть от `PYTHONHASHSEED` процесса) и от расположения строк в куче, а не от ответов: те же два профиля давали 49% и 50% в двух процессах (замерено на `PYTHONHASHSEED=0` и `=1`).
- `explain_pair(a, b)` возвращает `CompatibilityResult` (общий процент, разбивка по категориям, версия движка) и `CompatibilityExplanation` (сильные стороны, отличия, общие интересы — пересечение множеств интересов пары).
- Признак `has_data` у категории — не украшение объяснения: со стадии 72 он выходит в `categories[]`
  на всех трёх маршрутах — живая карточка пары (`GET /matches/{match_id}/compatibility`), чужой
  профиль (`GET /users/{id}`), личный результат (`POST /tests/complete`). До него экран получал
  только число, а нейтральная половина движка и ровно половина совпадения пишутся одними и теми же
  50, поэтому полоса категории, где сравнивать было нечего, выглядела измеренной на середине. На
  личном результате флаг всегда `true`: `build_vector` (`test_service.py:120`) не заводит полосу для
  категории, под которой нет ни одного ответа.
- Процент пары не зависит от того, кого считать зрителем: категории сравниваются симметрично, вес задан категории, а не человеку, поэтому `compute(a, b) == compute(b, a)` (закреплено тестом). На этом держится одна строка `matches` на пару — обновить её может любая из сторон.
- Экраны пары показывают один и тот же процент. `matches.compatibility_score` — не архив момента лайка: он перезаписывается там же, где инвалидируются колода и рекомендации (пересдача теста в `test_service.recompute_profile`, правка `interests`/`city`/`dating_goal` в `profile_service.update`, `compatibility_service.refresh_pair_scores`), а seed пишет в него число движка. Замер до правки: после пересдачи — `list=100 single=100 live=46`; в seed-стенде — `list=single=82` против живых 67/67/56/66. Тот же замер после `PATCH /api/v1/users/me` с неизменным `city`: `stored == live` на всех семи парах стенда (2026-10-06) — поэтому посеянный старым seed стенд чинится вызовом API, а не пересевом (`docs/OPERATIONS.md` §16).
- Город поиска — слово зрителя, а не его анкета, и до стадии 104 у этого слова не было пишущей стороны: колонка, условие `func.lower(Profile.city) == city.lower()` в `_preference_conditions` (`repositories/social_repo.py:370-371`) и ведущая колонка индекса `ix_profiles_city_lower_birth` лежали вместе, но ни один маршрут города не принимал. Стадия дописала её: `PATCH /users/me` держит `city_preference` (120 символов, `strip()`, пустой после stripping — NULL как «снимите фильтр», отсутствующее поле — не ответ, `profile_service.py:207-214`), город стоит в `_DECK_FIELDS` (`profile_service.py:47`), поэтому его правка сбрасывает очередь зрителя — тем же `deck_invalidate`, которым живёт правка `age_min`, — а Android-правка анкеты несёт поле «Город поиска» в разделе «Кого вы ищете» и шлёт обрезанный текст, где пустая строка и есть стирание: JSON null этот клиент отправить не может (сериализатор выбрасывает явные null, `core/network/HttpClientFactory.kt:57-58`). Приватность ряда держат одиннадцать проверок `tests/test_the_search_city_a_person_names_narrows_the_deck_that_answers.py`: карточка `/users/me` слово отдаёт, `GET /users/{user_id}` и колода — нет.
- `universe.py` — карта пары «два мира», производная от того же движка, а не второй движок. Она ничего
  не оценивает: процент, вес и `has_data` каждой из семи полос копируются из `CompatibilityResult`,
  а слово связи узла следует тем же порогам `STRENGTH_THRESHOLD` / `DIFFERENCE_THRESHOLD`, что читает
  объяснение (`explanation.py:10-11`). Четыре связи: `harmony` (двое названных ответа в верхней
  полосе), `complementarity` (между порогами), `discussion` (в противоположной) и `unknown` — и
  именно четвёртая несущая: у `unknown` нет сравнения (черта, которую ответил один; интерес, который
  назвал один; цель, о которой молчат), и карта не красит его как совпадение. Узел несёт обе
  половины своего числа и строку `evidence`, поэтому объяснение на карте связано с данными узла, а
  не с текстом рядом. Документ попарно-глобален: `a`/`b` — собственный порядок строки матча
  (`user_a`/`user_b`), а не «зритель первым», поэтому двое открывают одну карту, а не зеркало друг
  другу (класс асимметрии, названный стадией 70). Процент и покрытие разведены: `coverage` полосы —
  доля узлов, где сравнение состоялось, и она не двигает ни процент, ни `has_data` (стадия 73,
  маршрут `GET /matches/{match_id}/universe`). Документ карты несёт ещё и `story` — те же семь полос,
  пересказанные строками, где названы только итоги: общий процент, процент полосы, её вес и сколько
  её пунктов легли в каждое из слов связи. Ни имени оси, ни одного ответа отдельно взятого человека в
  этих строках нет, потому что метка узла и есть чей-то ответ, а «наша история» существует ровно для
  того, чтобы уйти за пределы приложения. Строки сочиняются внутри `build_universe` из уже собранных
  полос: второго обращения к базе за историей нет, и цена `/universe`, снятая стадией 76, остаётся
  ценой одного вызова.

### Движок рекомендаций (`app/recommendations/`)

- Каталог активностей (`activities`) несёт сигналы `energy / social / cost` (0..1).
- Оценка пары по активностям детерминированная: учитываются интересы, досуг, образ жизни, локация и цель знакомства обоих пользователей. Каждая рекомендация содержит `score`, `position` и человекочитаемые `reasons`.
- `reasons` — объяснение «почему именно этой паре», и собирается оно из ответов пары, а не из порога полосы. Ось досуга и ось образа жизни называются только когда все значения за этим утверждением — ответы двоих и сигнал самой активности — отвечают одной стороне этой оси, а слово стороне даёт `describe_side`: тот же, что у разбора совместимости и карты пары (стадия 75 убрала второй перевод одного ответа). «умеренно» стороной не считается, одна полоса печатает не больше одной строки, и выбрана она детерминированно — резче всего отвеченная ось идеи, при равенстве по ключу, — потому что страница хранится и читается дважды. interest-полоса различает тег, выбранный двоими, и тег, выбранный одним из них (второй двигает 0.4-е слагаемое полосы), город отвечает «в вашем» / «в ваших» / «в городе одного из вас» по числу совпадений, а цель различает одну названную и две не расходящиеся. Замер до правки на рабочей базе: «Подходит вашему стилю досуга» на 15 из 16 карточек двух живых пар, единственная строка на 7 из 8 карточек одной из них; после — 33 строки вместо 28, карточек с одной строкой 4 вместо 8, при тех же числах: 56 карточек семи пар, 0 расхождений в `score`, порядок страницы тот же. Держат правило 43 проверки `tests/test_an_explanation_has_to_name_the_pair_not_the_threshold.py` (25 из них — сетка energy × ответ второй половины, одна сверяет образец `docs/API.md`, одна — подпись экрана).
- Цель знакомства, о которой молчат, не считается расхождением: `_goal_match` отдаёт 0.5 — половину
  веса `goal` (0.10), — потому что пустое значение сигнал получает, когда у половины пары нет строки
  профиля, а `goal_compatibility` отвечает `0.0` любой паре, для которой в матрице нет клетки. Так же
  этот движок уже читает interests, и так же пустой ответ читает движок пары (`NEUTRAL_SCORE`,
  стадия 60). Замер до правки и после: карточка 82 % с двумя названными целями, 72 % и 78 % при
  молчании одной стороны. На трёх живых базах ветка пока никому не доступна — 0 пар, где у половины
  нет строки профиля, и 0 половин пары с пустой целью (`s70_final_erased.txt`, окно
  00:51:59…00:52:00 UTC), —
  поэтому правка чинит не текущий процент, а правило, по которому он будет считаться (стадия 70).
- Страница считается один раз и читается из `recommendations`, но кэш не бессмертен: правка профиля, из которой пара оценивается (`interests`, `city`, `dating_goal`), и пересчёт теста удаляют сохранённые строки pair-а — иначе «Общий интерес — Фотография» остаётся висеть у человека, который интересы снял.
- Нажатие на карточку — это запись в `activity_preferences` под замком пары и с `match_id` в ключе, и та же строка читается обратно при сборке ответа как `selected`. Отметка принадлежит тому, кто нажал, а не паре: сохранённая страница у двоих общая, и идея, которую одна половина уже отправила в чат, для другой остаётся не отправленной. Без этого чтения запись была write-only, экран не помнил выбор между двумя открытиями вкладки, и второе нажатие на ту же карточку вторично приносило «Идея для нас: …» в чат пары (стадия 63, миграция `b4d8f1c07a52`). То же чтение отвечает и про вторую половину — `partner_selected`: фильтр по читателю выбрасывал строки собеседника молча, поэтому совпадение выборов выглядело на обоих экранах как предложение одного. Клиент меняет по нему только подпись кнопки («Поддержать в чате»). С стадии 95 у него отнято и само сообщение: тап — это один `POST …/recommendations/{activity_id}/select`, который через `PlanService` пишет и ряд `activity_preferences`, и строку журнала плана в той же транзакции (`plan_proposed`, а когда ряд второй половины уже есть — `plan_accepted`), поэтому вторая половина приносит в переписку не второй экземпляр той же фразы, а присоединение к той же сущности плана.
- Отказ («Не подходит») — тот же ряд, но отдельный флаг `declined`, а не замена `proposed`: человек отвечает карточке дважды, и оба ответа могут остаться в силе — идея ушла в чат и потом разонравилась. Свёртка в один флаг вернула бы дефект стадии 63: вторая половина снова читала бы карточку неотмеченной и несла в чат второй экземпляр. Отвечается он только зрителю: поля «партнёр отклонил» в ответе нет, и сам флаг остаётся правкой личного списка. Но с стадии 95 отказ второй половины говорит о себе в переписке — он отвечает на уже вынесенную идею, план переходит в `declined`, и та же транзакция кладёт в нить строку `plan_declined`; отказ того, кто идею вынес, о паре ничего нового не сообщает и строки не пишет. Снятый отказ возвращается в нить как `plan_changed`, а если за идеей снова стоят обе половины — следом и `plan_accepted`. Отклонённая карточка не выбрасывается из ответа — она остаётся со своим `score` и `reasons`, чтобы отказ было кем отменить, и переживает пересборку страницы, потому что живёт в ряду решений, а не в собранной странице.
- Согласование времени — те же два ряда, но двумя `timestamptz`: `meeting_time` называет свой час, `accepted_time` фиксирует, на чужой час согласились. Договорённостью это становится не тогда, когда появляется третий флаг, а когда `accepted_time` одного равен `meeting_time` другого, и карточка отдаёт это как `agreed_time` обеим половинам. Два таких совпадения — обмен предложениями, а не план, поэтому `agreed_time` у обоих пуст: более ранний час напечатать значило бы выдать обещание, которого никто из двоих не держит. Согласившийся не становится предложившим (`proposed=false` на этой записи — иначе вернулся бы дефект стадии 63), но свой отказ снимает: назвать час и отклонить идею — два ответа, которые ряд не может держать одновременно. Времена читаются тем же единственным `SELECT activity_preferences`, что и три флага, поэтому страница не платит за них лишним round-trip'ом, и сравниваются мгновения, а не строки: у пары может быть два часовых пояса (миграция `c9b4e7a2d5f1`). (`0.6*|теги ∩ оба|/|теги| + 0.4*|теги ∩ хоть один|/|теги|`, вес 0.40) — собственный список тегов активности, поэтому каждый его элемент обязан быть slug'ом из каталога интересов: тем, что человек может выбрать на экране. Тег, которого в каталоге нет, никогда не попадёт в числитель и навсегда держит карточку ниже её же потолка, и никакая правка профиля это не поднимет. Так и было в семи из 25 списков каталога — `nature`, `food` и `art`, три из десяти названий групп, на которые каталог делит свои 40 интересов, — записанные там, где ожидался slug (стадия 61, миграция `7c4f2a91be36`). Инвариант охраняет `tests/test_an_activity_tag_nobody_can_select_caps_the_score.py`, а `activities.interests` читает только этот движок: ни API, ни клиент этого списка не видят.
- У пары есть и сама сущность договорённости. `shared_plans` — одна строка на `(match_id, activity_id)`, `shared_plan_members` — по строке на половину пары; час плана не хранится вторым местом, а является проекцией двух рядов `activity_preferences`, которые пересобирает `PlanService.sync_pair`. Правила часа при этом живут только в `app/services/plan_time.py` (`agreed_instant`, `unmatched_offer`, `validate_meeting_time`, `MIN_LEAD = 15 минут`), и ни одна дверь их не удваивает: `POST …/recommendations/{activity_id}/select`, `PUT …/time`, `POST …/time/accept` и `POST /plans/{plan_id}/hour[/confirm]` вызывают один и тот же сервис, поэтому страница идей, «Наши планы» и переписка двигают одну сущность, а не три её копии. Состояние (`_status`, `plan_service.py:205`) — один упорядоченный список проверок, а не флаг, который гладит каждая правка: отмена сильнее часа, который ещё лежит в рядах, а ответ, который человек изменил, сильнее часа, который был до него. Журнал плана — разница состояний до тапа и после него (`_journal` в транзакции вызывающего, `_newest_last` помечает `is_latest`), поэтому тап, который ничего не изменил, молчит, а строка, которая появилась, описывает час, который база действительно держит. С стадии 106 у этой сущности есть и её два слова — `place` и `note`, и пишет их одна дверь: `PATCH /plans/{plan_id}` → `plan_service.edit`. Она читает четыре слова тела раздельно: поле, которого в запросе нет, остаётся таким, как его держит строка, а снятие — это отдельный флаг `clear_place`/`clear_note`, поэтому пустая строка не может случайно стёреть чужое слово; сам сервис трогает только эти два поля и свою личную заметку, а час через него не двигается — передвинуть договорённый час значит спросить вторую половину снова, и для этого есть двери часа. Закрытый план (`cancelled`/`completed`/`declined`) отказывает (`409`), а строка журнала `plan_changed` идёт только тогда, когда пара слов действительно изменилась, — тот же принцип, по которому молчит тап по часу. На клиенте редактор живёт в карточке «Наши планы» (`WordsEditor` на `PlansScreen`), решение о том, что именно послать, вынесено в чистую функцию `planWordsEdit`, доступную JVM-тесту: она сравнивает введённое слово с тем, что отдаёт сервер, и не шлёт поле, которое человек не тронул.
- У плана есть два ответственных читателя, и оба читают ряд, а не догадываются о нём. `_decision`
(`plan_service.py:118`) снимает с двух флагов `activity_preferences` одно слово — `pending` / `joined` /
`declined` — и делает это в порядке, который и превращает подтверждение в обратимый ответ: стоящий отказ
читается раньше метки предложения, потому что метка снята быть не может (она сторожит повторную
отправку уже ушедшей в чат фразы — стадия 63). `plan_service` поэтому не заводит параллельного
жизненного цикла ответов: `shared_plan_members.decision` остаётся проекцией тех же двух флагов, а
`PlanService.sync_pair` пересобирает её на каждом чтении пары — второй источник состояния появился бы
из молча расходящегося с первым. Двери ответа (`select`/снятие отклонения на странице идей и
`accept`/`decline`/`DELETE decline` на детали) ведут в один и тот же глагол, вторая из пары вызывает
первый через `_pair_of`, поэтому «изменить свой ответ» — это тот же ряд, тронутый с любого экрана. Двери
ответа закрываются не симметрично: `_refuse_answer_closed` (`plan_service.py:88`) отсекает
`cancelled`/`completed` на подтверждении и на взятом обратно отказе, а свежий отказ пропускает у любого
статуса — забирать своё слово человек вправе и на закрытом плане, иначе пара осталась бы с
договорённостью, которую никто из двоих не может починить. `needs_my_answer` читается из собственного
слова смотрящего (`my_answer == DECISION_PENDING`) либо из часа, названного собеседником, — чужой долг
для этого есть `partner_decision`, и ни одно поле не решает за человека его ответ. На клиенте то же
одно правило держит чистая `canAnswerPlan` (`plans/PlanBuckets.kt`): карточка убирает двери и говорит
фразой (`planAnswerWord`) вместо тапа, который может только упереться в `409`, а
`planHourIsThePairWord` оставляет галочку часа ровно там, где на этом часе пара стоит, — унаследованный
от серверного порядка отказ её гасит, но сам момент не стирает.
- С стадии 108 вечер пары двигает любая из половин, а план сам знает, о каком часе он спрашивает.
Передвижение часа (`offer_hour`) писал ряд через `set_meeting_time`
(`repositories/activity_repo.py:94`) так, что под свежим часом оставался отказ и метка согласия на
старом часе: половина, которая только согласилась, не могла назвать вечер, не оставив себе двух
взаимно исключающих ответов, и `_decision` читал старый. Теперь тот же `ON CONFLICT DO UPDATE` снимает
`declined` и сохраняет `accepted_time` ровно тогда, когда он называет тот же самый час, — перенесённое
согласие перестаёт врать, что человек по-прежнему стоит на прежнем часу. Второе: у плана появился
собственный свидетель спрашиваемого часа. `_record_ask` (`plan_service.py:352`) после проекции рядов
кладёт `pending_hour`/`pending_by` на саму строку плана — когда договорённость ещё не состоялась и час
не совпадает с уже спрашиваемым, — а `_ask_of` (`:326`) верит этой записи ровно настолько, насколько
ряд спрашивающего по-прежнему называет тот же миг, и иначе возвращается к `unmatched_offer`. Причина в
том, что двух рядов для этого не хватает: две половины, назвавшие два разных часа, — это или пара,
которая ещё не сошлась, или пара, у которой один час только что передвинули, а различие между ними не
факт о рядах, а история плана, и только она решает, долетит ли вопрос переноса до второй половины.
Третье: дверь часа закрывается над состоявшейся встречей — `_refuse_closed` (`:85`) отвечает `409` и на
`completed`, потому что до этого `204` на таком плане стирал `starts_at` у встречи, о которой обе
половины уже отчитались. Четвёртое: строка `plan_changed` называет оба края изменения, а не одно поле —
`plan_change_sentence` (`services/plan_time.py:84`) собирает «место: не было → «улица»» из снятого и
поставленного словом (`FIELD_WORDS`, `_FIELD_NOTHING`, `_FIELD_REMOVED`), поэтому человек, пропустивший
кадр, читает из переписки то же, что видит экран; личная заметка (`my_note`) в общий журнал не
попадает. На клиенте история плана — отдельный экран (`PlanHistoryScreen` с
`PlanHistoryViewModel`, маршрут `planHistory/{planId}`), который читает те же строки
`GET /plans/{plan_id}`, что и чат: новой двери под него не заводилось, потому что второй источник
истории начал бы расходиться с первым.

### WebSocket-шлюз (`app/websocket/`)

- Эндпоинт `/ws/chat/{match_id}?token=<access>`.
- Авторизация по JWT на рукопожатии; невалидный токен → закрытие соединения с кодом `1008`.
- Проверяется участие пользователя в матче.
- Входящие типы: `message`, `typing`, `read`. Исходящие: `message`, `typing`, `read`, `presence`, `error`.

### Модерация жалоб

- Три маршрута чтения и решения (`app/api/v1/moderation.py`) стоят за одной дверью — `get_moderator`
  (`app/auth/deps.py:56`), которая берёт флаг из строки аккаунта на каждом запросе, а не из токена:
  JWT роли не переносит, поэтому снятое право перестаёт действовать со следующего запроса.
  Сервис (`app/services/moderation_service.py`) не знает, кто его вызывает, зато знает жизненный
  цикл: таблица `ALLOWED_TRANSITIONS` перечисляет, куда жалоба двигается из текущего состояния, два
  закрытых состояния (`resolved`, `dismissed`) — тупики с пустым множеством продолжений, а
  неправомерный переход, повтор того же статуса, пустой комментарий при закрытии и комментарий
  длиннее 1000 символов отвечают разными кодами (`422`, `409`), потому что клиенту нужно называть
  разное. Модератор не решает о себе: `reported_id == moderator_id` даёт `403` до всякой записи.
- Ряд разбора пишет две строки одним коммитом: `report_reviews` (кто, откуда, куда и с каким
  комментарием) и новый `status` самой жалобы (`app/services/moderation_service.py:141-143`).
  Читаемая перед записью строка берётся `FOR UPDATE`
  (`app/repositories/moderation_repo.py:30-35`), поэтому два модератора, ответившие на одну
  жалобу, оказываются последовательностью, а не двумя перекрывающимися решениями, и прогон,
  упавший до коммита, не двигает статус, оставляя историю молчать.
- Очередь листается парой `(created_at, id)` и лимитом не больше `MAX_PAGE = 100`, а не смещением:
  жалоба, пришедшая, пока человек на первой странице, не сдвигает вторую страницу под ним, а `id`
  разрывает равенство двух жалоб одной секунды, которое голый `created_at >` то потерял бы, то
  повторил. Под этот порядок в базе лежит `ix_reports_status_created_at (status, created_at, id)`:
  прежний `ix_reports_status` отвечал предикат и затем сортировал всю выбранную корзину в читателе,
  что было неважно, пока никто не читал этот предикат из маршрута, и стало важно, когда модератор
  пошёл по открытым жалобам снизу вверх; одноколоночный индекс — левая приставка нового — снят тем
  же переходом (`alembic/versions/b4e7d3a8c619…`).
- Модератору показывают ровно то, на чём решение делается: `accounts_for`
  (`app/repositories/moderation_repo.py:79-103`) читает имя, возраст, город и три флага
  (`is_deleted`, `is_hidden`, `is_moderator`) двух названных в жалобе аккаунтов — ни анкету, ни
  снимки, ни lifestyle-jsonb, ни почту. Возраст удалённого аккаунта не считается с его строки
  (`age_years` дала бы число, которым никто не был: удаление пишет свою дату рождения), а автор
  жалобы остаётся анонимным для того, на кого он написал, — адресат разбора об этом ничего не
  читает ни одним маршрутом продукта.

### Безопасность

- Пароли — bcrypt-хэш; refresh-токен хранится как SHA-256 и ротируется при обновлении.
- Ряды `refresh_tokens` читаются их владельцем и только владельцем, и это чтение не является дверью перечисления: `app/repositories/token_repo.py:76` (`live_for_owner`) фильтрует `revoked IS FALSE AND expires_at > now` по `user_id` из заголовка, а `:100` (`revoke_one_live_for_owner`) держит тот же предикат, что и `consume`, — чужой id, уже законченный id и id строки, которой никогда не было, отвечают одной `404`, поэтому список адресов не превращается в способ узнать, чьи сеансы существовали. Из ответа наружу не уходит ни материал токена, ни его хеш — это держит отдельная проверка ряда.
- Rate limiting — скользящее окно; отдельный лимитер для `/auth`.
- Загрузки изображений перекодируются Pillow (защита от вредоносных файлов), каталог загрузок отдаётся отдельно. Тело читается чанками с пределом (`read_upload_capped`), поэтому oversized-файл не проходит через память процесса целиком; объявленный холст проверяется до выделения пикселей. Предел размера тела на границе — задача reverse proxy (`client_max_body_size`): multipart-парсер пишет тело во временный файл до того, как его увидит код приложения.
- Секреты только в `.env` (исключён из Git). В логах не выводятся пароли, токены и чувствительные данные.

Пять файлов: `UniverseViewModel` (зовёт маршрут через `MatchRepository.universe`, а миры подписывает именами из `a_user_id`/`b_user_id` этого же ответа — не догадкой о том, кто открыл карту, — держит `mode` из трёх слов `UniverseMode` в том же состоянии, поэтому переключение чтения не шлёт второго запроса и не производит второй карты, и при 404 ставит `gone`, чтобы экран не предлагал «Повторить» там, где повтор не может сработать), `UniverseLayout` (чистая геометрия, доступная JVM-тесту: `place` раскладывает семь полос на метки по сторонам, `nodeAt` ищет узел под тапом с допуском 26 dp, `percentOf` переводит 0..1 узла в число, `shapeOf`/`linkOf` дают слову связи форму и тип линии), `UniverseStory` (слова переключателя, порядок полос для разбора — `analysisOrder` сортирует по весу, ничего не пересчитывая, и `storyShareText`, который кладёт рядом со строками движка только заголовок и оговорку) и `UniverseHandoff` (единственные слова, которые карта отдаёт полю ввода чата) и `UniverseScreen` (переключатель из трёх слов и три чтения над одним и тем же `state.data`: «Два мира» — Canvas в `Box` с `widthIn(max = 420.dp)`, легенда четырёх слов, четыре раздела по слову связи, тап раскрывает панель узла: `evidence`, уверенность (`assuranceSteps` рисует ряд из четырёх черт, `assuranceWord` подписывает его словом, а `unknown` читается как «сравнения не было»), совет движка и вопрос анкеты, из которого этот ответ взят, а под каждым таким вопросом — «Спросить в чате», который уводит пару в её же переписку с этим текстом в поле ввода (`UniverseHandoff.chatDraftFor` добавляет к вопросу только обрамление «Хочу спросить:»: ни процент, ни `evidence`, ни имя кого-то из пары в черновик не едут, и сам черновик экран не отправляет); в шапке карты живёт та же кнопка «Идеи для встречи», что и в шапке чата, — у карты два продуктовых выхода (чат с черновиком и идеи для пары) кроме «назад» и `ACTION_SEND` в чтении истории; «По полосам» — те же полосы сверху вниз по весу, с подписью `bandCaption`, значком процента только там, где `has_data` true (дефект 72-1), уверенностью полосы и её узлами, раскрытыми той же `NodeRow`; «Наша история» — строки `story` и кнопка «Поделиться», которая отдаёт собранный текст через `ACTION_SEND` и `text/plain`, а для ответа сервера, где `story` ещё нет, честно говорит об этом и гасит саму кнопку; панель и строка раздела раскрываются через `AnimatedVisibility` (`expandVertically` + `fadeIn`) и сворачиваются кнопкой «Свернуть», которая возвращает `onSelect(null)`). Чисел экран не производит: в `UniverseLayout` нет обращения ни к `score`, ни к `weight`, ни к `overall`, — полоса получает объект `UniverseLayer` целиком, поэтому у карты и экрана под ней не появилось бы второго источника процента. Разбор полос читает `weight` — но ровно для одного решения: какую полосу показать следующей; ни один процент здесь не пересобирается, включая вес, который история уже называет числом со стороны сервера (`int(round(...))` в Python, а не `roundToInt()` на Kotlin, чтобы две единицы не разъехались на половине). `unknown` рисуется одной меткой без линии: сравнения нет, и рисовать «встречу» запрещает то же правило, по которому движок отдаёт нейтраль. Доступность — `contentDescription` из `universeDescription(state)` на всей карте, а появление полос и раскрытие панели анимация пропускает, когда система выставила `ANIMATOR_DURATION_SCALE == 0` (полосы — `tween(Motion.Slow)`, панель — `tween(0)` в тех же `revealIn`/`revealOut`).
- **`presentation/common/ReportForm.kt`** — форма жалобы, живущая один раз, а не трижды по экранам.
  До стадии 102 её владелицей был `PublicProfileScreen`; когда к тем же двум вопросам пришли лента
  подбора и переписка, дублировать диалог означало бы дублировать не UI, а правила: о ком именно
  пишется жалоба, что происходит со вторым тапом, пока первый запрос в пути, и что человеку говорят
  после. Поэтому `ReportForm` — класс-владелец состояния (`StateFlow<ReportFormState>`), который
  экраны получают через `askReport(userId)` / `closeReport()`, а `ReportDialog` — единственный
  Compose-ряд, который это состояние рисует. Три вещи здесь держатся как инварианты, а не как детали
  вёрстки: `targetUserId` захватывается в момент открытия (карточка ленты уезжает сразу, как только
  тап засчитан, и жалоба, написанная позже, называла бы человека, которого никто не трогал),
  `sending` сверяется с состоянием, в которое пишется, поэтому второй тап не улетает на сервер
  вторичной жалобой или 409, который клиенту не растолковать, и предел текста (1000 символов)
  назван на клиенте тем же числом, что стоит на сервере (`details: Field(max_length=1000)` в
  `api/v1/safety.py`), — иначе длинный рассказ о плохом вечере возвращается ошибкой валидации,
  которую человек не может починить. Экрана очереди жалоб в клиенте до стадии 103 не было
  сознательно: чтение модератора жило на сервере (`api/v1/moderation.py`), и фиктивный экран со
  статическими данными обошёлся бы дешевле честного отсутствия. Стадия 103 добавила не фиктивный,
  а настоящий: `presentation/moderation/` (`ModerationViewModel.kt` + `ModerationScreen.kt` поверх
  `ModerationRepositoryImpl.kt`) читает те же три адреса — страницу очереди с фильтром по статусу и
  «Показать ещё» курсором, карточку с историей и `allowed_next_statuses`, диалог решения, — и
  рисует переходами тот же список, против которого сервер проверяет запись, поэтому закрытая
  жалоба не предлагает тап, способный только краснеть. Дверь на экран висит на `is_moderator`
  хозяйского ответа `/users/me…`, но показ двери защитой не считается: те же маршруты отвечают
  обычному аккаунту `403` на сервере, а роль читается со строки аккаунта на каждом запросе.

### Сетевое взаимодействие

- Все вызовы через `ApiService` возвращают `ApiResult<T>` — сетевые ошибки и не-2xx не бросают исключение, а превращаются в `ApiResult.Error(code, message)` (сообщение берётся из конверта ошибки backend).
- Автообновление access-токена настроено в Ktor `Auth` (bearer): при 401 выполняется `POST /auth/refresh`, токены обновляются в `TokenStore`. Отказ refresh (401/403 от самого `/auth/refresh`) очищает `TokenStore`; сетевая неудача refresh — не очищает.
- Все URL собираются в одном месте (`ApiConfig.joinUrl`: база без завершающего слэша + путь без ведущего). Разница важна: `/auth/refresh` вызывался единственной конкатенацией без нормализации, и база с завершающим слэшем давала `https://api.example.comapi/v1/auth/refresh`. Обновление не могло состояться, а это разрыв сессии на сборке, которую никто не тестировал.
- Судьба сессии решается по хранилищу токенов, а не по коду ответа: `RootViewModel` уходит на экран входа при 401 **и пустом `TokenStore`** (отказ refresh очищает хранилище сам). 401 с сохранёнными токенами означает, что refresh не состоялся вовсе — простой сервиса, перезапуск backend, отсутствие сети, — то есть сессия цела и пользователь остаётся в `MAIN`, где экран владеет «Повторить». 5xx и сетевые ошибки (`-1`) на `GET /users/me` тоже не разрыв сессии: иначе чужой простой сбрасывал бы вход без причины.
- У HTTP-клиента названа каждая фаза ожидания: `install(HttpTimeout)` в `HttpClientFactory.kt` объявляет connect 5 с, чтение и запись сокета 10 с и потолок целого вызова 35 с. До этого объявлен был только connect, а всё остальное доживало до унаследованного дефолта OkHttp — замер на этой связке (JVM, Ktor 3.0.1 + OkHttp, прогон `:app:testDebugUnitTest`): сервер, который принял соединение и молчит, был оборван на 10 063 мс с текстом ошибки `socket_timeout=unknown`, то есть границу держал движок, а не развёртывание, и по отказу нельзя было понять, какую цифру менять; ответ, прибывающий по чанку каждые 300 мс, не был оборван вовсе (читался 80 034 мс) — это то, что держит спиннер экрана открытым столько, сколько соединение производит байтов. Потолок в 35 с выбран выше измеренной очереди бэкенда (30.002 / 30.004 / 30.007 с, §7 `docs/OPERATIONS.md`), но досидеть эту очередь он не покупает: поставленный в очередь запрос не шлёт байтов, поэтому первым его обрывает строка тишины в 10 с — это производное от двух замеренных чисел, прогона против выдохшегося пула стадия не делала. Сама строка сокета объявляет ровно те десять секунд, которые держались дефолтом и до правки: стадия меняет название границы, а не время ожидания.
- Отдельные маршруты называют свои границы на уровне запроса. `ApiService.uploadPhoto` поднимает их (60 с тишины, 600 с на вызов), потому что длительность этой отправки — свойство канала загрузки, а не ответа сервера: на канале, отдавшем 2.4 МБ за 37 с, прежний унаследованный дефолт оборвал загрузку на 10 123 мс, пока байты ещё шли, а клиентский потолок — на 35 098 мс. На бездействие сокета эти числа не влияют — см. пункт про WebSocket.
- Чат: история/отправка — через REST (надёжная доставка и персистентность), realtime-события (входящие, typing, read, presence) — через WebSocket; входящие сообщения дедуплицируются по `id`. Сообщения и отметки о прочтении, принятые через REST, backend транслирует в `manager.broadcast_to_match`, поэтому открытый сокет второго участника получает их мгновенно.
- WebSocket-клиент установлен с `pingIntervalMillis = 10_000`, и эта правка переписала, что про этот интервал известно. Прямой съём байтов, которые клиент отправляет после рукопожатия, на немом собеседнике (стенд принимает соединение, отвечает 101 и больше ничего не читает и не пишет): за 60 с висения `incoming.receive()` на провод ушло **восемь байт** — `88 82 …`, то есть маскированный `Close` со статусом 1000, отправленный в момент, когда стенд сам отменил сессию, — и **ни одного `Ping`**; сессию стенд закрыл на 62 118 мс. Отсюда два вывода. Первый: прежнее утверждение, что keepalive-пинг заставляет оборванное без close-фрейма TCP соединение всплыть ошибкой чтения и что на этом держится переподключение `ChatSocket`, этой связкой не подтверждается — переподключение вызывает реальное завершение чтения (close-фрейм, ошибка транспорта, отказ рукопожатия), а чёрная дыра сама по себе не всплывает. Второй: объявленные границы REST-клиента на сокет не влияют — то же соединение жило всё окно прогона и при `socketTimeoutMillis = 15 s`, и при `requestTimeoutMillis = 35 s`. Интервал оставлен как стоял: подъём heartbeat-механики — новое поведение, а не правка названных чисел, и стадия его не делает. События публикуются через `tryEmit`, чтобы переполнение буфера не могло заморозить петлю reconnect.
- WebSocket не может инициировать обновление токенов (токен передаётся query-параметром при рукопожатии), поэтому `ChatSocket` перед подключением выполняет probe-запрос `GET /users/me` через REST-клиент с автообновлением
- Клиент называет себя сам: `defaultRequest` (`HttpClientFactory.kt:200`) кладёт в каждый вызов заголовок `User-Agent`, собранный `befosUserAgent` (`:85`) из версии сборки, модели и релиза Android — `BeFoS/<version> (<model>, Android <release>)`. Форму выбрал не вкус, а ряд стадии 110: аккаунт читает свои устройства ровно по этому столбцу, и без него все его строки названы библиотекой. Два падения здесь названы и дороже, чем красивое слово: `asHeaderWord` (`:93`) выбрасывает символы вне печатного ASCII, поэтому кириллическое имя модели исчезает из строки целиком, а ряд остаётся хорошо сведённым — сверка держит и это, и отсутствие висячей запятой, которую человек прочёл бы как сломанное имя; и потому что каждое обращение приложения проходит через эту функцию, устройство, которое о себе ничего не сказало (`Build` в JVM-тесте отвечает `null`), деградирует до `BeFoS/<version> (Android)` вместо исключения по всему пути. и берёт свежий access-токен из `TokenStore`.

## Наблюдательность

- Каждый HTTP-запрос получает correlation id в `X-Request-Id`: клиентский id принимается только если он является одним печатным токеном `[A-Za-z0-9_.-]{1,64}`, иначе генерируется свой 16-hex. Значение возвращается в заголовке ответа — по нему пользователь или поддержка называет конкретный запрос.
- Формат лога — `время | уровень | логгер | request_id | сообщение`. Id берётся из `contextvars` (`RequestIdFilter`), поэтому error-строка, analytics-событие и access-строка одного запроса читаются как одна история.
- `befos.access` пишет `request METHOD path -> STATUS in X ms`; дольше 1000 мс — отдельный `WARNING slow request`; `/api/v1/health` уходит в DEBUG, чтобы пробы живости не заполняли поток. Middleware — чистый ASGI, а не `BaseHTTPMiddleware`: сокеты проходят сквозь него нетронутыми.
- Жизненный цикл WebSocket пишется целиком: отказ без пригодного токена и отказ «не пара» (WARNING с причиной), connect, disconnect с числом оставшихся слушателей в комнате, close с длительностью соединения, `WS room closed` при блоке или удалении аккаунта.
- В лог не попадают пароли, access/refresh-токены и заголовок `Authorization`; строка запроса пишется без query-части (рукопожатие сокета несёт токен именно там), а `SensitiveFilter` дописывает `[redacted]` к `token=`, `"password":` и похожие ключи в строках uvicorn.
- Покрыто набором `backend/tests/test_observability.py` (19 тестов), включая проверку, что заголовок-инъекция не может дописать вторую строку в лог.

## Надёжность данных

- Соединение берётся из пула до хэндлера (`get_session`), а не на первом его запросе:
  разрыв, который сервер успел закрыть в момент выдачи, стоит запросу одну повторную
  попытку взять соединение, а не оборванный на середине хэндлера. Если не вышло и дважды — 503
  `database_unavailable` с `Retry-After: 5`; текст ошибки драйвера (host, user, пароль
  строки подключения) клиенту не показывается никогда.
- `/health` утверждает только «процесс жив», `/health/db` — «соединение берётся и `SELECT 1`
  выполняется». Healthcheck контейнера читает первое, алерт должен читать второе: при
  упавшей базе контейнер остаётся healthy, и перезапуск backend этому не помогает.
  Измерено на `docker restart befos_postgres`: outage ~2.1 с, за него backend отдал 503 и
  200, ни одного 500.
- Копиируются всегда оба тома (дамп базы + архив `myapp_befos_uploads`), копия проверяется
  восстановлением в отдельную базу и сверкой отпечатка (`backend/ops/backup_fingerprint.sql`),
  а не тем, что `pg_restore` вышел с нулём. Том Docker резервной копией не является.
- Порядок фото в списке — одно правило на весь код (`PHOTO_DISPLAY_ORDER`: выбранное
  владельцем, затем `position`, затем `created_at`/`id`). Сортировка только по `position`,
  который у всех строк 0, — порядок строк с одинаковыми значениями, то есть heap-порядок,
  который `VACUUM` переписывает; экраны берут `photos[0]` как аватар, поэтому ответ обязан
  быть фактом, а не удачей.
- Удаление аккаунта забирает и строки `photos`, и файлы (после commit, чтобы неудачная
  транзакция не оставила базу, указывающую на несуществующее). Сокрытие анкеты этим не
  является: `/uploads` — публичная статика без авторизации, и url, который кто-то успел
  открыть, отвечает, пока лежит файл.
- Расторжение пары тем же рядовым порядком не оставляет висящего: `matches_service.dissolve` берёт
  advisory-замок пары до удаления, поэтому сообщение, план или отметка о прочтении, написанные в тот же
  миг, дожидаются и получают 404, а не FK 500 — тот же инвариант, что держит блокировка. Комната
  закрывается (`manager.close_room`) после коммита, а не до него: сокет, открытый на строку, которой уже
  нет, должен получить отказ от состояния базы, а не от порядка вызовов внутри запроса.
- Порядок и детали — [`docs/OPERATIONS.md`](OPERATIONS.md).

## Деплой

`docker-compose.yml` поднимает `postgres` (16-alpine) и `backend`. При старте backend применяет миграции (`alembic upgrade head`), сеет данные (`python -m app.seed --if-empty`) и запускает `uvicorn`. Загрузки хранятся в именованном томе `befos_uploads`, БД — в `befos_pgdata`. Оба тома — единственное состояние, и ни один из них копией не является (см. выше). У backend есть healthcheck на `/api/v1/health` с `start_period=60s`, потому что миграции и сид выполняются в той же команде, что и сервер. Android-клиент собирается отдельно (`:app:assembleDebug`).

Сев справочников с стадии 71 называет и расхождение: строку interests, активностей или анкеты,
которая в базе отличается от каталога, `_seed_catalogs` выписывает в `WARNING` и не переписывает.
Практический смысл для развёртывания: правка каталога не доезжает до базы, где строки уже есть,
пока её не перенесёт отдельная ревизия данных, и из-за самого расхождения запуск контейнера не
падает. Детали и путь ремонта — `docs/OPERATIONS.md`, §17.

## Push: архитектура подготовлена, реализации нет

Приложения, которое будит человека, когда он не смотрит в экран, в проекте нет, и это не
забытая галочка, а решение: FCM-проект и сервисный аккаунт не заведены, поэтому любой «push-клиент»
в этом репозитории был бы декорацией — код, который ничего не доставляет, но выглядит как
доставка. Декораций тут не заводят (пароль демо-аккаунта, «realtime» без сокета, подписанный релиз
без ключа — все эти границы уже пройдены и описаны в `docs/RELEASE.md` §11). Ниже — что должно
произойти, когда появятся credentials. Швы указаны существующими строками кода, чтобы план нельзя
было прочитать как описание уже сделанного.

### Куда это встанет

| Событие | Точка в коде | Что она уже делает |
| --- | --- | --- |

Отправка не становится отдельной подсистемой: она происходит из тех же двух мест, что и
WebSocket-кадр, и обязана пройти те же проверки, что и кадр.

### Модель данных

`push_tokens`: `user_id` (FK на `users`), `device_token` (уникальный), `platform`, `created_at`,
`last_seen_at`, `revoked_at`. Смысл колонок не в статистике, а в двух отказах: протухший токен
(FCM отвечает `UNREGISTERED`) должен вычёркиваться, а не переотправляться каждый раз, и удаление
аккаунта обязано забирать токены тем же путём, которым оно забирает ответы теста и фото, — иначе
«стёртый» человек остаётся адресуемым устройством.

Register-токен клиента попадает в базу как чувствительные данные: он даёт право показывать на этом
устройстве что угодно от имени backend. Поэтому он не выводится в логи (правила
`docs/OPERATIONS.md` §10 про это же), не возвращается ни в одном ответе API и не участвует в
отладочных дампах.

### Правила доставки, которые уже решены в коде

1. **Не будить того, кто уже здесь.** `presence` знает, кто в комнате; уведомление про сообщение
   в паре, где получатель сидит в сокете, — это двойной сигнал и лишняя трата доверия.
2. **Блокировка работает и на пуш.** Стена стоит на `404`/`WS 1008` и перепроверяется в
   `_refusal_reason`; уведомление обязано проверять её до формирования текста, иначе push обогнал
   бы блокировку и показал то, что человек прятал.
3. **Идемпотентность.** У сообщения уже есть `client_msg_id` и уникальный индекс; повторная
   доставка сообщения не имеет права дать повторное уведомление — то же самое, что уже сделано для
   повтора отправки.
4. **Одно уведомление на пачку.** Сообщение в чате — событие частое; отправке нужен группирующий
   ключ (`match_id`) и потолок, иначе десять ответов подряд превращаются в десять вибраций.

### Содержимое уведомления

Заголовок — имя пары, текст — «Новое сообщение», а не сам текст. Сообщение пары — это приватный
разговор, и показывать его на чужом lock screen (и складывать в очередь вендора) — то же
нарушение, которого избегают правила про логи. Для «у вас пара» содержательный текст нужен, и он
безопасен: там нет чужих слов.

### Что требуется, чтобы это стало реальным

FCM-проект и сервисный аккаунт с credentials (вне git, как `keystore.properties`), добавление
Android-приложения в Firebase, `GoogleApiManager`/HTTP v1 на backend, эндпоинт
`POST /devices` с отзывом на `logout`, и тестовое устройство. До этого здесь остаётся этот раздел —
он и есть «подготовленная архитектура»: схема, швы и ограничения известны, и включение не
затронет половину сервисов.

## Резюме архитектуры (для защиты проекта)

Один запрос — весь путь данных, без «магии»:

```
Android (Compose UI → ViewModel → Repository)
   ↓  REST (JSON, Ktor) / WebSocket
FastAPI (маршруты api/v1)
   ↓
Services (бизнес-логика, не знает про HTTP)
   ↓
Repositories (SQLAlchemy 2.0 async)
   ↓
PostgreSQL 16 (25 модели + alembic_version)
```

- **Compatibility Engine** (`app/compatibility/`): семь взвешенных категорий —
  ценности (0.25), характер, интересы, коммуникация, образ жизни (по 0.15), досуг (0.10), цели (0.05);
  `Score = Σ normalize(component_i) × weight_i`, Σ weights = 1.0. Детерминирован: одинаковый вход →
  одинаковый результат; версия движка (`ENGINE_VERSION`) фиксируется в каждом ответе. Отсутствие
  ответа — не ответ: `NEUTRAL_SCORE = 0.5` держит категорию нейтральной там, где сравнивать нечего,
  и со стадии 60 так же ведут себя интересы, когда хоть один из двоих не назвал ни одного интереса
  (прежняя ветка отдавала за это `0.0` с данными, то есть чужой пропуск стоил ответившему половины
  веса категории; два названных непересекающихся набора остаются расхождением). Результат
  сопровождается объяснением (сильные стороны, отличия, общие интересы) — всё выводится из реальных
  данных пары. Это инженерная эвристика на основе анкет и теста, а не психологическая диагностика.
- Вектор ответов ключуется полями самой строки вопроса (`category`, `trait`), поэтому каталог
  вопросов и таксономия `traits.py` обязаны сходиться. Держит это путь записи ответа:
  `TestService._require_declared_axes` отказывает пачке `POST /tests/answers`, если вопрос называет
  категорию или ось, которых в таксономии нет, — и делает это до первой записи, поэтому отказ не
  двигает ни уже данные ответы, ни сохранённый вектор (стадия 69). Без сверки лишняя ось попала бы
  в пересечение ключей `_trait_similarity` и сдвинула категорию пары на своё среднее.
- **Recommendation Engine** (`app/recommendations/`): каталог активностей с сигналами
  `energy / social / cost`; оценка пары по интересам, досугу, образу жизни, городу и цели знакомства
  обоих. interests-компонента (вес 0.40) делит покрытие карточки на её собственный список тегов,
  поэтому каждый тег каталога — выбираемый интерес, а не название группы интересов: иначе потолок
  оценки держится мёртвым знаменателем (стадия 61). Пять весов лежат в одном словаре `WEIGHTS`, и
  сумма проверяется при импорте — так же, как `WeightConfig.validate()` у движка совместимости:
  потолок страницы равен этой сумме, ниже 1.0 он опускается молча, а выше 1.0 поломку не видно
  вовсе, потому что `_clamp01` насыщает сумму до 1.0 (стадия 68). Каждая рекомендация несёт `score`,
  позицию и человекочитаемые `reasons`, плюс отметки и часы из `activity_preferences`, снятые одним
  чтением на страницу: `selected` — что этот читатель уже предлагал идею этой паре (стадия 63),
  `partner_selected` — что это сделал собеседник, чтобы экран пары показывал совпадение, а не
  два одинаковых предложения в чате, `declined` — что этот читатель карточку отклонил (отказ
  называется только ему), и четыре поля времени — чей назван час, на чужой он согласился и сошлась
  ли пара на одном (`agreed_time`, стадия 81.2).
- **Realtime Chat**: WebSocket `/ws/chat/{match_id}` с JWT-авторизацией на рукопожатии и проверкой
  участия в матче. Надёжность доставки даёт REST (сообщение сохраняется в БД и транслируется второму
  участнику через `broadcast_to_match`); сокет отвечает за мгновенность (входящие, typing, read,
  presence). Клиент: keepalive-пинг 10 с, авто-переподключение с backoff, дедупликация по `id`.
- **Authentication**: JWT access + refresh; refresh хранится на сервере как SHA-256 и ротируется при
  каждом обновлении; на клиенте — DataStore, автообновление по 401 в Ktor `Auth`. WebSocket перед
  подключением получает свежий токен через probe `GET /users/me` (сокет не может сам инициировать refresh).
- **Security**: bcrypt для паролей; скользящий rate limiting (отдельный лимитер `/auth`); CORS без
  wildcard+credentials, в production — только https-origins; конфигурация отклоняет плейсхолдер- и
  короткие/совпадающие JWT-секреты при `ENVIRONMENT=production`; загрузки изображений перекодируются
  Pillow; SQL-инъекции исключены параметризацией SQLAlchemy; авторизация проверена IDOR-набором тестов.
