# Эксплуатация BeFoS

Документ о том, как это живёт, ломается и чинится. Всё, что здесь написано про цифры,
измерено на dev-стенде этого репозитория (PostgreSQL 16 в Docker, backend в Docker, один
узел) и датировано на месте, рядом с числом: прогон 2026-10-06 старше не делает — замер
2026-10-04 остаётся замером 2026-10-04, а не сегодняшним днём. Команды — однострочные и
работают в PowerShell.

## 1. Что резервируется, а что нет

Два состояния, оба вне контейнеров:

| Что | Где лежит | Имя тома | Измеренный объём |
|-----|-----------|----------|------------------|
| Данные (аккаунты, тесты, совместимость, чаты, колода подбора) | `/var/lib/postgresql/data` | `myapp_befos_pgdata` | 158 МБ на диске (кластер целиком: `befos` 12 МБ + тестовая `befos_test` 11 МБ + WAL) |
| Загруженные пользователями фото | `/app/uploads` | `myapp_befos_uploads` | 3.9 МБ, 131 файл (58 из них имеют строку в `photos`) |

**Том Docker — не резервная копия.** Это рабочая directory того же диска того же хоста:
она переживает перезапуск контейнера и не переживает `docker volume rm`, переустановку
Docker, удалённый с ошибкой каталог и dying диск. Единственная команда в этом репозитории,
которая уничтожает оба сразу, — `docker compose down -v`; её не надо вводить на живом
стенде никогда.

Резервная копия — это файл вне контейнера, который можно положить на другой носитель.

## 2. Снятие копии

Копируются оба тома, отдельно и всегда парой: копия базы без фотографий рисует профили
пустыми, копия фотографий без базы — набор файлов, которые никто не показывает.

База — в custom-формате `pg_dump`, потому что он сжат, восстанавливается выборочно и не
зависит от того, что кто-то пишет в базу во время снятия копии:

```powershell
docker exec befos_postgres sh -c "pg_dump -U befos -d befos --format=custom --compress=6 -f /tmp/befos.dump"
docker cp befos_postgres:/tmp/befos.dump "C:/backups/befos-$(Get-Date -Format yyyyMMdd-HHmmss).dump"
```

Измерено 2026-10-07: 0.85 с, 259 931 байт на выходе (база 12 МБ, 23 таблицы, 62 индекса).
Предыдущий замер того же шага — 2026-10-06: 0.99 с, 256 КБ, 77 индексов; разница в индексах —
миграция `e6b28c4a13d0`, снявшая 15 ключей, которые были левым префиксом другого индекса той же
таблицы.

Фотки — архивом тома, на снимке только для чтения, чтобы записи во время копирования не
дали смешанный набор файлов:

```powershell
docker run --rm -v myapp_befos_uploads:/data:ro -v C:/backups:/out alpine tar czf /out/uploads-$(date +%Y%m%d-%H%M%S).tgz -C /data .
```

Измерено 2026-10-05: 2.5 МиБ, 51 файл — ровно по числу строк в `photos`.

Дамп — это персональные данные: тексты чатов, адреса, ссылки на фотографии, хэши паролей.
Файл не кладётся в git (проверка: `git status` после снятия копии должен быть чистым —
копия пишется вне репозитория именно поэтому) и не лежит на том же хосте, что и оригинал.

## 3. Проверка копии: drill, а не надежда

Копия, которую ни разу не восстанавливали, — это предположение. Drill делает его
фактом за две минуты и ничего не трогает в рабочей базе: восстановление идёт в
отдельную базу на том же кластере, сравнивается отпечаток, затем база удаления.

```powershell
docker cp "C:/backups/befos-<timestamp>.dump" befos_postgres:/tmp/befos.dump
docker exec befos_postgres sh -c "dropdb -U befos --if-exists befos_restore_drill && createdb -U befos -O befos befos_restore_drill"
docker exec befos_postgres sh -c "pg_restore -U befos -d befos_restore_drill --no-owner --exit-on-error /tmp/befos.dump"
```

`--exit-on-error` здесь обязателен: pg_restore по умолчанию печатает ошибку и продолжает,
то есть молча возвращает неполную базу. Измерено: восстановление 2.2 с.

Отпечаток — `backend/ops/backup_fingerprint.sql`, одна и та же программа против рабочей
базы и против копии:

```powershell
docker cp backend/ops/backup_fingerprint.sql befos_postgres:/tmp/fp.sql
docker exec befos_postgres sh -c "psql -U befos -d befos -X -q -P pager=off -f /tmp/fp.sql" > source.txt
docker exec befos_postgres sh -c "psql -U befos -d befos_restore_drill -X -q -P pager=off -f /tmp/fp.sql" > restored.txt
Compare-Object (Get-Content source.txt) (Get-Content restored.txt)
```

(`psql` есть только в контейнике базы, файл надо положить туда — в образ backend он не
копируется, хотя `ops/backup_fingerprint.sql` в нём лежит.)

Пройденный drill 2026-10-07 (поверх миграции `e6b28c4a13d0`): вывод совпал целиком — 52 строки,
23 таблицы построчно (`users=270`, `profiles=270`, `messages=46`, `message_reads=65`,
`test_answers=1284`, `discovery_queue=357`, `refresh_tokens=642`), `alembic=e6b28c4a13d0`,
**62 индекса**, 4 sequence. Дамп — 0.85 с (259 931 байт), восстановление — 1.73 с. План чтения
входа на копии — в следующем разделе.

Предыдущий проход той же проверки — 2026-10-06, после миграций `c5a7d1e0b342` и
`d8f4b2c6a157`: 52 строки, `users=264`, `alembic=d8f4b2c6a157`, 77 индексов, 4 sequence; дамп
0.99 с (256 КБ), восстановление 1.80 с. Ещё раньше, 2026-10-04 после `9c1f5b7d2a40`: 23 таблицы,
`users=198`, 75 индексов. Между этими замерами были `uq_discovery_queue_viewer_rank` и
`uq_users_email_lower` (добавили два индекса) и `e6b28c4a13d0` (снял пятнадцать), и именно
поэтому число в отпечатке менялось, а не потому что копия стала другой.

Индексы проверяются не количеством, а тем, что копия остаётся пригодной для чтения:
`pg_restore --exit-on-error` проходит целиком (то есть восстановлены и частичный уникальный
индекс `uq_message_sender_client_id`, и `ix_profiles_city_lower_birth`, и оба новых
уникальных), и план чтения на восстановленной базе показывает живой индекс — без единой
подсказки planner'у. Снимок 2026-10-06:

```
->  Index Scan using uq_users_email_lower on users (actual time=0.045..0.046 rows=1 loops=1)
      Index Cond: (lower((email)::text) = 'demo@befos.app'::text)
Execution Time: 0.187 ms
```

Проход 2026-10-07, уже поверх `e6b28c4a13d0`, даёт на той же копии тот же `Index Scan` за
`0.293..0.295 мс` (`Execution Time: 0.420 мс` с планированием 2.508 мс на холодном кэше) —
то есть удаление пятнадцати индексов не тронуло чтение, которое осталось в схеме.

Это то самое чтение, которое вход и регистрация делают на каждом запросе: на копии оно
отвечает индексом, на рабочей базе — тоже (`0.276 мс`), и до этой правки оба читали таблицу
целиком. В наборе `backend/tests/test_db_reliability.py` то же утверждение стоит под
`SET enable_seqscan=off` не потому, что индекс не выбирается, а потому, что тестовая база
растёт до нескольких сотен строк, и там выбор planner'а — это про стоимость, а не про
наличие индекса.

С планом подбора надо быть точнее, чем хотелось бы. Тот же `EXPLAIN` на восстановленной базе
для формы с городом (`lower(p.city) = 'москва'` плюс диапазон по `birth_date`) даёт
`Bitmap Index Scan on ix_profiles_city_lower_birth` с обоими условиями в `Index Cond` за
0.458 мс — но **эта форма написана руками, и на момент замера из API она прийти не могла**:
`city_preference` не писал ни один эндпоинт (так было до правки стадии 104), поэтому в
реальном чтении кандидатов город не связывается вовсе, и остаётся один диапазон возрастов,
где planner на рабочей базе выбирает `Seq Scan`. С правки стадии 104 город поиска пишется
`PATCH /users/me`, и названный город связывает ведущую колонку в живом запросе, — но этот
EXPLAIN на такой трафик никто не переснимал. Drill
поэтому доказывает про это чтение не «горячее чтение подбора использует индекс», а «индекс
на копии пережил дамп и восстановление и годен к использованию». Копия, потерявшая индексы,
возвращается медленнее, чем была рабочая база, и это единственный способ заметить это до
аварии.

Второе, что показывает только что восстановленную базу и чего не видно на рабочей: первый
запрос к `discovery_queue` после `pg_restore` выполнился за 436 мс, тот же запрос вторым
проходом — за 0.486 мс. Разница — холодный page cache виртуальной машины Docker, а не
схема и не планы: страницы индексов и таблиц после восстановления читаются с диска.
Поэтому время отклика после восстановления измеряют вторым-третьим прогоном, а не первым,
и иначе drill нашёл бы «проблему производительности», которой нет.

После сверки: `docker exec befos_postgres sh -c "dropdb -U befos befos_restore_drill"`.

## 4. Восстановление после потери данных

По-настоящему destructive вариант — поверх рабочей базы. Порядок ровно такой, потому что
обратного хода у него нет:

1. Остановить backend, чтобы копии не расползались под руками:
   `docker stop befos_backend`.
2. Снять копию с того, что осталось (пусть даже повреждённого) — это единственный шанс
   разобрать потом, что именно пропало.
3. Пересоздать базу и восстановить:
   `docker exec befos_postgres sh -c "dropdb -U befos --if-exists befos && createdb -U befos -O befos befos && pg_restore -U befos -d befos --no-owner --exit-on-error /tmp/befos.dump"`
4. Поднять том фото, если потеряны и они:
   `docker run --rm -v myapp_befos_uploads:/data alpine tar xzf /in/uploads-<timestamp>.tgz -C /data`.
5. `docker start befos_backend`, дождаться healthy, проверить `/health/db`, затем
   `alembic current` — он должен показать тот же `revision`, что и отпечаток копии.

не после.

## 5. Ретенция и копия вне хоста

Правило, которое надо исполнять: ежедневно, 14 дневных копий парами (dump + tar), одна
недельная на 8 недель, копия минимум на одном носителе вне хоста. Перед любым
`docker compose down -v`, любым изменением миграций и любым `pg_restore` — копия и drill.

Автоматизации здесь нет, и это не забыто, а заблокировано: для выгрузки вне хоста нужен
адрес и ключ (S3/RSYNC/иное), а реальные секреты в этот репозиторий не кладутся. Локальная часть работы сделана — команды выше исполнимы, отпечаток сравним, drill проходит, —
не хватает только строки назначения. Планировщик (cron/tasks) добавляется вместе с ней.

## 6. Миграции

Миграции накатываются при старте контейнера (`Dockerfile`/compose command:
`alembic upgrade head && python -m app.seed --if-empty && uvicorn ...`). На одном реплике
это удобно. На двух репликах, поднимающихся одновременно, это гонка два `upgrade head`
против одной базы: Alembic не блокирует, и вторая попытка падает на уже существующем
объекте. Поэтому правило перед горизонтальным масштабированием такое:

1. Убрать `alembic upgrade head` из команды контейнера.
2. Накатывать миграции отдельным шагом релиза:
   `docker compose run --rm backend alembic upgrade head`.

Порядок релиза с миграцией всегда: копия → drill → `alembic upgrade head` → новый образ
backend → e2e. Этот порядок — не ритуал, а следствие того, что и миграция, и код меняют
одну и ту же таблицу: на копии без `uq_message_sender_client_id` вставка идемпотентной
отправки падает ещё до всякого кода приложения (`ERROR: there is no unique or exclusion
constraint matching the ON CONFLICT specification` — измерено на базе drill с
преднамеренно удалённым индексом, транзакция откатана, индекс на месте). Откат:
`alembic downgrade -1` существует в каждом ревизии, но downgrade
`4f2a1c9d7b30` удаляет таблицу `discovery_queue` вместе с историей показов, а downgrade
`9c1f5b7d2a40` снимает и `client_msg_id`, и уникальный индекс по нему — то есть откат schema
под кодом, который на неё опирается, это потеря данных, а не откат кода. Если потеря
приемлема, откатываются вместе с кодом, если нет — восстанавливают копию.

Две последние ревизии в этом смысле другие, и это проверено на копии, а не на пустой базе.
Прогон 2026-10-06 против `befos_restore_drill` (264 пользователя, 357 строк колоды):
`downgrade -1` дважды подряд снимает `uq_users_email_lower` и
`uq_discovery_queue_viewer_rank`, не трогая ни одной строки, `upgrade head` возвращает оба
индекса, и на входе и на выходе `discovery_queue=357`, `users=264`, `alembic check` чист.
Отпечаток после этого отката и повторного наката совпадает с отпечатком рабочей базы целиком,
все 52 строки — то есть downgrade и upgrade не оставили базу в состоянии «схема та же, а
объекты другие».
Откат индекса — это откат скорости, а не данных; именно поэтому `c5a7d1e0b342` и
`d8f4b2c6a157` переживают drill в обе стороны, тогда как `4f2a1c9d7b30` в downgrade
уничтожает историю показов. Обратная сторона медали: повторный `upgrade` после отката
заново выполняет `DELETE` коллизий рангов и `UPDATE` регистра адресов — на копии с 357
строками и 264 пользователями оба прошли за нуль изменённых строк, потому что коллизий там
нет, но на базе, где между откатом и накатом успели вставить дубликат почты в другом
регистре, `upgrade` упадёт на шаге нормализации и не даст базе половину схемы.

Проверка соответствия моделей и схемы: `docker exec befos_backend sh -c "cd /app && alembic
check"` → `No new upgrade operations detected`. Раньше он врал: `discovery_queue` и
`user_interests` объявлялись с отдельным `UniqueConstraint` поверх тех же колонок, что и
первичный ключ, Postgres повышал этот уникальный индекс до PK, и autogenerate вечно
предлагал добавить ограничение, которое уже есть и добавить дважды нельзя. Сейчас эти два
ограничения объявлены как `PrimaryKeyConstraint` с теми же именами, что были заведены
миграцией: `uq_user_interest` назван явно в `ON CONFLICT (constraint ...)`, а
`uq_discovery_queue_pair` остался в схеме как имя первичного ключа — код постановки в колоду
после `c5a7d1e0b342` имени арбитра не указывает, так что переименование было бы миграцией
ради имени, а не ради поведения.

Перед мержем любой новой миграции: `alembic check` чист, `pytest` зелёный, `EXPLAIN
ANALYZE` на горячем чтении (см. `docs/DATABASE.md`), и миграция не содержит `DROP COLUMN`
без отдельного решения о данных.

Тестовая база устроена иначе: `backend/tests/conftest.py` строит схему через
`Base.metadata.create_all`, а `create_all` никогда не меняет уже существующую таблицу. После
правки моделей `befos_test` сохраняет прошлую схему, и тесты падают на `UndefinedColumnError`
(так произошло с `client_msg_id`). Пересоздание — это одна строка, и терять там нечего, кроме
строк, которые conftest и так вычищает между тестами:

```powershell
docker exec befos_postgres sh -c "dropdb -U befos --if-exists befos_test && createdb -U befos -O befos befos_test"
```

Если в тестовой базе что-то лежит и терять это нельзя, её доводят миграцией как обычную:
`alembic stamp <предыдущая ревизия>` против `befos_test` (таблицы `alembic_version` в ней нет,
поэтому без stamp `upgrade head` пойдёт накрывать уже существующие объекты) и затем
`alembic upgrade head`. Проверено 2026-10-04 на `9c1f5b7d2a40`: после stamp+upgrade частичный
уникальный индекс `uq_message_sender_client_id` в `befos_test` и в `befos` одинаковый.

С 2026-10-11 (стадия 64) прогон на устаревшей стендовой схеме не доживает до конца: `conftest`
сверяет `Base.metadata` с отражённой схемой сразу после `create_all` и завершает запуск через
`pytest.exit` с кодом 1, называя каждую разбежку таблицей и колонкой — отсутствующую колонку,
сузившийся уникальный ключ, пропавшее имя индекса и лишнюю таблицу, — плюс выход (`dropdb`/`createdb`
выше, либо `BEFOS_TEST_DB=befos_test_2`). Замерено на стенде, собранном до стадии 63: прежний прогон
давал 11 failed и 4 errors за 684.09 с (12:05:28…12:16:52 UTC), нынешний отказывает за 1.78 с,
«no tests ran»; те же семь файлов на пересобранном стенде — 59 passed за 133.60 с, то есть падал
стенд, а не продукт. Двум ложным обвинениям отказ не учится: индексу, собранному на выражении
(`ix_profiles_deck_order` ведёт `created_at DESC`, поэтому на модели и на отражённой стороне колонки
разные), и таблице `alembic_version`, которую цепочка миграций оставляет на стенде намеренно.

## 7. Пул соединений и его математика

`backend/app/core/database.py`: `pool_size=10`, `max_overflow=20`, `pool_timeout=30`,
`pool_pre_ping=True`, `pool_recycle=1800`.

Числа ниже сняты 2026-10-09 на этом стенде (backend-контейнер + PostgreSQL 16, другой нагрузки
в момент замера нет); способ замера — в конце раздела.

- Потолок одного процесса — 30 соединений, и он измерен, а не сложен. 45 одновременных заёмов
  у пула, собранного из тех же чисел, дали ровно 30 разных `pg_backend_pid()`; остальные 15
  получили отказ: `sqlalchemy.exc.TimeoutError`, «QueuePool limit of size 10 overflow 20
  reached».
- Ждут они ровно `pool_timeout`. Отказы наступили через 30.002 / 30.004 / 30.007 с. Это значение
  было дефолтом SQLAlchemy, которого в коде не называли, а на нём держится вся арифметика этого
  раздела, поэтому `pool_timeout=30` теперь стоит в `database.py` явно, и страница сверяется с
  движком проверкой `backend/tests/test_pool_capacity.py`. Заметим, что со стороны Android-клиента
  это ожидание до конца не досиживается: клиент обрывает молчание на 10 с (`socketTimeoutMillis` в
  `HttpClientFactory.kt`, замер стадии 47 — молчащий сервер оборван на 10 063 мс), поэтому
  31-й запрос при выдохшемся пуле покажет пользователю «Сервер не отвечает. Попробуйте ещё раз.»
  раньше, чем наступит 503 с `Retry-After`. Это производное от двух замеренных чисел — прогона
  выдохшегося пула вместе с телефоном в паре не делалось. Уменьшать его замер не советует: при
  тех же 45 заёмщиках, держащих соединение по 3 с, последняя волна ждала 6.15 с и была
  обслужена — порог в 5 с превратил бы её в отказы.
- Сервер этого стенда держит 100 клиентских бэкэндов. 96 соединений пробы, её собственное
  соединение-наблюдатель и 3, которые уже держал backend-контейнер, — 100 принятых; 101-я
  попытка получила `asyncpg.exceptions.TooManyConnectionsError` («sorry, too many clients
  already», SQLSTATE 53300). Пачки по одному соединению и по десять остановились на той же
  границе.
- Резерв суперюзера — 3, а не «~10», и на это приложение он не влияет:
  `superuser_reserved_connections=3` (`pg_settings`), а роль `befos` на стенде суперюзер
  (`pg_roles.rolsuper=true`, `rolconnlimit=-1`), поэтому отказ пришёл на сотом соединении, а не
  на 97-м. Если в проде приложение ходит в базу не суперюзером — отнимите эти 3.
- Что видит клиент, когда мест нет. Обычный маршрут над `get_session` ответил `503
  database_unavailable` с `Retry-After: 5` и без текста драйвера; `/health/db` ответил `503
  {"status":"degraded","database":"unavailable"}`. Отказ сервера виден только в логе —
  `no database connection for this request (TooManyConnectionsError)`. Прежнее утверждение
  этого раздела — что четвёртая реплика будет ошибаться не «базой недоступна», а refused
  connection'ом — было неверно: человеку приложение отвечает именно «база недоступна», а refusal
  остаётся в логе оператора.
- После пика пул не пустеет. После 45 заёмов на стороне сервера осталось 13 соединений: 10
  держит сам пул (`pool_size` — это ещё и нижняя граница живых соединений), 3 — контейнер
  backend. То есть N реплик после первого же пика стоят 10N простаивающих соединений, а не ноль,
  и это и есть их «текущая нагрузка» между пиками.
- Сколько реплик влезает: 3 × 30 = 90 ≤ 100 — три процесса проходят своим пиком;
  4 × 30 = 120 > 100 — четвёртый начнёт получать отказы на пике, в покое же все три держат ~30.
  «Практически 3 реплики» подтвердилось, но граница теперь стоит на замеренных 100 принятых
  соединениях, а не на «100 минус ~10 резерва».
- Пропускная способность процесса — уже производная, а не замер: соединение занято всё время
  запроса (его берут до хэндлера), поэтому очередь начинается, когда висят 30 запросов сразу. На
  самых долгих из горячих маршрутов это 30 / 0.1397 с ≈ 215 запросов/с для `answers_submit`
  (медиана 139.7 мс на 10 000 анкет) и ≈ 767 запросов/с для `chat_history` (39.1 мс). Оба числа —
  деление опубликованных замеров задержки на потолок пула; прогоном под нагрузкой они не
  проверялись.
- Эти же числа не достижимы одним адресом: потолок лимитера 120 запросов в минуту на окно, то
  есть 2 запроса/с. 215 запросов/с требуют ≥108 разных ключей окна одновременно
  (215 × 60 / 120), а 767 — ≥384. Пока стенд стоит за прокси без `TRUST_PROXY_HEADERS`, все они
  считаются одним окном (см. §11), и узкое место переезжает из пула в лимитер: 120 запросов в
  минуту на адрес прокси — это 2 запроса/с на весь сайт, а не 215.
- `pool_pre_ping` ловит соединение, которое сервер закрыл, пока оно стояло в пуле.
- `pool_recycle=1800` выбрасывает соединение старше получаса: сеть между контейнерами
  (и любой NAT/Sidecar/proxy) забывает молчаливое TCP-соединение быстрее, чем это
  замечает пул.

Способ замера первых четырёх пунктов: `create_async_engine(url, pool_size=10, max_overflow=20,
pool_pre_ping=True, pool_recycle=1800)` и 45 задач, каждая из которых делает
`checkout_connection`, `SELECT pg_backend_pid()`, спит и закрывает сессию; параллельно
отдельное соединение с шагом 0.2 с считает
`select count(*) from pg_stat_activity where usename = current_user and backend_type =
'client backend' and pid <> pg_backend_pid()`. Потолок сервера — тот же цикл, но на
`asyncpg.connect` по одному соединению, пока не придёт отказ. Scratch-пробы этого вечера в
репозиторий не легли; механизмы (потолок = size + overflow, отказ по истечении
`pool_timeout`, форма ответа клиенту, сколько соединений пул держит после пика) закреплены
`backend/tests/test_pool_capacity.py`, который воспроизводит их на пуле 2+1 и на инъекции
замеренного класса отказа.

Остаток, который pre-ping не покрывает, измерен: если сервер закрыл соединение в
момент, когда пул уже его отдаёт, asyncpg поднимает `InternalClientError`, это не DBAPI-
ошибка, и pre-ping не может классифицировать её как разрыв. Замер после
`pg_terminate_backend`: из трёх подряд выдач одна поднимала ошибку, две следующие — нет;
пул выбрасывает отравленное соединение сам. Поэтому соединение берётся явно, до того как
хэндлер начал работать (`get_session`), и попытка повторяется один раз; если не удалось и дважды —
это 503 `database_unavailable` с `Retry-After: 5`, а не 500 с текстом драйвера.

### HTTP-соединения клиента: `--timeout-keep-alive 75`

Всё выше — про сторону «backend → база». У границы «клиент → backend» своя математика бездействия,
и она стоит в `docker-compose.yml` флагом uvicorn'у.

- Дефолт uvicorn — 5 с, и замер подтверждает, что он короче паузы между двумя действиями в
  приложении: сырой сокет с хоста видел FIN от сервера через 5000 мс после ответа, а второе
  заявление на паузах 8 / 20 / 40 с не получало ответа вовсе. С эмулятора тем же заявлением:
  пауза 1 с и 4 с → два ответа на одном сокете, 8 / 20 / 40 с → один.
- 75 с — замеренный компромисс: пауза 41 с между двумя действиями приложения соединение пережила
  (запрос пришёл на тот же порт запуска), а простой 121 с — нет (новый порт, ответ те же 200:
  OkHttp переподключается сам). Полный разбор — в `docs/SCALE_PLAN.md`.
- Если перед стендом встанет прокси с более коротким idle-таймаутом, это число должно стать меньше
  его, иначе сервер будет держать сокет, о котором прокси уже забыл, — та же причина, по которой
  `pool_recycle=1800` стоит выше.
- Держит это проверка `backend/tests/test_stand_keep_alive.py`: она читает команду сервиса из
  `docker-compose.yml` и сверяет флаг с тем, что реально читает `uvicorn.config.Config`. Это страж
  конфигурации, а не поведения — тестовый набор поднимает ASGI-приложение в процессе, где нет
  провода, который можно было бы засечь.
- Симметричную границу со стороны клиента назвала стадия 47: connect 5 с, пауза между байтами 10 с,
  потолок целого вызова 35 с, а загрузка фото поднимает их до 60 с и 600 с на уровне запроса
  (`HttpClientFactory.kt`, `ApiService.uploadPhoto`). На `--timeout-keep-alive 75` это не влияет:
  клиентский потолок считает от начала вызова, а не от последнего байта, и держит он спиннер
  экрана, а не сокет. Проверено на том же JVM-приборе, что и всё остальное в этом разделе:
  холостое WebSocket-соединение, поднятое тем же `createHttpClient` уже после правки, пережило и
  10-секундную строку сокета, и 35-секундный потолок — `incoming.receive()` висел 60 с и был снят
  только собственным таймаутом стенда (`TimeoutCancellationException` на 62 079 мс), а прежний
  клиент не закрыл такое же соединение за всё 70-секундное окно прогона ни под
  `socketTimeoutMillis = 15 s`, ни под `requestTimeoutMillis = 35 s`. Тот же замер показал и вторую
  сторону: за 60 с висения чтения на провод ушло 8 байт — маскированный `Close` со статусом 1000,
  выпущенный при отмене сессии, — и ни одного `Ping`, хотя `pingIntervalMillis = 10_000`.
  Переподключение чата поэтому опирается на завершение чтения, а не на pong-таймаут; механика
  heartbeat стадия не меняла (подробности — в `docs/ARCHITECTURE.md`).

### План соединения: `plan_cache_mode = force_custom_plan`

`backend/app/core/database.py` держит настройку в константе модуля `PLAN_MODE_CONNECT_ARGS`
(`{"server_settings": {"plan_cache_mode": "force_custom_plan"}}`) и передаёт её движку в
`connect_args`. Правка без миграции и без изменения API, и видна она не в запросах, а в том, как
соединение их исполняет, поэтому этот раздел и объясняет, куда смотреть, когда страница вдвое
медленнее, чем была. Константа лежит на уровне модуля, а не внутри одного вызова, потому что у
приложения есть второй движок, который обязан совпадать с этим: проба `backend/ops/scale_probe.py`,
которая публикует таблицу задержек, строит свой движок в `_stand_engine()` и берёт ту же строку —
иначе таблица «что стоит один вызов продукта» снята на соединении, которого в продукте нет.

Postgres планирует именованное подготовленное выражение по присланным значениям первые пять
исполнений, а потом вправе оставить один обобщённый план на весь остаток жизни соединения. Диалект
SQLAlchemy готовит и именует *каждый* текст и держит его в кэше на соединении, так что этот переход
принадлежит движку приложения, а не тому, кто писал SQL; `pool_recycle=1800` означает, что
соединение живёт полчаса и успевает прочитать горячий текст больше пяти раз.

Что это стоит и что даёт — снято стадией 57 на стенде 50 000 (таблицы в разделе «Парные прогоны
стадии 57» документа `docs/SCALE_PLAN.md`):

- пустая страница колоды: медиана 40 вызовов `DiscoveryService.feed` на одном соединении — 230.15 мс
  без настройки против 106.02 мс с ней; в серверном времени самого правила 192.52 против 65.89 мс;
  счётчики сервера после окна — 35 generic / 5 custom против 0 / 40.
- семь прочих горячих чтений (анкета зрителя, счётчик и ранг колоды, правило на открытой колоде,
  карточка, страница переписки, список пар) платят планированием 0.05…1.88 мс на вызов, медиана по
  отдельным обращениям +0.34 мс. Пять сдвигов из семи больше разброса между двумя позициями одной
  конфигурации.
- второй кандидат, `prepared_statement_cache_size=0` (диалект перестаёт держать выражение), дороже
  на всех путях без исключения: +4.13…+24.68 мс на вызов, +4.69 мс медианой на обращение. Отклонён.

**Как проверить на живом соединении.** `SHOW plan_cache_mode` на заимствованном из пула соединении
обязано отвечать `force_custom_plan`; `SELECT name, generic_plans, custom_plans FROM
pg_prepared_statements` не должно показывать обобщённых планов. Второй запрос — представление на
сессию: он отвечает только о том соединении, на котором выполнен, поэтому «проверить пул» означает
прочитать его на каждом backend-процессе (`pg_stat_activity` их перечисляет), а не один раз на
удачном. Окно из двенадцати одновременных заёмщиков поднимает от шести до десяти процессов — пул
возвращает соединение в очередь, и следующий заёмщик берёт его, а не открывает новый. Если страница
колоды на глаз стала вдвое медленнее, а в счётчиках появились generic-планы — первым делом сверяйтесь
с этой строкой: признак именно в переходе плана, а не в данных, и отличить его от медленного скана
можно по `Index Only Scan … loops = кандидатов` в плане. Охраняется проверкой
`backend/tests/test_the_engine_plans_from_the_values_it_is_given.py` — она читает и настройку, и
счётчики на движке приложения, с контролем на движке без настройки. Что настройка доходит до каждого
соединения пула, а не до одного, охраняет
`backend/tests/test_the_plan_setting_holds_on_every_connection_of_the_pool.py`: двенадцать заёмщиков
по восемь исполнений одного текста, счётчики читаются о каждом backend-процессе, и контроль на пуле
без строки обязывает хотя бы один из них переключиться. Пробу стенда охраняет
`backend/tests/test_the_stand_harness_measures_on_the_products_plan_mode.py`: она сравнивает
`SHOW plan_cache_mode` соединения продукта и движка `scale_probe.py` и не даёт циклу замера собрать
движок у себя.

**Что известно о настройке, кроме чтений (стадия 59).** Пути записи и вход в приложение измерены
парной чередой на стенде 50 000: `login`, `chat_history`, `like`, `answers_submit`, `test_complete`
на одном соединении, семь вызовов на путь. Прежнее соединение уходит в обобщённый план на всех пяти
путях (один текст из одного на входе, семнадцать из девятнадцати на отправке ответов), охраняемое —
ноль, и `generic + custom` на прежнем ровно равен `custom` на охраняемом: настройка меняет способ
планирования, а не число исполнений. Сдвигов, которые стоило бы приписать настройке, при этом нет:
медианы путей двигаются на −1.95…+2.70 мс, а два наибольших превышают разброс двух позиций на 0.10 и
0.13 мс — то есть на величины, которые метод парных прогонов не разрешает публиковать. Штраф
обобщённого плана, найденный стадией 57, привязан к чтению правила подбора колоды, а не к записи.
Пул продукта тоже измерен: в восьми окнах по двенадцать заёмщиков прежний пул переключился на всех
поднятых процессах, охраняемый — ни на одном.

**Чего настройка всё ещё не касается.** Замер под параллельной нагрузкой дал счётчики планов, но не
дал задержки: разброс двух позиций одной конфигурации на окне страницы колоды — 266.43 мс при сдвиге
66.29 мс, поэтому «дороже или дешевле страница под соседями» остаётся неоткрытым вопросом (числа —
в разделе «Парные прогоны стадии 59» документа `docs/SCALE_PLAN.md`). Двенадцать заёмщиков — меньше
потолка пула в тридцать, так что поведение, когда очередь доходит до `pool_timeout`, стадия не
мерила. Замеры сняты на двенадцати заёмщиках одного зрителя, то есть на самых спорных строках колоды,
и не моделируют нагрузку, распределённую по разным анкетам. Живая база приложения (291 анкета) не
измерена. Опубликованная таблица «Задержки горячих путей» в `SCALE_PLAN.md` закрывает пробел прибора,
но не нагрузки: с стадии 58 проба строит движок в `_stand_engine()`, который берёт ту же
`PLAN_MODE_CONNECT_ARGS`, и таблица переснята парной чередой прежнего движка с новым (стадия 57
оставила её снятой на `default`-планах; после пересъёмки `deck_exhausted` на 50 000 — 326.6 мс вместо
377.1 мс медианой, а его же максимум на 10 000 — 89.3 мс вместо 2 397.1). С стадии 67 тот же прибор
перед каждым путём сверяет статистику планировщика со строками, которые подготовил этот путь, и
таблица переснята им заново одним прогоном: `deck_exhausted` держит в ней 46.5 / 53.3 / 106.5 мс
медианой на 1 000 / 10 000 / 50 000 при семи чтениях за вызов. Держит
`backend/tests/test_the_stand_settles_statistics_before_timing_a_path.py`, механизм — раздел «Свёрка
статистики перед каждым путём (стадия 67)» того же документа.

## 8. Health-пробы: за чем следить

| Endpoint | Что утверждает | Код, когда базы нет |
|----------|---------------|---------------------|
| `GET /api/v1/health` | процесс backend жив | всегда 200 |
| `GET /api/v1/health/db` | соединение берётся и `SELECT 1` выполняется | 503 `{"status":"degraded","database":"unavailable"}` |

Healthcheck контейнера (`docker-compose.yml`) опрашивает `/health`, потому что «процесс
жив» и «база жива» — разные утверждения, и первое нужно для управления самим контейнером.
Алерт надо вешать на `/health/db`: при упавшей базе контейнер остаётся healthy, docker
его не перезапускает (перезапуск backend ничего против отсутствующей базы не делает), и
без пробы на базу вы об этом узнаете из жалоб.

Тело 503 на `/health/db` никогда не содержит текста ошибки драйвера — в нём есть host,
user и пароль строки подключения, а маршрут отвечает без логина. Проверено тестом.

У этого маршрута есть свой потолок — 60 запросов в минуту на адрес, отдельный от общего
лимитера API и от free-прохода `/health`. Причина не в процессоре, а в пуле: каждый запрос
к `/health/db` берёт соединение, которые делят настоящие пользователи, поэтому цикл по
нему без авторизации — способ оставить приложение без пула. Настройка алерта от этого
становится практической: интервал опроса должен быть заметно реже секунды, а 429 в ответ
на `/health/db` читается как «я спрашиваю слишком часто», а не как «сервис падает». Проверено
тестом: при уменьшенном потолке второй запрос ещё получает ответ про базу, третий — 429
`rate_limited`, и `/health` в это же время продолжает отдавать 200.

`/docs`, `/redoc` и `/openapi.json` в production не отвечают (404), и корневой ответ на `/`
на них не ссылается; на стенде в development все три работают. Если нужно прочитать контракт,
глядя на продакшен-образ, — поднимите тот же образ с `ENVIRONMENT=development` вне публичного
хоста, чем открывайте документ на живом сервисе.

## 9. Playbook

**База не отвечает.** Клиенты получают 503 + `Retry-After: 5` (Android показывает «сервис
временно недоступен», сессия не сбрасывается — 5xx это не logout). В логах:
`no database connection for this request (ConnectionRefusedError)`, у пробы —
`database probe failed`. Действие: `docker ps`/`docker inspect befos_postgres`,
`docker logs --tail 50 befos_postgres`. Если контейнер базы жив, а соединения нет —
смотрите диск и `max_connections`. Если контейнер мёртв — `docker start befos_postgres`,
дождаться `pg_isready`, затем `/health/db` должен стать 200 без перезапуска backend (пул
восстанавливается сам). Проверено: при `docker restart befos_postgres` outage занял
~2.1 с, за это время backend отдал 503 и 200, и ни одного 500.

**Диск полный.** Первые признаки — ошибки записи в логах postgres, затем `/health/db` 503.
Освобождать в таком порядке: дампы/архивы в `/tmp` контейнеров, старые Docker-образы
(`docker image prune`), затем — и только с копией — `VACUUM ANALYZE` по горячим таблицам.
Никогда не удалять файлы из `/var/lib/postgresql/data` вручную.

**Контейнер backend unhealthy.** `docker inspect --format '{{json .State.Health}}'
befos_backend`, затем `docker logs --tail 100 befos_backend`. Unhealthy при живом
процессе почти всегда означает, что база не даёт ответа, и начинать надо с postgres.

**Подъём нового образа backend на уже живом стенде.** С 2026-10-06 сервис в контейнере
работает не от root, а под пользователем `befos` (uid 10001), и каталог `/app/uploads` —
именованный volume — унаследует владельца из образа только если создан заново. Существующему
volume надо сменить владельца, иначе первая же загрузка фото упрётся в `Permission denied`, а
остальной сервис продолжит отвечать и ничего не подскажет:

```
docker exec -u root befos_backend chown -R 10001:10001 /app/uploads
```

Команда идемпотентна; проверка после неё — `docker exec befos_backend ls -ld /app/uploads`
(ожидается `befos befos`) и `/api/v1/health/db` в 200. Полный список того, что изменилось в
образе и почему, — в [`DEPENDENCIES.md`](DEPENDENCIES.md).

**WebSocket.** Сокет аутентифицируется один раз при handshake и живёт до disconnect.
Отказ при handshake пишется как `socket refused, ...` с указанием причины и без токена, и
закрывается кодом 1008. Если база падает в момент, когда сообщение уже в сокет-петле,
исключение ловит общий обработчик, пишет `WS error match=... user=...`, сокет закрывает,
и клиент переподключается; текст при этом не теряется — неотправленное сообщение остаётся
в поле ввода (закреплено тестом Android-слоя). WebSocket-путь открывает сессию сам, мимо
зависимости запроса, поэтому разорванное сервером соединение стоит ему одного упавшего
обработчика вместо прозрачного retry — этой правкой он сознательно не перекрыт.

## 10. Логи

`docker logs befos_backend` (stdout, плоские строки, JSON не используется намеренно —
один узел и человек вместо парсера):

```
2026-10-04 16:43:44 | WARNING  | app.core.database | c25062b2415d4a58 | no database connection for this request (ConnectionRefusedError)
2026-10-04 16:43:44 | INFO     | befos.access      | c25062b2415d4a58 | request GET /api/v1/users/me -> 503 in 5.7 ms
```

Поля: время, уровень, логгер, correlation id, сообщение. Каждое обращение к базе и каждая
строка доступа имеют один `X-Request-Id` на всю историю запроса; id принимается от
клиента только если это один печатный ASCII-токен, иначе генерируется свой. `slow request`
— WARNING при пороге 1000 мс. `/health` пишется на DEBUG, чтобы healthcheck
каждые 30 с не превращал лог в шум.

В логах не бывает: паролей, access/refresh токенов, значения `Authorization` заголовка,
содержимого запросов, строки подключения. Это закреплено тестами, а не договорённостью (`backend/tests/test_observability.py`).

## 11. Конфигурация и секреты

`JWT_SECRET` и `JWT_REFRESH_SECRET` в compose имеют значения по умолчанию только для
того, чтобы dev-стенд поднимался без ручной работы. При `ENVIRONMENT=production` такой
конфигурации контейнер не поднимется — `app.core.config` отклоняет секрет-заглушку,
секрет короче минимума, совпадающие access и refresh, `*` в CORS и http-адрес вместо
https, а вместе с ними ещё пять настроек, каждая из которых обходила бы остальные:
`DATABASE_URL` со значением из этого репозитория (прод обязан назвать свою базу), `DATABASE_URL`
с паролем `befos_password` — см. ниже, `DEBUG=true`
(на этом уровне asyncio и httpx пишут свои внутренности в тот же поток, что и access-лог —
в логах стенда это видно), `DEMO_ENABLED=true` и непронятое значение самого `ENVIRONMENT`.
Последнее важнее, чем кажется: прод определяется сравнением строки, поэтому `Productionn`
или пустая строка читались бы как «не production» и снимали разом все перечисленные проверки.
Теперь значение сверяется со списком понятных (`development`/`dev`/`test`/`staging`/
`production`/`prod`), и всё, чего список не знает, — ошибка старта.

Проверка `DATABASE_URL` сравнивает строку целиком, и одной этой проверки на compose не хватает:
`docker-compose.yml` собирает `postgresql+asyncpg://${POSTGRES_PASSWORD:-befos_password}@postgres:5432/...`,
то есть адрес, не равный литералу из `config.py`, но с тем же паролем, который напечатан в
`.env.example` и в самом compose. Поэтому прод смотрит не
на строку, а на компонент пароля DSN (`_database_password`) и отказывает, если там
`befos_password`. Измерено на живом контейнере: `docker compose run` с этим URL и
`ENVIRONMENT=production` падает на
`DATABASE_URL still carries the development database password this repository ships`, а с
переопределённым `POSTGRES_PASSWORD` и явно заданным `DATABASE_URL` — стартует и печатает
`environment=production`. Хост, на котором работает стенд, при этом не важен: отказ срабатывает
и для `@postgres`, и для `@db.internal`, и для `@10.0.0.5`.

Пароль dev-базы остаётся значением по умолчанию в compose — это осознанное удобство локального
стенда, и оно перестаёт быть безопасным в тот момент, когда репозиторий становится публичным.
Второй эшелон защиты — публикация порта: `127.0.0.1:5432:5432` вместо `5432:5432`. Хост при этом
не теряет доступ: `tests/conftest.py` по умолчанию берёт `localhost:5432`, и после этой правки
прогнанные хостовые тесты и `/api/v1/health/db` прошли как раньше. Меняется другое — стенд,
поднятый с этим файлом на сервере, больше не отвечает на 5432 наружным интерфейсом, где
известный из репозитория пароль был бы доступен любому, кто маршрутизируется до хоста.
`netstat -ano -p tcp` на стенде после `docker compose up -d --build` показывает единственный
listener `127.0.0.1:5432`.

`DEMO_ENABLED` до этой правки был написан в README и DEMO как переключатель, который не
пускает демо-аккаунт в развёртывание, и не читался никем: seed сеял его всегда. Теперь seed
его уважает — с `DEMO_ENABLED=false` стенд получает каталоги (интересы, вопросы, активности),
без которых приложение не работает, и не получает выдуманных людей. Проверено тестом
`test_the_demo_switch_decides_whether_people_get_seeded`: ноль строк в `users`, каталоги на месте.

Это проверка времени запуска, а не совести дежурного: неверный прод-конфиг обязан
остановить подъём, а не работать тихо. Реальные секреты в git не кладутся: в репозитории нет ни `.env` со
значениями, ни signing-ключа.

Одна переменная закрывает обе дыры сразу: `POSTGRES_PASSWORD` в корневом `.env` читается и
контейнером postgres (он создаёт базу с этим паролем), и подстановкой в `DATABASE_URL` сервиса
backend. Прод-стенд, поднятый с compose, обязан задать её значение сам — иначе он получит
отказ на старте, и это тот случай, когда отказ лучше тихо работающего стенда с паролем из
публичного репозитория.

`DATABASE_URL` содержит пароль, поэтому он не попадает ни в ответы, ни в логи, ни в
описания ошибок. Резервный дамп пароля не содержит, но содержит всё остальное.

### Лимитер: чьё окно считает ключ, когда перед приложением стоит прокси

Правило из README — «120 запросов в минуту, ключ берётся по адресу соединения, а не по
`X-Forwarded-For`» — читается из `app/core/rate_limit.py`, но до этой правки не читалось из
развёртывания: `_client_key` смотрит на `settings.trust_proxy_headers`, а uvicorn подставляет
заголовок вместо адреса соединения раньше, чем приложение успевает его не принять. Дефолты
обеих половин никто не записывал: `proxy_headers=True` и `forwarded_allow_ips="127.0.0.1"`, а
ни `docker-compose.yml`, ни `CMD` образа, ни команда в README флага не называли.

Замер на этом стенде (2026-10-10) — `GET /api/v1/users/me`, `RATE_LIMIT_PER_MINUTE` на дефолте
120, контейнер перезапускался между прогонами, потому что окно живёт в памяти процесса:

| Откуда и с чем шли запросы | Ответов | Отказов | Первый отказ |
| --- | --- | --- | --- |
| Хост через опубликованный `8000`, заголовка нет (130 заявлений) | 120 | 10 | 121-й |
| Хост через опубликованный `8000`, 30 ротируемых адресов в `X-Forwarded-For` (300) | 120 | 180 | 121-й |
| Loopback самого контейнера, те же 30 ротируемых адресов (300) | **300** | **0** | — |
| Loopback самого контейнера, один фиксированный адрес в заголовке (130) | 120 | 10 | 121-й |
| Loopback самого контейнера, заголовка нет (130) | 120 | 10 | 121-й |

Третья строка — это и есть дыра, а две последние — контроли, которые не дают прочитать её как
«трафик с loopback не ограничивается»: с одним фиксированным адресом в заголовке окно одно, и
отказ приходит на 121-м так же, как без заголовка. Потолок снимает именно ротация — 30 имён, 30
окон. Границы дыры честные: снаружи, через опубликованный порт, пир не входит в список
доверенных, поэтому подмены не происходит и правило работает. Срабатывает всё, что может открыть
соединение к бэкенду по loopback: любой процесс того же хоста, сосед по `network_mode`, SSRF на
`127.0.0.1` и — что важнее для этого проекта — документированный запуск без Docker, где сервер
слушает хост и каждый локальный клиент приходит с `127.0.0.1`; прогон той же матрицы на таком
сервере дал те же цифры (ротация — 300 ответов и 0 отказов, фиксированный адрес и отсутствие
заголовка — отказ на 121-м, а ротация от пира вне списка доверия, `127.0.0.2`, — отказ на 121-м,
что и указывает автора подмены: `ProxyHeadersMiddleware` uvicorn, а не `_client_key`).

Правка называет границу там, где её читает сервер, а не только там, где её читает приложение:
`--no-proxy-headers` в `command` compose, в `CMD` образа и в команде README. С ним адрес
соединения остаётся адресом соединения, и единственным местом, где объявляется доверие
заголовку, становится `TRUST_PROXY_HEADERS` — теперь он проброшен из `.env` в сервис backend и
написан в `.env.example`, а не живёт только в `config.py`.

Переснятая матрица на том же контейнере после правки: A, B, D и E не изменились ни в одном числе
(120 ответов, отказ с 121-го), а C — тот самый прогон с ротацией по loopback — даёт теперь 120
ответов и 180 отказов с первым на 121-м вместо 300 и нуля. Что переключатель не превратился в
«заголовок не читается никогда», проверяется на том же контейнере прямо: с `TRUST_PROXY_HEADERS=true`
те же 300 ротированных запросов отвечены все 300 и отказов ноль — окно снова на каждого
пользователя, но теперь по объявлению оператора, а не по умолчанию сервера.

Для стенда за прокси выбор у оператора один и тот же в обе стороны: доверять должна ровно одна
сторона — либо `TRUST_PROXY_HEADERS=true` (ключ — адрес из заголовка, который перезаписал
nginx/Caddy, окно на каждого пользователя), либо оставить `false` (ключ — адрес прокси, и тогда
все посетители сайта делят одно окно в 120 запросов в минуту, что на живом трафике превращается
в отказ всем сразу). Второй вариант не «безопаснее»: он просто считает не тех. Если прокси стоит
на том же хосте и флага `--no-proxy-headers` по какой-то причине нет, альтернатива —
`--forwarded-allow-ips` с адресом этого прокси, но тогда доверие объявляет uvicorn, а
приложение об этом не знает; держать два слоя доверия одновременно — способ потерять границу
вовсе.

Что правка не меняет, и это стоит знать до того, как цифра 120 станет спорной: окно
по-прежнему считается на адрес, а не на аккаунт, поэтому дом или мобильная сеть за NAT дают
одну корзину на всех её жителей, а `pod`-реплики за одним балансировщиком без
`TRUST_PROXY_HEADERS` — одну корзину на весь сайт. Отдельная корзина на аккаунт есть только у
кадров WebSocket (`_ws_frame_limiter`).

Держат это четыре проверки `backend/tests/test_rate_limit_trust_boundary.py`: две про ключ
в памяти приложения (при `trust_proxy_headers=false` три разных адреса от одного пира тратят окно
на третьем заявлении — 200, 200, 429; при `true` те же три адреса отвечены, а повторная
идентичность получает отказ), одна читает команды
запуска из compose, `CMD` и README и разрешает их через `uvicorn.config.Config`
(`proxy_headers is False`), и одна смотрит, что эта секция называет переключатель, флаг,
заголовок и потолок. Красное состояние на прежнем дереве снято дословно: `2 failed, 2 passed`
с `AssertionError: docker-compose.yml command lets uvicorn replace the peer address with
X-Forwarded-For, so the limiter's key is chosen by whoever sends the request` и
`docs/OPERATIONS.md has no limiter subsection — the page does not own this yet`.

## 12. Фото: предел тела, RAM и осиротевшие файлы

Загрузка одного фото — единственный путь, где клиент передаёт серверу большие байты,
поэтому у него три разных предела, и путать их дорого.

**Предел приложения (RAM).** `MAX_UPLOAD_SIZE_MB=5` (в контейнере не задан → дефолт).
Тело читается чанками по 1 МиБ и останавливается на превышении
(`photo_service.read_upload_capped`), поэтому заведомо слишком большое тело не проходит через
память процесса целиком. Замер на живом стенде: 60 МБ тело → ответ 422, RSS контейнера
вырос на 1.0 МБ; в изолированном замере самого обработчика — 60.0 МБ прироста до правки
против 6.0 МБ после.

**Предел тела (диск до того, как код его увидел).** Его в этом репозитории нет, и
приложение его не даст: multipart-парсер Starlette спилит тело во временный файл до
первого байта, который увидит хэндлер. Читает ли код 5 МБ или нет — на диск уже легло
всё. Ровно поэтому лимит размера обязан стоять на reverse proxy
(`client_max_body_size` в nginx/Caddy/Traefik), а приложение отвечает за содержимое.
Без прокси один узел принимает сколько угодно 60 МБ тел одновременно, и падает не
backend, а диск.

**Предел холста.** Заголовок изображения объявляет размеры, поэтому отказ считает пиксели
до того, как они выделены: `MAX_TOTAL_PIXELS = 80_000_000` (выше самой большой сенсорной матрицы
телефона сегодня и ниже собственных порогов Pillow, которые начинают ругаться при ~89 Мп
и отказывают при ~179 Мп — в промежутке объявленный холст уже оплачен памятью при decode).
`MAX_DIMENSION = 1600` — сторона, к которой снимок приводится (`thumbnail` + `draft` у JPEG
до того, как пиксели появились). Ответ — 422 `validation_error` со ссылкой на лимит, а не
500: это входные данные, а не поломка сервера. Проверено тестами.

**Удаление аккаунта забирает файлы.** `/uploads` — публичная статика без авторизации,
так что «анкета скрыта» и «снимков больше нет» — разные утверждения: url, который кто-то
успел открыть, отвечает, пока лежит файл. `safety_service.delete_account` удаляет строки
`photos` и после commit удаляет файлы. Проверено живьём: url отдавал 200 до удаления и
404 после, строк `photos` 0, файла на диске нет.

**Файлы без строк.** Оставаться в томе могут: неудачные загрузки (файл записан, строка не
создана), снимки, удалённые до этой правки, и файлы из распакованных копий. Read-only
сличение — посчитать, а не удалять:

```powershell
docker exec befos_postgres psql -U befos -d befos -tAc "select count(*) from photos"
docker exec befos_backend sh -c "ls /app/uploads | wc -l"
```

Измерено 2026-10-05 (после разборки мусора от QA-прогонов): 51 строка против 51 файла, 2.8 МБ;
сличение по именам — 0 осиротевших файлов и 0 строк без файла. Удаление — отдельное осознанное
действие, потому что файл в томе может относиться к ещё не накатанной строке, к копии,
которую кто-то распаковал, или к загрузке, чьё тело не дошло: прежде чем резать, сличите
список с дампом. Никакого планировщика чистки в репозитории нет, и появляться он без
решения о гонке «файл записан, строка ещё нет» не должен.

## 13. Удаление аккаунта: что стирается, а что остаётся

«Удалить аккаунт» — единственное обещание в приложении, которое пользователь не может
отменить сам, поэтому оно должно быть про данные, а не про экран. Реального `DELETE FROM users`
нет: схема оставляет строку (мягкое удаление), значит `ON DELETE CASCADE` в ней не срабатывает
никогда, и всё, что не стёрто кодом, переживает нажатие.

Что делает `safety_service.delete_account` (всё в одной транзакции, файлы — после commit):

- анонимизирует `profiles`: `name → 'Deleted User'`, `about → NULL`, `city → ''`,
  `lifestyle → {}`, `interests` очищаются, `is_hidden = true`;
- стирает ответы, которые нельзя вырезать без значения в колонке: `birth_date → 1900-01-01`,
  `gender → 'erased'`, `dating_goal → 'erased'`, `age_min/age_max → 18/18`,
  `gender_preference → []`, `city_preference → NULL`. Это не «реальные» данные — это значения,
  которые не могут прийти с формы, поэтому строку нельзя ни показать, ни подобрать;
- удаляет строки: `photos` (+ файлы с диска), `test_answers`, `test_results`,
  `compatibility_profiles`, `activity_preferences`, `discovery_queue` (свои карточки просмотра);
- гасит пары и переписку (`purge_social_graph`), закрывает сокет комнаты;
- `users`: `is_deleted/is_active = false`, `email → deleted_<uuid>@deleted.befos.local`,
  `password_hash → '!deleted'`, все `refresh_tokens` отзываются.

С правки стадии 110 удаление аккаунта — не единственная дверь, которая гасит эти строки: человек может
прочитать их сам (`GET /auth/sessions`) и закончить одну (`POST /auth/sessions/{session_id}/revoke`) или
все разом (`POST /auth/sessions/revoke-all`), не трогая анкету и своё слово. Оператору это меняет и способ
разговора: на «я не узнаю это устройство» больше не нужен SQL, чтобы показать человеку его собственные
данные, — список читается из-под его токена тем же маршрутом. Рукой в `psql` здесь стоит гасить только
то, до чего человек сам не дотянулся (утрачен доступ, ряд нужен снятым до разбора), и помнить об открытом
конце: отзыв строки не отзывает уже подписанный доступный токен, он доживает `ACCESS_TOKEN_EXPIRE_MINUTES`
(30 минут, `backend/app/core/config.py:63`).

Что остаётся намеренно:

- строка `users` и `reports`, поданные этим человеком или на него. Отчёт переживает уход
  того, на кого подан, иначе «Удалить аккаунт» становится способом сбежать от жалобы на
  harassment; с стадии 102 к тому же ряду относится и `report_reviews`: ряд решения модератора
  держит `moderator_id` ссылкой с `ON DELETE RESTRICT`, поэтому планировщик, который превращает
  анонимизированные строки в `DELETE`, упрётся в историю чужих решений и обязан будет оставить
  такие строки;
- анонимизированный профиль — он больше никого не описывает и никем не читается (все пути
  сначала спрашивают живого пользователя).

Проверено тестами (`backend/tests/test_privacy_lifecycle.py`, 3 теста): до удаления ответы,
результаты, вектор совместимости, аффинность активностей и колода существуют — после всех
пяти групп 0 строк, чужой аккаунт при этом не тронут; колонки-сентинелы стоят ровно те, что
написаны выше; репорт на удалившего аккаунт остаётся `open`. Живой путь стадии 102 добавил к
этому две сверки своими: жалоба и её история решений (`report_reviews`) переживают удаление
обоих аккаунтов, которых они называют (`s102_journey_run.log`, 16:30:49…16:31:00 UTC
2026-10-17, HEAD `d8a0957`), а удалённый аккаунт, у которого роль была, больше не проходит ни в
одну дверь: рукопожатие WebSocket отвечает `403`, `GET /reports` — `401` (строки лога
`a deleted account gets no room` и `a deleted account keeps no key to the queue`).

Отметка для того, кто читает dev-стенд: строки с `is_moderator = true` в нём есть, и это не
живые администраторы, а пробовые аккаунты живого пути, удалённые теми же прогонами
(`is_deleted = t`, войти нельзя). Прогон оставляет ровно одну такую строку, поэтому на стенде, где
путь снят дважды, их две: отдельный пересчёт dev-базы `befos` в 18:38:30…18:38:32 UTC того же дня
(`s102_dev_moderator_rows.log`, где напечатаны сами запросы) даёт 398 аккаунтов, две строки с
`is_moderator = true` — обе с `is_deleted = t`, — шесть строк в `reports` и четыре в `report_reviews`.
Из шести строк жалобы две записаны до этой стадии (3 октября, обе ещё `open`), а четыре написаны двумя
съёмами живого пути стадии 102: каждый съём заводит жалобу, доводит её до `resolved` двумя строками
истории (`open` → `reviewed` → `resolved`) и оставляет вторую жалобу нетронутой в `open`. Всё это —
ожидаемое состояние ряда после прогонов, а не признак заведённого админ-доступа.

**Backfill для аккаунтов, удалённых до этой правки.** Правка действует на будущее, поэтому в
dev-БД до неё висело на 126 уже удалённых аккаунтах: `test_answers=1974`, `test_results=470`,
`compatibility_profiles=94`, `activity_preferences=37`, `discovery_queue=1922`, один `match`
и два `like` с их участием, и у всех 126 профилей — настоящие `birth_date` и `gender`.
`backend/ops/anonymize_deleted_users.sql` приводит старые аккаунты к тому же обещанию. Скрипт
можно запускать повторно: каждое условие смотрит на `users.is_deleted`, поэтому второй прогон
даёт `DELETE 0` по всем девяти таблицам и только перечитывает те же сентинелы в уже
анонимизированные профили (`UPDATE 132` из тех же значений). Проверено двумя прогонами подряд
на dev-БД 2026-10-05. Порядок
— как с любой правкой данных: копия (раздел 2), прогоны на восстановленной копии, и только
затем рабочая база.

```powershell
docker exec befos_postgres sh -c "pg_dump -U befos -d befos --format=custom -f /tmp/pre_backfill.dump"
docker cp befos_postgres:/tmp/pre_backfill.dump "C:/backups/befos-pre-backfill-$(Get-Date -Format yyyyMMdd-HHmmss).dump"
docker exec befos_postgres psql -U befos -d postgres -c "create database befos_anon_drill owner befos"
docker cp backend/ops/anonymize_deleted_users.sql befos_postgres:/tmp/anon.sql
docker exec befos_postgres pg_restore -U befos -d befos_anon_drill --no-owner /tmp/pre_backfill.dump
docker exec -i befos_postgres psql -U befos -d befos_anon_drill -v ON_ERROR_STOP=1 -f /tmp/anon.sql
```

Дальше — тот же запрос-сверка, что и ниже, и только после нулей повторить две последние
команды с `-d befos` (и убрать `befos_anon_drill`).

```powershell
docker exec befos_postgres psql -U befos -d befos -c "select count(*) from test_answers ta join users u on u.id = ta.user_id where u.is_deleted"
```

Пройдено 2026-10-05: на копии — `DELETE 1974/470/94/37/1922`, `DELETE 1` (match), `DELETE 2`
(likes), `UPDATE 126`, `COMMIT`; после прогона все шесть счётчиков по нулям, живых аккаунтов 92,
репортов 2 (не тронуты). На рабочей dev-БД тот же скрипт дал ровно те же числа. `user_interests`
сошлись в ноль: интересы очищал и старый код удаления.

Два места, где SQL не угадывается, и скрипт это ловит по факту (первый прогон упал на первом
же и откатился целиком):

- `profiles.gender_preference` — это `varchar[]`, а не `jsonb`, поэтому пустота сюда пишется
  как `'{}'::character varying[]`; `'[]'::jsonb` — ошибка типа, а не тихая замена;
- `profiles.lifestyle` — наоборот `jsonb`, там `'{}'::jsonb` и должен быть.

Снимки такими аккаунтами: файлы уходят кодом только при удалении, а для старых аккаунтов
это отдельная проверка — сличение из раздела 12 покажет, остались ли сироты (2026-10-05:
51 строка / 51 файл / 0 сирот, то есть ни одного файла от удалённого аккаунта не осталось).

## 14. Модерация: очередь жалоб, решение по ней и снятие блокировки

Читатель у `reports` теперь и в приложении: поверхность разбора — три административных маршрута
(`GET /reports`, `GET /reports/{report_id}`, `POST /reports/{report_id}/review`,
`backend/app/api/v1/moderation.py`), каждый за дверью `get_moderator`
(`backend/app/auth/deps.py:56`), которая читает роль из строки аккаунта на каждом запросе. С правки
стадии 103 у этих трёх маршрутов есть клиент: секция «Модерация» на странице «Настройки» ведёт в
`android/app/src/main/java/app/befos/presentation/moderation/ModerationScreen.kt`, и секцию видит лишь
аккаунт, чьё собственное чтение назвало его модератором (`ProfileOut.is_moderator` —
`backend/app/schemas/schemas.py:110`, отвечают только хозяйские маршруты `/users/me…`, чтение —
`backend/app/api/v1/users.py:75`). Скрытие кнопки защитой не считается и держится не обещанием:
обычный аккаунт получает `403` от самого маршрута, это проверяют тесты поверхности. Команды ниже
остаются приборным путём — он нужен, когда разбор идёт, а экрана под рукой нет (утрачен доступ,
нужен точный ответ маршрута в терминале). Контракт страницы, карточки и перехода описан в
`docs/API.md` (раздел «Модерация»), поэтому здесь остаётся только то, что делает оператор.

**Инструкции «поставить статус через `psql`» в этом документе больше нет, и снята она не за
красотой.** Ручный `update reports set status = …` передвигает статус и оставляет `report_reviews`
пустой — ряд, у которого состояние изменилось, а память о том, кто и зачем это сделал, молчит.
Маршрут пишет статус и строку истории одним коммитом, поэтому способ передвинуть статус так, чтобы
история осталась, один: `POST /reports/{report_id}/review`.

**Первого модератора делает оператор, и это один осознанный шаг.** Пути записать `is_moderator`
через API нет: колонка без серверного значения, ни регистрация, ни правка профиля её не принимают, и
это держат `tests/test_an_ordinary_account_cannot_reach_the_moderation_surface.py` вместе с
`tests/test_route_guard_sweep.py`. Публичной регистрации модераторов в продукте нет, поэтому роль
записывают руками — ровно один раз:

```powershell
docker exec befos_postgres psql -U befos -d befos -c "select id, email from users where email = 'someone@corp.local';"
docker exec befos_postgres psql -U befos -d befos -c "update users set is_moderator = true where id = '<uuid>';"
```

Снимается роль тем же `false` и перестаёт действовать со следующего запроса, а не через час: JWT её
не несёт, её читают со строки аккаунта.

Очередь читают и решают по ней и с экрана, и через API; ниже — приборный путь: токен берут входом
модератора, `-ContentType` обязан быть
с `charset=utf-8` (ловушка ниже), ряд отдают страницей, решение пишут переходом:

```powershell
$t = (Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/auth/login -ContentType 'application/json; charset=utf-8' -Body '{"email":"<почта модератора>","password":"…"}').tokens.access_token
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/reports?status=open&limit=50" -Headers @{ Authorization = "Bearer $t" } | ConvertTo-Json -Depth 5
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/reports/<report-uuid>" -Headers @{ Authorization = "Bearer $t" } | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/v1/reports/<report-uuid>/review" -ContentType 'application/json; charset=utf-8' -Headers @{ Authorization = "Bearer $t" } -Body '{"status":"reviewed"}'
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/v1/reports/<report-uuid>/review" -ContentType 'application/json; charset=utf-8' -Headers @{ Authorization = "Bearer $t" } -Body '{"status":"resolved","comment":"<почему закрыли>"}'
```

Ряд идёт от самой старой жалобы, `next_cursor` передают обратно как `after_id`, `limit` не больше
ста. Закрыть жалобу можно только с комментарием (до 1000 символов), а `resolved` и `dismissed` —
тупики: опечатку не переписывают вторым решением, на неё отвечает следующая жалоба того же человека,
которая приходит своим рядом и решается заново. Текст — `details` от автора жалобы и `comment` от
модератора — лежит в колонках, то есть попадает в дамп базы и в `pg_restore`-копию раздела 2, и не
попадает в логи: access-лог пишет маршрут, код и длительность, но не тело запроса (раздел 10).

**Ловушка в кодировке тела: Windows PowerShell кладёт кириллицу в `?`.** Замер: `Invoke-RestMethod`
с `-ContentType 'application/json'` и телом, где комментарий жалобы написан по-русски, отдаёт на
приём 62 байта, в которых вместо каждой русской буквы стоит `0x3f`, — сервер принимает такой запрос
как хороший и пишет в `report_reviews.comment` строку вопросительных знаков, которую уже никто не
восстановит. С `-ContentType 'application/json; charset=utf-8'` те же байты приходят в 82 и
декодируются в исходную фразу; `curl.exe --data-binary "@review.json"` даёт ровно те же 82, потому
что передаёт файл как есть и не пропускает его через кодировку строки PowerShell. Прогнано
17:32:34…17:32:35 UTC 2026-10-17 на версии `5.1.26100.7462` против локального эхо-приёмника, который

прогон стадии 103 держит и новые две проверки сигнала роли — свежий аккаунт отвечает `False`, а после
операторского `UPDATE` то же чтение на том же токене отвечает `True` (прежний съём того же ряда —
132/132, `s102_journey_run.log`, 16:30:49…16:31:00 UTC). Разница двух съёмов не случайна и записана
здесь нарочно: дверь стоит до разбора тела, поэтому PowerShell-половина проверена только до неё, а
переход с русским комментарием целиком снят Python-клиентом живого пути. Тот же ряд переснят деревом стадии 104 —
144/144, `s104_journeyC.log`, 01:59:56…02:00:10 UTC 2026-10-18 против образа, собранного этим деревом
(`docker inspect` создания образа — 2026-10-18T01:52:09Z, сверка md5 продуктовых файлов ряда города —
`s104_image_parity.txt`), — и очередь модератора остаётся пройденной в этом же прогоне: шаг, где анкета
доходит до решения модератора, читает `GET /reports` и пишет `POST /reports/{id}/review`, а город одного из
аккаунтов задан тем же рядом, то есть дверь и город держатся одним прогоном, а не двумя разными сборками.

С правки стадии 101 блокировку снимает само приложение: «Настройки» → «Кого вы заблокировали» →
тап по «Разблокировать» с подтверждением, и `DELETE /users/{user_id}/block` убирает строку под тем
же замком пары, который берут блокировка и `like`. SQL ниже остаётся приборным путём — на случай,
когда человек пишет оператору, а доступ к экрану утрачен; он делает ровно то же удаление строки и
тоже не возвращает ни пару, ни переписку, удалённые при блокировке.

```powershell
docker exec befos_postgres psql -U befos -d befos -c "delete from blocks where blocker_id = '<blocker>' and blocked_id = '<blocked>';"
```

Дальше всё обычным путём, и это следует из кода, а не из обещания: подбор исключает пару
anti-join'ом по `blocks` (`social_repo._acted_conditions`), а `like` проверяет
`is_blocked_either` (`match_service`), поэтому без строки блокировки человек снова приходит
в ленту, а `like` с обеих сторон создаёт новый `match` — с новым `id`, старую переписку не
поднимет уже ничего.

## 15. Что здесь честно не сделано

- Нет PITR: точка восстановления — момент последнего дампа, а не произвольная секунда.
  Для этого нужны `archive_mode`/`wal_level=replica` и хранилище вне хоста.
- Нет планировщика копий (см. раздел 5) и нет назначения вне хоста — нужен адрес и ключ.
- Одна база, без реплики и без read-реплики для аналитики; тяжёлый отчёт ляжет на
  рабочие соединения.
- Миграция накатывается на старте контейнера — правильно при одном реплике, гонка при
  нескольких (раздел 6).
- `pool_recycle` стоит на 30 мин, потому что нативный балансир/прокси в этом стенде не
  задан; если появится облачный proxy с более коротким idle timeout, recycle должен стать
  короче его.
- Проверка копии здесь исполняется руками. Как только появится планировщик, drill
  (`restore → compare → drop`) должен запускаться по расписанию, потому что копия,
  которую не проверяли, портится незаметно.
- Удаление аккаунта не удаляет строку `users` (раздел 13): мягкое удаление держит FK и
  историю пар, поэтому «стёрто» означает «ничего, что описывает человека», а не «строки нет».
  Планировщика, который превращает анонимизированные строки в `DELETE`, нет, и без решения
  о сроках хранения появляться он не должен.
- Снятие блокировки (§14) возвращает анкету в подбор, но не пару: переписка удалена безвозвратно,
  и новый `match` заводят двое заново — двумя `like`. Карточка, которую смотрели до блокировки,
  в колоду не приходит (`new_candidate_ids` добирает только тех, кого колода не держала), а
  разблокированный человек ни о чём не уведомляется: push-архитектура в продукте не реализована.
- Читатель у `reports` есть и в интерфейсе, и в API — с правки стадии 103 очередь рисует экран
  (`presentation/moderation/ModerationScreen.kt`), а три маршрута разбора (§14) отвечают и ему, и
  терминалу. Не сделано здесь другого: публичной регистрации модераторов в продукт не заложено,
  роль по-прежнему ставит только операторский `UPDATE`, и экранных средств управления ролей нет.
  Уведомления модератора о
  новой жалобе тоже нет: push-архитектура не реализована, очередь читают по расписанию руками — с
  экрана или из терминала, — и
  пока её читают, заявка на разбор ничего не обещает автору жалобы — приложение ему о статусе
  разбора не сообщает никогда (так записано в карточке отправки и держится тестом).
- Список своих устройств (§13) не приводит никого за собой: о новом входе человек не узнает, пока сам не
  откроет «Настройки», — уведомления о входе нет, потому что push-архитектура в продукте не реализована.
  Название строки — ровно то, что о себе сказало устройство: маршруту нечем додумывать модель, и с правки
  стадии 110 Android-клиент начинает называть себя сам (`BeFoS/<версия> (<модель>, Android <релиз>)`), а
  ряды, записанные до этой правки и чужими клиентами, так и остаются подписаны библиотекой или пустыми.
- `/uploads` — статика без авторизации: любой, кто знает url, получит снимок, пока лежит
  файл. Приватность здесь держится на непредсказуемости имени и на удалении файла вместе
  с аккаунтом, а не на проверке права.

## 16. Стенд, посеянный до правки: чиним процент пары

`matches.compatibility_score` — это то, что показывают список пар и заголовок пары. До
правки его писали только seed (литерой `0.82`) и взаимный лайк, и никто не перечитывал
после пересдачи теста, поэтому на dev-стенде 2026-10-05 четыре демо-пары давали
`list=single=82` против живых `67/67/56/66`. Код исправлен — уже посеянный стенд сам не
починится, но и пересев ему не нужен: путь ниже. Стенд, о котором идёт речь (dev,
`demo@befos.app`), исправлен этим путём 2026-10-06, и теперь признак даёт 0 расхождений из
7 пар; повтор 2026-10-08 против пересобранного образа — 0 расхождений из 8 пар (пар стало
больше, стенд живой). Раздел остаётся в руководстве, потому что на любом стенде, посеянном
старым seed, расхождение появится снова.

Проверка (она же признак): у одной пары сравнить `compatibility` из
`GET /api/v1/matches` с `overall` из `GET /api/v1/matches/{match_id}/compatibility` под
демо-аккаунтом (`demo@befos.app`). Различаются — строки посеваны старым seed. Сверяется
через API, а не SQL, потому что сравнение считает Python-движок.

- **Основной путь — перечитать проценты через API, ничего не перезаписывая:** `PATCH
  /api/v1/users/me` под демо-аккаунтом со значением поля, из которого складывается процент, —
  таким, каким оно уже стоит (цель отношений: `{"dating_goal": "relationship"}`). Движок берёт
  вектор ответов, набор интересов и цель (`app/compatibility/engine.py:19`), поэтому полем
  ремонта обязано быть одно из `_SCORE_FIELDS` (`profile_service.py:56`): только они вдвоём
  вызывают `refresh_pair_scores` (`compatibility_service.py:46`). До стадии 35 путь был
  расписан городом (`{"city": "Москва"}`) — город входил в `_REC_FIELDS` и по нему крутился
  веер, хотя процента город не меняет. С 2026-10-08 город роняет только кэш страницы
  активностей и больше не пересчитывает процент, так что предписание, написанное городом,
  молча ничего не починит. Обе половины сняты прогоном, а не рассуждением. На dev-стенде
  против пересобранного образа: строке пары возвращён посевной литерал (`compatibility_score =
  0.82` при живых `63`), `PATCH` с городом, равным текущему, оставил `stored = 82`, а `PATCH`
  с целью, равной текущей (`relationship`), вернул `stored = 63 == live`; после этого тот же
  признак прошёл по всем восьми парам демо-аккаунта — 0 расхождений. В наборе те же две
  половины держит
  `tests/test_compatibility.py::test_a_patch_that_changes_nothing_repairs_a_percent_seeded_wrong`.
  Замер 2026-10-06 на dev-стенде: до — четыре пары `82` против живых `67/67/56/66`, после —
  `stored == live` у всех семи пар (три совпадали и до: `72/73/72`). `app.seed --force` для
  этого не нужен.
- **Пересев нужен, когда заново нужна вся демо-база:** `docker compose exec backend python
  -m app.seed --force`. `--force` вызывает `_clear_domain` и удаляет все доменные строки,
  включая аккаунты, заведённые руками на эмуляторе. Так делать только на demo-базе и
  никогда на боевой.
- **Естественный путь:** процент перезапишется сам, как только кто-то из пары пересдаст
  тест или изменит `interests`/`dating_goal`. Правка города процент не трогает — с стадии 35
  она роняет лишь кэш страницы активностей пары. На живом стенде это происходит само
  собой; демо-пары никто не редактирует — поэтому для них и существует путь выше.

После пересева те же четыре пары дают `stored == live` с теми же числами (замер на
отдельной базе `seed_check`, создана и удалена: 67/67, 67/67, 56/56, 66/66). Оба пути
сходятся в одну точку, потому что оба зовут `compute_compatibility` на текущих ответах;
разница в цене — пересев ради четырёх чисел обнуляет весь доменный слой стенда, `PATCH`
не обнуляет ничего.

## 17. Расхождение справочников: что делает посев, а что — ревизия данных

`docker-compose.yml` перед запуском uvicorn исполняет `python -m app.seed --if-empty`, и с
стадии 71 эта команда называет расхождение справочных строк, а не молчит о нём. Возникает оно
потому, что справочники пишутся в пустую таблицу: в непустую посев дописывает только то, чего
в базе ещё нет. Правка каталога (`interests_catalog.py`, `activities_catalog.py`,
`questions_catalog.py`) до существующей строки не доходит никогда, и до стадии 71 команда об
этом не сообщала ничего.

Что видно в логе. Снято той же командой в образе, собранном этим деревом (`myapp-backend:latest`,
id `6e6f9b1386cd`; `md5sum /app/app/seed.py` даёт `3a3c0a6b9e9d48a67ae1409181849811` — тот же, что
у рабочего файла), на одноразовой базе `befos_s71_rt`, где строке `art_exhibition` возвращён
прежний массив тегов (артефакт `s71_image_seed.txt`, прогон 03:43:48…03:45:36 UTC):

```
2026-10-12 03:45:09 | WARNING  | __main__ | - | Catalogue drift: 1 reference row(s) in this
database are not what the code ships. … What disagrees:
  activity art_exhibition (id=3) holds interests=['painting', 'design', 'theatre', 'art'],
  the catalogue ships interests=['painting', 'design', 'theatre']
```

Команда отвечает `exit 0`, а строка остаётся прежней: `art_exhibition` после прогона прочитан
снова и держит тот же массив. (Первая строка блока в логе — одна, здесь она перенесена для
ширины.) Контроль той же команды на чистой рабочей базе `befos` — ноль
строк расхождения, `exit 0`, `DEMO_ENABLED=false`.

Почему посев называет, а не чинит:

- Переписать строку, которую оператор правил руками, — то же самое, от чего отказала ревизия
  `7c4f2a91be36`, условившая каждый `UPDATE` прежним массивом (`WHERE slug = … AND interests =
  <список>`). Ревизия чинит каталог, который она увидела, а не редактуру чужого стенда.
- Варианты теста не переписываются и здесь: `test_answers.option_id` указывает на вариант,
  который человек действительно выбрал, поэтому замена его текста или числа перечитывает
  прошлые ответы как ответы на другой вопрос.
- Интерес, которого каталог больше не называет, держит `user_interests` через
  `ON DELETE CASCADE`, так что удаление строки выбрасывает чужой выбор. Посев такую строку
  только называет.

Сколько строк называет посев на живых базах. Снято вызовом тех же функций
(`_row_drift`, `_extra_row`, `_questionnaire_drift`) над строками, прочитанными `psql`, — ничего
при этом не записано (артефакты `s71_scale_lines.txt`, 03:15…03:16 UTC и `s71_scale_lines_v2.txt`,
04:25:52…04:26:00 UTC, где к списку добавлена четвёртая база):

| База | Строк расхождения | Что названо |
|---|---|---|
| `befos` (рабочая) | 0 | — |
| `befos_test` (стенд pytest) | 0 | — |
| `befos_scale` (50 000 анкет) | 16 | 7 списков тегов активностей, 7 полей пяти интересов (переименованные и перегруппированные строки), 2 slug'а, которых каталог больше не содержит |
| `befos_s59new` (50 000 анкет, стенд стадии 59) | 16 | те же 16 строк тем же прогоном; карточек с недоступным тегом — 7, прочитано `count(*)` |

Анкета не даёт строки ни на одной из четырёх баз: все 21 позиция и их варианты совпадают с
каталогом даже на стенде, посеянном до того, как каталог вырос. Из расхождения
`befos_scale` в 48 полей (`s71_drift.txt`, 02:28 UTC) 34 — интересы, которых на стенде нет
вовсе: их посев дописывает молча, потому что добавление строки ничего не отнимает.

Что делает оператор. Перенос правки каталога в базу, где строки уже есть, — дело отдельной
ревизии данных (`UPDATE`, условленный прежним значением по образцу `7c4f2a91be36`), а не посева.
Если расхождение и есть редактура этого стенда, warning остаётся как факт: он ничего не
блокирует и на пустой базе не печатается. Проверяется это тем же путём, что и снимок выше, —
`docker compose run --rm --no-deps backend sh -c "python -m app.seed --if-empty"` против нужной
базы через `-e DATABASE_URL=…`.
