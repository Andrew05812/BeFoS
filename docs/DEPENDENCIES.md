## Политика зависимостей

Правила, которые применялись к этому проекту, а не правила, которые красиво выглядят:

1. **Runtime-зависимости пинятся ровно** (`пакет==вершина`). Никаких `>=`, `~>`, `*` и
   «latest». Контейнер, который отдаёт трафик, должен быть тем же контейнером, на котором
   тесты проходили; `>=` это утверждение ломает.
2. **Тестовые инструменты — отдельно** (`backend/requirements-dev.txt`). Файл
   `requirements.txt` читает сборка образа, `requirements-dev.txt` — только локальный
   прогон pytest и живой путь E2E. Проверено в собранном образе: `pytest`,
   `pytest-asyncio`, `httpx` в нём отсутствуют.
3. **Заведомо уязвимую версию не оставляем.** Перед тем как оставить пин или поднять его,
   артефакт прогоняется через аудит ниже. Если для пакета есть опубликованный advisory и
   есть залатанный релиз, который не ломает продукт, — пакет поднимается до него.
4. **Один пакет — один осмысленный коммит с тестами.** Массовые апгрейды «ради свежих
   версий» не делаются: неподнятый пин, на который нет advisory, — это осознанный выбор, а
   не долг (см. «Что не обновлено»).
5. **Транзитивные зависимости не пинятся вручную.** Их сдерживают пины прямых зависимостей,
   а проверка идёт по resolved-графу, а не по файлу манифеста, — потому что дыры живут в
   графе, а манифест их не называет.
6. **Lock-файла нет, и это решение, а не забывчивость.** `pip freeze` на Windows не
   отдаёт `uvloop` (он под маркером `sys_platform != "win32"`), поэтому lock, сгенерированный
   на dev-машине, молча убрал бы runtime-зависимость Linux-образа. Источник истины — пины
   плюс аудит resolved-графа. Lock появится вместе с CI, где его будет
   генерировать сам раннер на Linux.
7. **Секретов в зависимостях нет.** Ни signing-ключей, ни `.env`, ни токенов в дереве;
   плейсхолдеры в `.env.example` — не секреты, и `ENVIRONMENT=production` отказывается
   стартовать, пока они остались в конфиге.

## Аудит: как это проверить самому

Инструмент — [`../backend/ops/check_advisories.py`](../backend/ops/check_advisories.py).
Он спрашивает ту же базу GitHub Security Advisories, которой пользуется Dependabot, но по
resolved-графу, а не по манифесту. Тот, кто хочет проверить проект, не обязан верить ни
этому документу, ни чужому скриншоту:

```bash
# backend ровно так, как его собирается контейнер
docker compose build backend
docker exec befos_backend python -m pip freeze \
  | python backend/ops/check_advisories.py --pip-stdin

# мобильное приложение так, как его разрешает Gradle
cd android && ./gradlew :app:dependencies --configuration debugRuntimeClasspath > tree.txt
python ../backend/ops/check_advisories.py --gradle-tree tree.txt

# то же самое глазами Dependabot (нужен токен с read:security_events)
curl -H "Authorization: Bearer $GITHUB_TOKEN" \
  "https://api.github.com/repos/Andrew05812/BeFoS/dependabot/alerts?state=open&per_page=100"
```

Анонимный запрос к advisory API живёт под лимитом 60 вызовов в час, а полное дерево Android —
порядка 165 артефактов, поэтому для дерева нужен `GITHUB_TOKEN`. Код возврата — 1, если найден
хотя бы один affected или хотя бы один запрос упал; молчаливое «ничего не нашлось» невозможно
перепутать с сетевой ошибкой, а непрочитанный диапазон печатается как `UNPARSED`, а не
додумывается.

Замер 2026-10-06 после исправлений:

```
checked 204 artefacts; affected 0; unparsed ranges 0; query errors 0   # 39 pip + 165 maven
checked  30 artefacts; affected 0; unparsed ranges 0; query errors 0   # сам контейнер backend
```

Для экосистемы `docker` advisory API GitHub фильтра `affects` не принимает (HTTP 422), поэтому
базовые образы проверялись тем, что умеют их пакетные менеджеры:

| Образ | Команда | Результат |
|---|---|---|
| `python:3.12-slim` (backend) | `apt list --upgradable` внутри готового образа | 0 пакетов |
| `postgres:16-alpine` | `apk version -l '<'` | 3 пакета новее в репозитории |
| `postgres:16-alpine` | `apk audit --sys` | 0 пакетов с известной уязвимостью |

`apk audit` читает ту же базу Alpine secdb, поэтому «новее в репозитории» здесь и означает
«обновление доступнее, чем дыра»: для `libcrypto3`/`libssl3` 3.5.8-r0 и `libldap` 2.6.14-r0
открытых advisory на момент замера нет.

## Инвентаризация alert'ов до исправления

На момент замера на репозитории висело **40 открытых Dependabot-alert'ов**: все в экосистеме
`pip`, все в одном манифесте — `backend/requirements.txt`. По severity: 1 critical, 20 high,
15 medium, 4 low. В `gradle` и `docker` — ни одного.

| Пакет | Alert'ов | Severity | Было | Залатано в | Достижимо в BeFoS? |
|---|---|---|---|---|---|
| `pillow` | 17 | 13 high, 4 medium | 11.0.0 | 12.1.1 / 12.2.0 / 12.3.0 | частично — см. ниже |
| `PyJWT` | 15 | 1 critical, 4 high, 9 medium, 1 low | 2.10.1 | 2.12.0 … 2.15.0 | частично — см. ниже |
| `python-multipart` | 7 | 3 high, 1 medium, 3 low | 0.0.20 | 0.0.22 … 0.0.31 | да, полностью |
| `pytest` | 1 | 1 medium | 8.3.4 | 9.0.3 | нет (тестовый инструмент) |

**PyJWT.** Сервис вызывает только `jwt.encode` и `jwt.decode` — с одним алгоритмом
(`HS256` из настроек, `algorithms=[settings.jwt_algorithm]`), с обязательными claims
`exp`/`sub`/`type` и с двумя разными секретами: отдельный для access, отдельный для refresh.
Ключ всегда приходит из конфигурации. Пути, где проверяющий ключ достаётся из чужого JWK, в
коде нет: `PyJWKClient`, `PyJWK` и `get_signing_key_*` по всему `backend/app` не встречаются.
Отсюда вердикт по классам (это вывод по месту вызова, а не проверка эксплуатации):

- *Недостижимо при текущем способе вызова* — всё, что живёт в загрузке и разборе JWKS: SSRF
  через схему URL (#31), redirect при загрузке набора ключей (#35), усиление запросов по
  `kid` (#30, #33), обрыв разбора JWK Set на битом RSA-JWK (#32), несогласованные `x/d` в
  OKP-JWK (#40), RecursionError до проверки подписи (#39), DoS на неиспользуемом сегменте
  detached-JWS (#13), ReDoS в `is_pem_format` (#38) — последняя срабатывает на *ключе*, а
  ключ в BeFoS выбирает оператор, не гость.
- *Достижимо, потому что вход целиком выбирает атакующий* — токены, которые приходят в
  заголовке: прием незнакомых `crit`-расширений (#3, high) и принятие публичного ключа
  (PEM/DER/JWK) за HMAC-секрет (#36 critical, #12, #34). Второе в этом проекте прикрыто
  сверху — секрет берётся из настроек, а не из запроса, — но ровно этот класс обхода
  (CVE-2022-29217 и его продолжения) закрывается апстримом, а не нашей конфигурацией.
- *Отдельно про неканоническую подпись* (#37, обход отзыва через raw-token): в BeFoS refresh
  хранится как SHA-256 от строки токена и ищется по этому хешу
  (`generate_token_hash` → `tokens.get_by_hash`), поэтому пересобранная запись подписи не
  «обходит отзыв», а не находит сессию и отказывает. Поведение и так fail-closed, и alert
закрыт тем же подъёмом версии.

Подъём до 2.15.1 закрывает все 15: статус alert'а зависит от версии пакета, а не от того,
дошёл ли кто-нибудь до уязвимой функции, поэтому вручную «достреливать» их пометкой
«не используется» здесь нечем и этого не делалось. Дополнительно к подъёму регрессии
проверяют, что PEM-материал не принимается как HMAC-секрет, а подделанный токен не открывает
ни HTTP-запрос, ни сокет.

**Pillow.** 17 alert'ов делятся на три разнородные кучи. Декодеры чужих форматов (PSD, TIFF,
FITS, PDF, JPEG2000, McIdas, GD) и их bomb-guard'ы — были достижимы, потому что `Image.open`
выбирает парсер по магии в теле файла, а не по полю `Content-Type`, которое клиент написал сам:
до этой правки jpeg-подписанный PSD долетал до PSD-парсера. Закрыто двояко: подъёмом до 12.3.0
и списком `ACCEPTED_PIL_FORMATS` в `app/services/photo_service.py`, который сверяет уже
распознанный `image.format` с множеством JPEG/PNG/WEBP/MPO — форматы, которые продукт честно
поддерживает. Шрифтовые декодеры (Bdf/Pcf/`FontFile`) достигаются только через `ImageFont`, а
этот путь в проекте использует один файл — DejaVu TTF, лежащий в репозитории
(`app/seed_data/placeholder_images.py`), то есть не ввод пользователя. `WindowsViewer`
(#23) и TGA-энкодер (#25) — API, которые нигде не вызываются (`image.show()` и запись `.tga`
в коде отсутствуют); `ImageCmsTransform` (#29) и `RankFilter` (#24) требуют цветовых профилей и
фильтра ранга, которых в конвейере нет. `Image.paste()`/`crop()` (#26) — этот путь вызывается
при усечении превью, поэтому он и закрыт версией, а не аргументом «не пользуемся».

**python-multipart.** Единственный пакет из списка, где весь класс дыр лежит на главном пути:
каждая загрузка аватара проходит через парсер рамок. Неограниченные заголовки части,
отрицательный `Content-Length`, квадратичный разбор `;`, preamble/epilogue — всё это выбирается
байтами запроса, а не настройкой сервера. Поднят до 0.0.32 (залатано последнее — 0.0.31).
`Content-Disposition`-smuggling (#14, #15) и «произвольная запись файла» (#1) бьют в то место,
которого продукт не даёт тронуть: имя файла из заголовка не используется нигде, имя на диске —
`uuid4().hex` плюс расширение из уже проверенного content-type. Регрессии проверяют и это: для
имени вида `../../../escape.png` ответный URL обязан совпадать с
`^/uploads/[0-9a-f]{32}\.png$`, и ни один файл не должен появиться вне каталога загрузки.

**pytest.** CVE-2025-71176 (обращение с `tmpdir`) — в инструменте, который крутится только на
машине разработчика и в тестовом прогоне, в образ его не включают. Поднят всё равно: версия
была единственная, которая тянула за собой пару с `pytest-asyncio` (тот объявляет
`pytest>=8.4,<10`), и 9.1.1 + 1.4.0 — единственная такая пара, которая и залатана, и согласована.

Ставка на «не трогать» здесь осознанная: стек Android отстал от апстрима по номерам, но по
аудиту на нём нет ни одной опубликованной дыры, а подъём Compose BOM или Ktor — это смена
поведения приложения, которую надо проверять на устройстве, а не в тесте сборки. Порядок
действия, когда такая необходимость появится (новая фича, требование совместимости, или
advisory): поднять один слой, прогнать `:app:testDebugUnitTest` и живой путь на эмуляторе,
и только потом следующий. Откладывать пачку апгрейдов «на потом» смысла нет — тогда не
будет понятно, что именно изменило поведение.

## Docker: что проверено в образе

Манифест сборки — [`../backend/Dockerfile`](../backend/Dockerfile).

- **Двухстадийная сборка.** Колёса собираются в одноразовом builder-этапе
  (`pip wheel --no-index --wheel-dir /wheels -r requirements.txt`), рантайм-этап ставит их
  с `--no-index --find-links=/wheels`: при установке образа сеть не нужна, и компилятор
  рантайму не нужен вовсе. Проверено в собранном контейнере: `gcc`, `g++`, `make`
  отсутствуют; размер образа 410 MB.
- **Не root.** `USER befos` (uid/gid 10001), каталог загрузки принадлежит ему. Проверено:
  `docker exec befos_backend id` → `uid=10001(befos)`.
  Внимание при подъёме образа на уже живом стенде: именованный volume `befos_uploads`
  наследует владельца из образа только когда создан заново, поэтому существующий volume
  сменить владельца — `docker exec -u root befos_backend chown -R 10001:10001 /app/uploads`
  (идемпотентно) либо пересоздать volume, — иначе сервис не сможет писать загрузку. Замер на
  текущем стенде: `drwxr-xr-x 2 befos befos /app/uploads`, запись в него проходит.
- **Тестовой обвязки в образе нет.** `pytest`, `pytest-asyncio`, `httpx` — в
  `requirements-dev.txt`, который сборка контейнера не читает. Оговорка, чтобы не
  преувеличивать: исходники тестов в образ попадают вместе всего остального (`COPY . .`),
  запустить их там нечем — раннера в установленном наборе нет.
- **Порты.** `8000` наружу — это и есть сервис; `5432` публикуется как `127.0.0.1:5432:5432`
  и наружу не смотрит. Правило loopback-only в силе, и регрессия на него есть.
- **Секреты.** В образе их нет; всё приходит через environment. Дефолтные значения
  (`befos_password`, плейсхолдеры `JWT_SECRET`/`JWT_REFRESH_SECRET`, demo-аккаунт) —
  удобства разработки, и `ENVIRONMENT=production` отказывается стартовать, пока DSN всё ещё
  несёт дефолтный пароль.
- **Healthcheck.** `curl --fail` на `/api/v1/health` каждые 30 s с `start_period: 60 s`
  (в этом окне идут миграции и сид). Ответственность разделена: `/api/v1/health/db`
  отдельно проверяет, что база подключается, — «процесс отвечает» и «базу видно» разные вещи,
  и на что шуметь, описано в [`OPERATIONS.md`](OPERATIONS.md).
- **Замер после пересборки.** `docker compose config`, `build`, `up -d`;
  `/api/v1/health` → `{"status":"ok","app":"BeFoS","environment":"development"}`,
  `/api/v1/health/db` → `{"status":"ok","database":"connected"}`.

## Регрессии, которые держат эту работу

[`../backend/tests/test_dependency_security.py`](../backend/tests/test_dependency_security.py)
— 44 теста. Они не «проверяют версию пакета», а проверяют поведение, ради которого версию и
поднимали, так что downgrade снова сломает тесты, а не отчёт.

- **JWT**: токен с чужим секретом, просроченный, без `exp`/`sub`/`type`, с подменённым
  алгоритмом (`none`, HS512 под allowlist HS256), битые рамки (пусто, одно/два/три слова,
  пробелы), подмена типа access↔refresh, PEM-материал как HMAC-секрет, минимальная длина
  секрета, которую принимает прод-валлидация, — и что сокет, собранный на непроверенном
  токене, не открывается (закрытие с `1008`).
- **Загрузка изображений**: тело с чужой магией (TIFF/GIF/BMP/PPM) отказывает и на сервисном
  уровне, и как 422 на маршруте; content-type вне списка (включая `image/svg+xml` и `None`)
  отказывает; EXIF вырезается, большая канва ужимается; oversized-тело отказывает, сессия
  после этого жива; пустое тело отказывает.
- **Имя файла**: `../../../escape.png`, `..\\..\\escape.png`, `uploads/../../escape.png`,
  `C:\\Windows\\System32\\escape.png` → URL обязан быть `^/uploads/[0-9a-f]{32}\.png$`, и
  рядом с каталогом загрузки не появляется ни один новый файл.
- **multipart-рамки**: запрос без boundary, с boundary, который нигде не встречается, с
  400 KB заголовков части, обрезанная часть, отсутствующее поле — все как 400/422, без 500 и
  без висячего соединения; после серии битых хороший аплоад всё ещё работает, а JSON-маршрут
  битый multipart не задевает.
- **Отключённый аккаунт**: `is_active = false` → 401 с кодом `disabled`.

## Остаточные риски

Здесь намеренно перечислено то, что осталось открытым. Формулировка «проект защищён»
к этому документу не применяется.

1. **Alert'ы закроются не мгновенно.** Dependabot пересчитывает default-ветку; пока фикс не
   попал в `main`, 40 alert'ов числятся открытыми, и PR #1 (`chore(deps): bump pyjwt from
   2.10.1 to 2.15.0 in /backend`) остаётся висеть — он предлагает 2.15.0, тогда как здесь
   стоит 2.15.1. Вручную alert'ы не достреливались.
2. **Аудит ловит только опубликованное.** Advisory появляется через дни или недели после
   дыры, а `pillow` и `python-multipart` из этой пачки чинили именно что post-disclosure.
   Регламент пересмотра — ниже.
3. **Список форматов — узкое место, которое надо помнить.** `ACCEPTED_PIL_FORMATS` защищает
   постольку, поскольку продукт поддерживает JPEG/PNG/WEBP/MPO. Первая же фича, которая
   начнёт принимать GIF или рисовать текст по байтам пользователя, обязана одновременно
   вернуть сюда регрессию, иначе защита превратится в легенду в комментарии.
4. **`/uploads` остаётся открытой статикой** без проверки прав: доступ держится на
   непредсказуемости имени и на удалении файла вместе с аккаунтом. Это известный предел из
   [`../SECURITY.md`](../SECURITY.md), и подъём зависимостей его не касается.
5. **Базовые образы отстают от репозиториев дистрибутивов**, а не от advisory: на момент замера
   открытых дыр на `postgres:16-alpine` не было, но digest надо обновлять по расписанию,
   иначе «нет дыр» превратится в «дыра есть, а образа нет».
6. **Нет lock-файла и нет CI-гейта.** Проверка зависимостей — ручной запуск скрипта; пока
   конвейера нет, ничто не мешает кому-то смёржить пин на уязвимую версию, не заметив этого.
   Первый кандидат при появлении CI — `check_advisories.py` с кодом возврата 1.
7. **Android-старый стек без дыр — всё ещё старый стек.** 0 advisory сегодня не обещают 0
   завтра, а подъём Compose BOM или Ktor потом будет дороже, чем по одному слою сейчас.
8. **`uvloop` под маркером платформы** значит, что локальное окружение Windows и образ Linux
   исполняют разный набор пакетов. Это честно для аудита (граф читается в контейнере), но
   значит, что «у меня локально зелёный» само по себе ничего не утверждает.

## Регламент пересмотра

- Планово: перед каждым релизом и, независимо от релизов, раз в месяц — прогон
  `check_advisories.py` по контейнеру и по дереву Gradle, плюс список открытых Dependabot
  alert'ов.
- По триггеру: при добавлении новой прямой зависимости; при любой правке в
  конвейере загрузки изображений или авторизации; когда появляется фича, описанная в пункте 3
  остаточных рисков.
- Что делать при находке: добавить/пробежать регрессию на поведение, поднять версию ровно до
  залатанной, прогнать backend-набор, живой путь и `:app:testDebugUnitTest`, откоммитить
  отдельно и обновить этот документ — версия, alert, достижимость, результат замеров.
